# NEW_AGENT.md — точка входа для нового чата

Проект: minimarket (собственный интернет-магазин с Joomla 6 в качестве CMS).
Репозиторий: komarovblog/minimarket. Рабочая ветка: `development`. Ветку `main` не изменять, не выполнять merge или force-push без отдельного явного решения пользователя.

## Граница проекта — обязательно для каждого нового чата
**В этом чате разрешён только репозиторий `komarovblog/minimarket` и только рабочая ветка `development`.** Это отдельный проект Joomla 6. **Репозиторий Shop — другой независимый проект на Symfony, который ведётся в другом чате.** Запрещено открывать, читать, искать, изменять файлы, ветки, задачи, настройки и коммиты Shop, обращаться к нему через инструменты или переносить оттуда код/ТЗ без отдельного явного поручения пользователя. Не путать названия, среду, технологический стек и план развития. Перед КАЖДОЙ операцией GitHub проверять точное полное имя репозитория `komarovblog/minimarket` и ветку `development`; несоответствие — остановка.

## Обязательный порядок чтения
1. `NEW_AGENT.md` — правила разработки и передачи контекста.
2. `docs/CONTEXT.md` — актуальные требования, архитектура, принятые и открытые решения.
3. `docs/PLAN.md` — пронумерованные этапы, подэтапы и их статус.
4. `CURRENT_TASK.md` — единственная активная задача и критерии готовности.
5. `logs/LAST_RUN.log` — результат последнего консольного запуска, если существует.
6. Только затем исходный код и прочие файлы, относящиеся к задаче. При противоречии между кодом и документацией: описать расхождение, не угадывать.

## Неизменяемые принципы
1. Простота прежде всего: минимальное число файлов, зависимостей, слоёв и команд; никакого усложнения «на будущее». Сначала объяснить, зачем новая сущность.
2. Разработка только в `development`. `main` не трогать. Не делать reset --hard, force-push, автоматический merge или удаление пользовательских данных.
3. Перед **каждой** локальной командой проверки использовать единый скрипт запуска, который проверяет ветку, выполняет `git fetch` и `git pull --ff-only`, удостоверяется в совпадении локального HEAD с `origin/development` и прекращает работу при конфликте или локальных изменениях. Никогда не скрывать ошибку синхронизации.
4. Результаты всех консольных проверок: команда (без секретов), время, SHA до/после, код завершения и **санитизированный** полный вывод — в `logs/LAST_RUN.log`. Скрипт коммитит и отправляет лог в `development` даже при неуспешном тесте. История прошлых запусков сохраняется в истории Git без множества отдельных лог-файлов. Если push лога не удался, явно сообщить об этом; «Готово» недостаточно для подтверждения результата.
5. Пользователь обычно отвечает только «Готово». После этого ассистент самостоятельно читает обновления и логи в GitHub, проверяет SHA/ошибки и выдаёт **один следующий** конкретный шаг. Не требовать копировать консольный вывод, если доступ к логу работает.
6. После **каждого** принятого изменения требований, плана, архитектуры и после **каждого** изменения кода обновлять затронутые `docs/CONTEXT.md`, `docs/PLAN.md`, `CURRENT_TASK.md` в том же коммите, где это уместно. Никаких решений «только в чате».
7. Секреты и машинно-зависимые параметры только в локальном `.env`, который игнорируется Git. `.env.example` содержит **все и только** актуальные имена параметров, безопасные примеры и русские пояснения; изменения ключей синхронизировать в обе стороны. Реальные секреты не включать в код, логи, документацию и Git.
8. Код и важные нестандартные решения комментировать **по-русски**, объясняя причины, входы/выходы, ограничения. Не добавлять комментарии, повторяющие очевидную строку.
9. Не ломать рабочий функционал: маленькие изменения, сначала воспроизводимая проверка, затем фиксация результата. При ошибке остановиться и диагностировать, а не повторять потенциально опасные операции.
10. **НИКОГДА НЕ МЕНЯТЬ ЯДРО JOOMLA.** Никаких правок/замен файлов, классов, библиотек, стандартных шаблонов и плагинов CMS; никаких изменений структуры системных таблиц, обхода штатных проверок и правок Joomla ради магазина. Используем ТОЛЬКО официальные API и штатные расширения (компоненты, модули, плагины, события, ACL, маршрутизатор). Разделять торговые сервисы и тонкий слой Joomla; собственная схема БД MiniMarket не меняет схему Joomla.
11. Писать переносимый код, не завязываться без необходимости на Docker. Локальная разработка и обычный PHP-хостинг должны использовать общие бизнес-правила и документированные различия конфигураций.
12. Не хранить в Git временные дампы БД, архивы сборок, `vendor`, кэши и разрозненные диагностические файлы. Архивы/резервные копии — отдельно от рабочего репозитория.
13. Любое потенциально разрушительное действие (изменение схемы с потерей данных, отмена/очистка истории, перезапись окружения) только после отдельного согласования и с проверяемым резервным копированием.
14. Не утверждать «готово», пока не проверены код/тесты, зафиксирован результат, подтверждён удалённый SHA и обновлена документация.
15. Производительность — основное нефункциональное требование: SSR без обязательного JS, минимум SQL и сетевых запросов, индексирование горячих запросов, корректная инвалидация публичного кэша; пользовательские корзины, платежи и заказы не кэшировать публично.
16. Один торговый объект с типом product/bundle, без дублирования бизнес-логики корзины и заказа; новые сущности только при доказанной потребности.
17. Перед разработкой новых возможностей сверяться с `docs/CONTEXT.md`: не переносить автоматически масштабную функциональность другого проекта Shop в минимальный MiniMarket.
18. Пользователи, пароли и сессии — только штатные API Joomla; собственный кабинет может хранить лишь контакты/настройки/заказы. Не создавать вторую базу паролей.
19. Цена, скидка, доставка и итог — только из доверенных серверных источников; данные браузера проверять, сумму платежа сверять с сохранённым заказом и API ЮKassa. Денежные значения — без float, использовать минимальные единицы.
20. Раздел администратора — штатный дизайн и формы Joomla; не создавать собственную тему админки. Сообщения email/Telegram/MAX и SMS OTP не должны блокировать оформление заказов или раскрывать секреты.
21. Вход на витрине по решению пользователя: **МТС ID, Сбер ID, Яндекс ID, VK ID, телефон с OTP MAX/SMS**. Email только необязательный канал уведомлений — не логин, не регистрация, не восстановление. Реализовать только подключённые и проверенные интеграции; внешний provider+subject связывать с одним Joomla user_id, не объединять аккаунты по совпадению телефона/email. Пароли покупателей не запрашивать. Соблюдать OAuth/OIDC security.

22. **ОБЯЗАТЕЛЬНАЯ УДАЛЯЕМОСТЬ:** весь MiniMarket — штатно устанавливаемый/обновляемый/удаляемый пакет собственных расширений. После удаления компонентов, модулей и плагинов нет зависимостей/хуков MiniMarket, Joomla, её стандартная админка и страницы работают как прежде, а ядро не менялось. Не обещать абсолютно побайтовое состояние прежней установки: собственные данные/настройки/содержимое и история CMS могут оставаться. Собственные таблицы и заказы при обычном удалении по умолчанию **сохранять** для восстановления; полная очистка — отдельная явно подтверждённая необратимая операция, сначала протестированная на копии.
23. **КАЖДОЕ ОБНОВЛЕНИЕ JOOMLA — ТОЛЬКО ЧЕРЕЗ ОЦЕНКУ СОВМЕСТИМОСТИ.** Пользователь может прислать ссылку или скрин страницы обновления, но новый чат обязан самостоятельно прочитать официальные release notes/changelog, требования PHP/MySQL, security fixes, изменения и deprecations API, затем сравнить их с текущим кодом и версиями зависимостей на GitHub, описать риски. Не считать релиз совместимым без теста, не начинать обновление PROD автоматически.
24. **ПОШАГОВЫЙ БЕЗОПАСНЫЙ АПДЕЙТ:** сначала проверенный бэкап файлов+БД и тест восстановления; затем изолированная staging-копия со строго отключёнными реальными платежами, SMS и уведомлениями; на ней обновить Joomla, выполнить smoke+регрессию каталога, URL/SEO, фильтра, корзины, OTP/ID входа, заказов, ЮKassa в sandbox, dataLayer, ACL и скорости, а также install/update/uninstall пакета. Зафиксировать Joomla/PHP/MySQL/версию MiniMarket, SHA, PASS/FAIL и логи в GitHub. PROD обновлять только после PASS и отдельного решения, с планом отката.
25. **ЕСЛИ ОБНОВЛЕНИЕ ЛОМАЕТ МАГАЗИН:** исправлять только собственные расширения и адаптеры, а не ядро Joomla. Пока проверка не PASS, отложить обновление на PROD; при критических исправлениях безопасности ускорить тесты, но не пропускать их. Возврат — по проверенному плану восстановить согласованные файлы и БД с учётом новых заказов/платежей.
26. **ОФОРМЛЕНИЕ ПО ЛОГИКЕ DNS:** на одной странице авторизованный пользователь заполняет только недостающие поля без OTP, гость может войти либо заполнить заказ без регистрации. Гость получает код MAX/SMS только после заполнения и подтверждения заказа; успешная проверка не создаёт Joomla-аккаунт и не открывает кабинет другого пользователя. Цена и доставка всегда серверные.

27. **Перед командами Windows определить оболочку.** Консоль Open Server Panel может открывать CMD (`C:\OSPanel>`), а наши команды используют PowerShell (`PS C:\OSPanel>`). Никогда не предлагать вставлять PowerShell в CMD: явно дать команду `powershell` для переключения либо написать CMD-совместимый вариант. Не трактовать синтаксические ошибки CMD как проблемы Apache/Joomla/Git; сначала изучить присланный вывод. В OSP 6.5.1 для MiniMarket Apache/PHP/MySQL включены, но HTTP-ответ самого сайта требуется проверить отдельно.

28. **GitHub ↔ локальная Joomla — строго разделены.** Исходный код MiniMarket, XML-манифесты, SQL-миграции, тесты и скрипт сборки держать только в `src`/`scripts` репозитория `komarovblog/minimarket` (`development`). Само ядро Joomla, живые данные, runtime-файлы OSP и `configuration.php` находятся в игнорируемом `public`/`.osp` и БД MySQL; **единственное исключение** — отслеживаемый профиль `.osp/project.ini` и заглушка `public/.gitkeep`. Синхронизировать с GitHub только собственные исходники, а затем устанавливать собранный компонент и модули через штатный Joomla installer; никогда не править установленные копии расширений вручную как единственный источник кода. Миграции создают/меняют только собственные `#__minimarket_*` таблицы в **той же БД, что и Joomla**, отдельное подключение/БД компоненту не требуется. После удаления пакета Joomla должна работать.
29. **Сначала проверяем фактическую синхронизацию.** Ассистент может писать в GitHub, локальный пользователь получает только fast-forward после проверки текущей ветки/локальных изменений. Автоматическая доставка логов Windows → GitHub всё ещё не подтверждена: не обещать её до успешного end-to-end теста. На первом этапе развёртывание ZIP вручную, затем компактный скрипт сборки, не строить лишнюю инфраструктуру.

30. **Новая чистая структура OSP 6.5.1:** в Git хранится `.osp/project.ini` (без секретов) с `web_root = {base_dir}\\public` и `public/.gitkeep`, но не сама Joomla. `scripts/setup-local.ps1` создаёт только одноразовый локальный `public/index.php` для проверки PHP/HTTP; перед установкой Joomla он заменяется оригинальным индексом. Перед чистым клонированием всю старую MiniMarket-папку перенести вне WebProjects в резервную копию; никакого удаления без бэкапа. Старые непроверенные `run.ps1`, `diagnose.ps1` и `logs/LAST_RUN.log` удалены из текущей рабочей ветки, доступны через Git history. В новом чате продолжать по `CURRENT_TASK.md`, не предлагать запуск удалённых скриптов.

31. **Публичная структура сайта для хостинга:** вся РАБОТАЮЩАЯ Joomla 6 в `public` (администратор, ядро, установленные версии MiniMarket, медиа); на хостинг переносится содержимое `public` прямо в `public_html`. `src/com_minimarket`, `.git`, `docs`, `scripts`, `.osp` — разработка вне DocumentRoot; не помещать их в `public` ради удобства копирования. Собственный код обновляется через ZIP Joomla. Структура и логика переноса: `docs/STRUCTURE.md`. Джумла ещё не установлена; будущие папки не путать с уже существующими.

32. **Единственный актуальный путь OSP с 30.10.2026:** `C:\OSPanel\home\minimarket.local`, веб-корень `C:\OSPanel\home\minimarket.local\public`, а в конце `public` соответствует `public_html` хостинга. Пользователь отключил каталог `WebProjects` из поиска проектов в Open Server. Не предлагать старый путь `C:\Users\User\Desktop\WebProjects\MiniMarket`, перенос старого клона или переустановку всей панели. Если папка `home\minimarket.local` не существует — клонировать `development` именно в неё; если существует — не перезаписывать без осмотра. `.osp/project.ini` с `{base_dir}\public` уже подходит без изменений. Подробности и один следующий шаг — в `CURRENT_TASK.md`.

## Как продолжать после смены чата
- Проверить `development` на GitHub; прочитать документы в указанном порядке.
- Проверить последние коммиты и `CURRENT_TASK.md`. Старые скрипты `run.ps1`, `diagnose.ps1` и журнал `logs/LAST_RUN.log` удалены из текущей ветки как непроверенные. До восстановления проверенного Git-push не обещать автоматические логи; результаты локальной проверки сообщает пользователь.
- Сформулировать: что завершено, что не завершено, текущий номер шага, критерий следующего шага.
- Продолжать с `CURRENT_TASK.md`, не начинать новую самостоятельную разработку и не повторять выполненные действия.
- Перед работой подтвердить соблюдение правил **10 и 22–25**: нет правок ядра, обновление только после официального анализа и теста на staging, штатное удаление пакета не ломает Joomla. Любую предложенную правку ядра отклонить и найти поддерживаемый API/расширение.

## Ограничения текущей инициализации
Пока не создана тестируемая реализация Joomla-расширения. Настоящие тесты, деплой и перенос функционала из отдельного Shop запрещено считать завершёнными до проверки. Набор команд и сред уточняется по мере разработки без лишней инфраструктуры.
