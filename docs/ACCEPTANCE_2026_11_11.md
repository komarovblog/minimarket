## Контракт SKU-экспорта/импорта v2 (до написания кода)

**Строка = продаваемая позиция (SKU), а не абстрактный товар.** Если у товара есть 5 сочетаний размеров/цветов — 5 строк с одним `product_id` и разными `variant_id`/`sku`. У простого товара без вариантов — одна строка с базовым SKU. Комплекты — отдельный вид строки со ссылкой на SKU/состав. Не создавать второй вид товара под вариант.

**Постоянные столбцы:** `product_id`, `variant_id`, `sku`, `product_type`, `product_title`, `category_id`, `category_title`, `published`, `price`, `old_price`, `stock_mode`, `stock`, `currency`, `brand`, `collection`, `image`, `weight_grams`, `volume_cm3`. Цена по принятому правилу общая для SKU одного товара, но значение повторяется в строках для удобства.

**Динамические колонки:** `attribute:<code>` для каждого информационного атрибута, `option:<code>` для каждого выбранного измерения SKU, системные атрибуты — с фиксированными стабильными ключами. Код, не локализованный заголовок, должен быть идентификатором для безопасного импорта; человекочитаемые подписи — в XLSX второй строкой или отдельной легендой.

**Без потери данных:** XLSX может иметь листы `SKU`, `Products`, `Categories`, `Attributes`, `Options`, `Bundles`. CSV для SKU — одна строка на вариант. JSON — те же сущности со структурированными связями. Экспорт v2 не подменяет v1 без парного и атомарного импорта/предпросмотра; проверить несколько SKU на один товар, импорт с ведущими нулями, запасами, сохранение связей и обратимость. Изменение формата — отдельный новый релиз.

## Контракт категории «Показывать в списке товаров»

- Флажок для каждой привязанной характеристики и опции категории, рядом с её режимом «наследовать / включить / обязательно / отключить».
- Влияет **только на карточку товара в списке**. Не удаляет характеристику из товара, не исключает значения из фильтра и не изменяет набор продаваемых SKU.
- Наследование: если категория переопределяет свойство, она может переопределить флажок. Иначе действует значение родительской категории. Для старых привязок — прежнее видимое поведение, никакой внезапной массовой потери свойств.
- Реализация: обновление схемы/миграции и моделей сохранения, серверное чтение на витрине, тесты fresh и upgrade, RU/EN и обе темы. Нельзя добавлять только галочку, если витрина её не читает.

## Контракт редактора сочетаний

Категория ограничивает доступные опции; после выбора опции показываются только её опубликованные значения. Каждая следующая строка «+ опция/значение» формирует комбинацию, после чего создаётся/выбирается реальный SKU, а невозможные значения отключаются по AND-совместимости. Сохраняется существующая матрица SKU — новая сущность или альтернативная база сочетаний не создаётся.

## Контракт системных атрибутов

Для каждого системного поля (цена, наличие, артикул, бренд и прочие существующие) отдельно задать: **используется ли в фильтре**, какой вид фильтра допустим по типу (число — диапазон/ползунок, текст — поле, выбор — флажки/радио и т.д.) и где отображается (карточка товара/карточка в списке/обе). Хранение в Основных настройках, единый явный default, чтение в реальном `FacetedCatalog`, `CategoryDisplayOptions` и шаблонах; тесты на несовместимые комбинации.

## Контракт checkout: регистрация, подтверждение и дополнительные поля

- Гость либо обязательная регистрация/подтверждение, только через единый Joomla `user_id`, без отдельной базы пользователей MiniMarket.
- Способ подтверждения выбирается только из **реально подключенных и работающих** методов (email через штатную Joomla регистрацию; SMS/ID — после адаптеров). Письмо активации и OTP-код — **разные механизмы**; не называть ссылку активации кодом.
- Поля «Имя / Телефон / Почта / Комментарий»: скрыто / необязательно / обязательно; маска и ограничения валидируются на сервере, не только в JS. Дополнительные поля «+» со стабильными идентификаторами, типом, длиной, маской, режимом, санитайзингом, сохранением снимка в заказе.
- Порядок: заполнить → подтвердить выбранным методом, если требуется → создать/подтвердить Joomla-account → атомарно создать заказ с серверными SKU/суммой → открыть подтверждение. Учесть повторный submit, CSRF, скорость/лимиты OTP, невозможность захвата чужого email/телефона, гостевой сценарий и rollback.
- Пока сквозной контракт не готов, существующая Joomla registration link и guest checkout остаются явными, без фиктивного обещания подтверждения при отправке заказа.
