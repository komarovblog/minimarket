# MiniMarket — обязательный регламент каждой итерации

**Применяется всегда до изменения исходников.** Репозиторий `komarovblog/minimarket`, `development` (не `main`). Источники: [карта](MASTER_PLAN.md), [реестр настроек](SETTINGS_REGISTRY.md).

## Перед началом

1. Прочитать `AGENTS.md`, `docs/MASTER_PLAN.md`, `docs/SETTINGS_REGISTRY.md`, `docs/ITERATION_RULES.md`, свежий `CURRENT_TASK.md`.
2. Назвать **ровно один этап** из карты, исходный Git SHA, сущности, зависимые сервисы, таблицы, формы, интерфейсы, затрагиваемые настройки и потенциальные расширения. Перед новым модулем/плагином проверить EXT-реестр; без явного обоснования новый пакет запрещен.
3. Записать приемочный контракт (формы/поля/поведение/база/URL/публикация/RU-EN/темы/мобильность) и точный end-to-end сценарий «настройка → хранение → потребитель → результат → тест».
4. Выписать, что НЕ меняем; установить способ бэкапа, upgrade и rollback. При изменении сущности/SQL — миграция без потери данных и fresh install.
5. Убедиться, что базовые PHP/PowerShell/JS/SQL и release-проверки уже зелёные; если нет — сначала устранить препятствие, не выпускать ZIP с известным CI FAIL.

## Реализация

6. Работать внутри существующего компонента, не дублировать сервисы/таблицы/поля. Только нативные контролы Joomla и устойчивые версии API; Joomla core не трогать.
7. Изменять вместе форму, сохранение, чтение, бизнес-логику, интерфейс потребителя, обе локализации, разрешения/валидацию, тесты и документацию.
8. На настройку заполнить реестр: фактический путь сохранения, читающий сервис, наследование, эффект, тест. Неподключённые поля либо скрыты/заблокированы, либо помечены как неготовые.
9. Исправлять старые тесты, если они проверяют устаревший контракт, но не отключать реальные регрессии и не подгонять их под ошибку. Проверять как PowerShell 5.1, так и используемые в CI среды.

## Проверка и завершение

10. Запустить проверки всего необходимого набора: синтаксис, unit/integration, БД 8.4 fresh/upgrade, рус/англ, светлая/тёмная, desktop/mobile, права, поиск/сортировка, реальные CRUD/внешние связи, ZIP-inspection. CI PASS отдельно от Joomla browser PASS.
11. Только при PASS сформировать версионированный `com_minimarket-<version>.zip`; `mod_minimarket_toolbar` остается отдельным ZIP; SQL демоданных не импортируется автоматически и никогда не включается в компонент.
12. Пользователь устанавливает на реальную Joomla и проверяет приемочный сценарий. До подтверждения статус только «проверено кодом» или «ожидает браузерной приёмки», не «готово».
13. По итогу внести в `CURRENT_TASK.md` commit SHA, версии/артефакты, пройденные проверки, список открытых рисков, статус раздела, необходимые будущие интеграционные тесты. Обновить мастер-план, реестр и Google Doc как читаемую копию; не плодить новый файл правил для очередной версии.

## Неизменные статусы

`спроектировано → реализовано → интегрировано → автоматические тесты PASS → браузерная приемка PASS → принято`. При непройденном предыдущем шаге следующий запрещен. Если зависимость еще не создана — `ожидает интеграции`, а не `готово`.
