# MiniMarket / Shop — проектирование жизненного цикла заказа v2, 13.11.2026

**Статус:** проектная модель для следующей реализации (не путать с уже работающей логикой). Источник приоритетов: утверждённое [Shop REQUIREMENTS_V2](https://github.com/komarovblog/shop/blob/development/docs/REQUIREMENTS_V2.md), §§6.4–6.6, 6.10–6.16, 11.3–11.4. Shop — ТЗ, а не реализованный модуль. В MiniMarket 0.6.9 уже есть \`OrderLifecycle\`, однако его автоматический перевод в работу по созданию Shipment и запрет отмены оплаченного заказа **противоречат Shop** и должны быть заменены в следующей бизнес-итерации.

## 1. Независимые оси

**Order.status — четыре значения и только они:**
- \`new\` «Новый». Выставляется при создании. Просмотр, платеж, создание/редактирование Shipment, выдача и внешние события не означают неявного принятия.
- \`confirmed\` «В работе». Только явное действие оператора **«Принять в работу»** с \`core.edit.state\`. Действие можно комбинировать в UI «Принять и создать доставку», но в базе сначала фиксируется явное принятие. Не путать с фактом передачи перевозчику.
- \`completed\` «Завершён». Автоматически при \`confirmed\`, **полной** подтверждённой оплате и **полном** подтверждённом вручении первоначального исполнения. Не требовать завершения отдельных замен по последующему Return.
- \`cancelled\` «Отменён». Полная отмена до фактической передачи/вручения; обязательные причина, проверка свежих состояний и атомарное освобождение исходного количества ровно один раз. Оплаченный заказ **разрешено отменить до передачи** с отдельным обязательством RefundTransaction; флаг «Отменён» не является доказательством возврата денег. Терминальный, не удалять.

**Payment — три базовых агрегированных состояния:** \`unpaid\` «Ожидает оплаты», \`processing\` «Оплата обрабатывается», \`paid\` «Оплачен полностью». Рассчитывать из проверенных \`PaymentTransaction\` и текущих \`PaymentAttempt\` относительно суммы заказа. Недоплаченная сумма остаётся видна числом; отдельный основной \`partially_paid\` без нового решения не вводить. Не хранить \`refunded\` в Payment.status как замену состоявшемуся платежу: фактические возвраты и долг по возврату считать **отдельно** из \`RefundTransaction\`.

**Fulfillment / получение — семь состояний:** \`awaiting_assembly\` «Ожидает сборки», \`assembling\` «Собирается», \`ready\` «Готов к передаче / выдаче», \`in_transit\` «В доставке», \`awaiting_pickup\` «Ожидает получения (ПВЗ)», \`delivered\` «Вручён», \`failed\` «Доставка не удалась». Для собственного самовывоза \`ready → delivered\`; собственного курьера \`ready → in_transit → delivered\`; ПВЗ СДЭК \`ready → in_transit → awaiting_pickup → delivered\`. Пропускать неприменимые шаги при реальном подтверждении, но не имитировать даты событий. Отдельные события «не дозвонился», «перенос», «возврат перевозчиком» не создавать как новые основные статусы.

**Return** остаётся отдельной карточкой с независимыми \`RefundTransaction\` и заменами/дополнительными Shipment; исходный Order не переоткрывается. Открытый возврат после получения не должен переписывать уже завершённый Order.

## 2. Карта переходов Order

| Из | В | Инициатор | Условия |
|---|---|---|---|
| создание | new | сайт/сотрудник/API | серверные данные и зафиксированный состав, без двойного Order |
| new | confirmed | оператор | явное «Принять в работу», права, идемпотентность |
| new/confirmed | cancelled | оператор или допустимый таймер неоплаченного самовывоза | до передачи/вручения, причина/основание; платёжная попытка не в неопределённом состоянии; освобождение резерва один раз; если деньги получены — отдельное возвратное обязательство |
| confirmed | completed | система | payment=paid, изначальная поставка/выдача=delivered; подтверждённые операции; атомарно и однократно |
| completed/cancelled | — | — | основные статусы конечные; сервисные финансовые/возвратные события не запрещены |

Ручной общий переключатель статуса заказа предлагается заменить **разрешением исключительного административного override** (права + причина + аудит), не влияющим на обычные операционные действия «Принять», «Отменить», «Записать оплату», «Отметить вручение». Исключение не может самовольно создать банковскую транзакцию, отгрузку либо восстановление товара.

## 3. Два разных срока удержания и резерв после создания

1. **CheckoutHold** (до Order): в Shop уже согласованы исходные 20 мин для online payment и 5 мин для OTP. Никакого Order до окончательного подтверждения успешной online-оплаты по действующему Shop ТЗ. Истечение требует корректной сверки с провайдером; поздний \`payment.succeeded\` создаёт событие для сверки, не вторую продажу.
2. **OrderAllocation / Reserve** (после Order): для самовывоза с постоплатой или ожидающим получением. Занять фактическое количество при создании постоплатного Order **атомарно** по SKU/варианту и готовому комплекту, исключив из продажи для других, не списывать дважды при выдаче. На каждой строке одна запись allocation и журнал её изменений. \`reserved_until\`/ \`pickup_deadline_at\` — даты обязательств, не самостоятельный Order.status. Дни в настройках отдельные для **неоплаченного** и **оплаченного** заказа; значения 3 дня / 7 дней только исходное предложение, не принятые константы.
3. Начало окна получения — **фактическое \`ready_at\`** (после извещения покупателя), чтобы магазин не сокращал срок своим временем сборки. С момента создания до \`ready_at\` наличие занято, но просроченная сборка — сигнал сотруднику, а не причина автоматической отмены неготового заказа.
4. **Неоплаченный самовывоз после дедлайна:** если нет вручения, реальных денег, открытого непрояснённого платежа и иных спорных фактов, после напоминания система может автоматически перевести в \`cancelled\` с причиной \`pickup_unclaimed\` и один раз освободить allocation. Это включаемая политика магазина. Исключение/ручная отсрочка доступна уполномоченному сотруднику, срок и автор записываются. При отсутствии надёжного фонового задания не объявлять автопроверку работающей.
5. **Оплаченный, но не забранный:** не отменять автоматически и не обещать возврат денег. Уведомление + задача проверки в том же заказе, продление хранения или документированное решение оператора, с учётом условий магазина и права покупателя. Занятое количество не освобождать лишь от прошедшей даты.
6. **Курьер / СДЭК:** резерв нужен до отправки, но факт \`in_transit\` не является возвратом в продажу. После передачи нельзя простой отменой освобождать доступные остатки.
7. **Ручной заказ:** один и тот же алгоритм цены/наличия/резерва, другой \`order_source\`. При отсутствии остатка не создавать ложное резервирование; для исключительного backorder нужен отдельный явный режим с правом и отметкой риска, не скрытый обход проверки.

Для MiniMarket текущая \`OrderStorage::create\` явно **не резервирует и не списывает** товары; одно поле даты без allocation и атомарного учёта будет декоративным и недостоверным. Без миграции + доменной операции нельзя считать резерв реализованным.

## 4. Достоверные платежи

- Онлайн ЮKassa: \`PaymentAttempt\` с ID провайдера и идемпотентным ключом; по \`payment.succeeded\` после API-проверки ID, суммы, валюты и принадлежности фиксировать **одну** транзакцию; \`payment.waiting_for_capture\` не считать окончательно полученными деньгами; \`payment.canceled\` — только соответствующая попытка. Повторные webhook не создают второе поступление. \`refund.succeeded\` обновляет только связанную RefundTransaction, не переписывает исходный факт оплаты.
- Наличные / POS при выдаче: \`PaymentTransaction\` с методом, временем, подтверждающим источником (кассовый чек / терминал / банковская транзакция) и сотрудником. Отдельный физический терминал НЕ синхронизируется автоматически лишь потому, что подключена ЮKassa для сайта. Возможно отдельно подключить поддерживаемый API банка/эквайера.
- Денежный поток (в т.ч. постоплата у перевозчика) не равен событию «вручён»; статус оплачено появляется от подтверждения поступления через ответственного оператора, банк либо платёжный адаптер.
- Если подтверждение платежа позднее отмены или истечения резерва, финансовый факт сохраняется и попадает в сверку/урегулирование, а завершённая отмена не снимается скрыто.

## 5. Доставка

- Собственный курьер: оператор фиксирует передачу и вручение с фактическим временем, источником подтверждения и автором; трек необязателен.
- СДЭК через API: одно подключение на способы СДЭК-ПВЗ и СДЭК-курьер. Можно создавать накладную, получать идентификатор/трек, печатать ярлык и принимать статусы API/webhook. Создание накладной не означает фактическую передачу. Если груз оформлен вне магазина, допускается однократное ручное связывание настоящего трека и последующее отслеживание.
- Источник истины для фактического статуса: проверенное событие перевозчика, для собственных способов — уполномоченный сотрудник. Нельзя автоматически проставлять \`delivered\` только от статуса «прибыло в ПВЗ».
- Повторная первоначальная доставка после неудачи не равна второй параллельной обязательной отгрузке. Для завершения исходного Order проверять подтверждённое вручение **всего исходного заказа**, не требовать отдельного вручения Replacement Shipment по Return. Частичную отгрузку не включать без отдельного решения.
- Риск: сейчас MiniMarket 0.6.9 использует 4 статуса Shipment, агрегирует даже replacement и сам переводит Order в работу. При миграции исправить совместимо со старыми кодами и сохранёнными отправками.

## 6. Один реестр заказов: колонки и фильтры

В Shop §6.10 утверждены 14 колонок для финансовой роли: №, создан, покупатель, статус заказа, оплата, получение, товары, историческая себестоимость, разница по товарам, плата за доставку, подтверждённый расход на доставку, разница доставки, итог, предварительный валовой результат. Для оператора — те же операционные сведения, но без экономических закрытых данных; нельзя раскрывать их через SQL/HTML/API/экспорт.

В MiniMarket пользовательский компактный вид по умолчанию предлагается как:
\`[✓] № | Создан | Покупатель | Статус заказа | Оплата | Получение | Резерв до | Итого | Способ получения\`.
По выбору: телефон, способ оплаты, перевозчик, трек, источник, даты оплаты/вручения, финансовые показатели только по ACL. **«Резерв до» показывать лишь при наличии достоверной OrderAllocation, иначе «—», не выводить придуманных дат.**

Фильтры: три независимые оси, способ доставки, номер/покупатель/телефон, период, срок резерва (действует / скоро истекает / просрочен), «требует действия». Один Order = одна строка, без умножения на число Shipment или Payment. Сохранённые персональные представления впоследствии. Статус \`cancelled\` остаётся видимым в основном реестре с фильтром, в корзину физического удаления не попадает сам.

**Уже реализован первый безопасный срез в \`development\` без изменения схемы:** три явные колонки \`status\`/\`payment_status\`/\`fulfillment_status\` и соответствующие фильтры. Это отображение существующих фактов, **не реализация** резерва или новых состояний платежа/отгрузки.

## 7. Предлагаемая схема расширения

- \`#__minimarket_checkout_holds\` (id, checkout_key, sku scope, qty, expires_at, state, release/applied_at; атомарные блокировки).
- \`#__minimarket_order_allocations\` (order_id, order_item_id, stock source ID, qty, state, held_at, released_at/consumed_at, unique action id); \`orders.reserved_until\` либо отдельная политика получения, \`ready_at\`, \`pickup_deadline_at\`, \`cancel_reason\`, \`accepted_at/by\`.
- \`#__minimarket_payment_attempts\`, \`payment_transactions\`, \`refund_transactions\` (provider+external_id unique, amount_cents, currency, verified_at, source, idempotency key, order_id, correction and webhook evidence).
- \`#__minimarket_shipment_events\` (+ carrier ID, tracking, source, occurred_at, received_at, proof); семистадийный нормализатор отдельным сервисом и явная связь \`return_id\` для replacement.
- One lifecycle transaction lock order → item allocation rows → payment/shipment references in a consistent lock order. Фоновые задачи повторяемые, с \`next_check_at\`, retry и monitoring; нельзя объявлять «автоматически» без реального scheduler.
- Миграция существующих 0.6.9 заказов **без выдуманных резервов и платежных доказательств**: пометка legacy-unverified, сохранение снимков, новые операции только после безопасного подтверждения. MySQL 8.4.

## 8. Приёмочные сценарии

1. Самовывоз, постоплата: Order New/unpaid, allocation занято, Ready, TTL, напоминание, после дедлайна и проверки — отмена и release ровно один раз.
2. Самовывоз, постоплата: подтверждённый POS-чек + «Вручён», Order после принятия автоматически Completed; порядок фиксации оплаты/вручения несущественен.
3. Предоплата, не забрал: Order New/Confirmed, payment Paid, fulfillment Ready; истёк срок — предупреждение, не авто-отмена/возврат.
4. ЮKassa: несколько webhook одного payment не удваивают оплату и не создают два Order.
5. Paid/до передачи: ручная полная отмена с причиной допустима; RefundTransaction pending, Payment остаётся доказанной Paid до отдельного факта refund, stock release 1 раз.
6. СДЭК: накладная создана ≠ отправлено; принятие сканом → In transit; ПВЗ → awaiting pickup; вручение только подтверждённым событием; при оплате и принятии Order Completed.
7. Свой курьер: отправлен без оплаты, затем вручён, затем POS/cash подтверждение → Completed, не блокировать доставку отсутствием предоплаты при разрешённом методе.
8. Невручение / повторная доставка / возврат и замена: исходный Order не завершать неверно, исходные позиции не восстановить двойным событием; replacement не требует изменения исходного Completed.
9. Платёж после просроченного/отменённого резерва: сохранить подтверждение и создать исключение сверки, не скрыто оживлять Cancelled.
10. Создание вручную с валидным составом/остатком всегда доступно сотруднику независимо от режима автоматического изменения статуса; оплата/доставка/отмена — отдельные проверяемые действия.

## 9. Разработка в следующем кодовом этапе

1. Сначала миграции + allocation, инварианты остатков и тесты гонок; затем фактические дедлайны и повторяемый cron.
2. Затем API независимых PaymentAttempt/Transaction/Refund и семистадийный Shipment; ручные провайдеры — через тот же контракт.
3. Перевести OrderLifecycle на первичные факты и явное принятие; устранить автоматическое принятие при создании Shipment и запрет платной отмены до передачи.
4. После каждой миграции реальные UI/CLI E2E: не объявлять PASS до проверки версий, сборки ZIP, кумулятивных SQL и браузера Joomla 6 / Atum.
