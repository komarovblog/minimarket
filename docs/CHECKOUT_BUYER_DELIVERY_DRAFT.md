# MiniMarket — проект UX: покупатель и получение (обсуждение)

**Статус:** проект на согласование, НЕ окончательно утверждён и НЕ реализован в 0.5.80.  
**Контекст:** пользователь просил сначала довести сценарии заказа без регистрации/платежных интеграций; затем подключать SMS/ID. Принцип — одна страница checkout, как в DNS по логике, без копирования бренда. См. [CHECKOUT_UX_SPEC.md](CHECKOUT_UX_SPEC.md).

## 1. Сетка экрана и общие правила

- Десктоп: основная колонка «Покупатель / Получение / Оплата» и справа колонка «Ваш заказ» с итогами. На мобильном одна колонка: покупатель → получение → оплата → итог. Не добавлять шаги-страницы или большие раскрывающиеся аккордеоны.
- Блоки видны сразу, **меняется только содержимое выбранного метода получения**, без сдвига остальных секций сильнее необходимого. Все формы по умолчанию компактные.
- На первой итерации оформление создаёт **заказ-заявку** без SMS и регистрации. Нельзя называть телефон подтверждённым; при отсутствии оплаты нельзя писать «Оплачено».
- Все варианты должны быть RU/EN, с доступными подписями, подсказками, клавиатурной навигацией, нативным Bootstrap 5; ни одна кнопка не должна вести к неработающей интеграции.

## 2. Блок «Покупатель» — предлагаемый UX

**Основная строка:** заголовок «1. Покупатель», под ним «Контактные данные для связи по заказу».

| Поле | На текущем этапе | Правило |
|---|---|---|
| Имя | Обязательное | Одно поле; не разделять на имя/фамилию/отчество; 2–120 символов |
| Телефон | Обязательное | Ручной ввод, автозаполнение браузера, доступная проверка формата; подтверждения SMS нет |
| Email | Необязательное | Для будущих уведомлений/чека; не используется для входа |
| Комментарий | Не в блоке контактов | Разместить ближе к итогу заказа, чтобы не загромождать данные покупателя |

- При существующей авторизованной сессии Joomla имя/email подставлять, но оставлять редактируемыми как **контактные данные конкретного заказа**; телефон из профиля — только если есть. Не менять данные Joomla-профиля при редактировании полей заказа.
- Пока регистрация не подключена, **не показывать** «Войти», «Зарегистрироваться», SMS, МТС ID, Сбер ID, Яндекс ID, VK ID как действующие контролы. Контракт будущей авторизации сохранён отдельно.
- Валидация при потере фокуса и при подтверждении; ошибки прямо под соответствующим полем; при ошибках не терять корзину или уже заполненные данные.
- Не создавать отдельную сущность «Покупатель»/таблицу аккаунтов. Хранить снимок введённого контакта внутри заказа. `user_id=0` означает заказ-заявку на текущем этапе без подтверждённой личности.

## 3. Блок «Получение» — предлагаемый UX

**Основная строка:** заголовок «2. Получение». Ниже — небольшие карточки выбора, **только если вариант активен и полностью настроен**.

| Вариант | Что показываем при выборе | Текущая логика |
|---|---|---|
| Самовывоз | Список собственных точек; адрес, часы и комментарий; выбор одной точки | Стоимость 0 или явно настроенная. Срок только если задан администратором, не «рассчитывать» фиктивно |
| Курьер | Населённый пункт, улица, дом, квартира/офис (опционально), подъезд/этаж/домофон (опционально), комментарий курьеру | Только локально настроенные зоны/цены, или честное «Стоимость уточняется» с заказом-заявкой без фиктивной финальной суммы |
| Пункт выдачи | Выбор из заранее внесённых в магазин доступных точек | Без API сторонних ПВЗ не показывать карту чужих пунктов, трек-номер и обещания автоматической доставки |

### Общие условия

- Методы «Самовывоз», «Курьер», «Пункт выдачи» — **предлагаемый набор**, требует утверждения. Если метод отключён, не настроены точки/зоны или в выбранной географии недоступен — его не показывать/явно объяснять недоступность по итогам серверной проверки.
- Если доступен ровно один метод, выбрать его автоматически. Если доступны несколько — предложить один безопасный дефолт (первый по порядку администратора) и дать переключать.
- При переключении метода сохранять введённые данные полей других методов в состоянии формы, но отправлять и сохранять в заказ **только релевантные выбранному методу данные**. Не сохранять одновременно адрес курьера и чужую точку самовывоза как активные.
- Сервер проверяет доступность метода, допустимые точки, адреса и стоимость, не доверяет цене из браузера. Заказ должен сохранять снимок: ID метода, название/тип, точку или адрес, стоимость/признак «будет согласована», обещанный срок лишь если задан.
- Если цена доставки заранее неизвестна, в интерфейсе писать «Стоимость доставки уточняется» и **не показывать ложный окончательный итог**. Сумма товаров показывается отдельно. Окончательный тариф согласуется/фиксируется администратором отдельным действием перед оплатой.
- При наличии товара/SKU/комплекта с ограничениями доставки сервер их проверяет; правила по габаритам и внешним перевозчикам не вводить без явного требования.
- При изменении количества товаров или метода получения пересчитывать сумму на сервере. Если доставка недоступна, не позволять отправить заказ с недействительным выбором.
- Пока нет доставки и оплаты в коде 0.5.80; добавление способов и таблиц — отдельные итерации только после утверждения UX.

## 4. Административные настройки (проект)

- Простое управление доступностью каждого способа, названием, сортировкой, описанием, сроками и стоимостью. Не нужна отдельная «CMS доставки».
- Для самовывоза и собственных ПВЗ — управление точками: название, адрес, режим работы, активность. Для курьера — ограниченные обслуживаемые населённые пункты/зоны и цена (фиксированная/бесплатная от суммы) **только если это потребуется**; не закладывать тяжёлую матрицу заранее.
- В заказе администратор видит выбранный метод, адрес/точку и тариф, может связаться с покупателем и сменить статус исполнения. Исторический снимок не меняется при последующем изменении настроек магазина.

## 5. Границы и вопросы на согласование

1. **Подтвердить состав и обязательность полей покупателя:** имя + телефон, email необязателен, комментарий перенести к итогу.
2. **Подтвердить набор способов получения:** собственный самовывоз, курьер, ПВЗ (ручной выбор точек до внешних интеграций).
3. **Как поступать при неизвестной стоимости курьера:** разрешать заказ-заявку с отдельной пометкой «стоимость уточняется» или требовать заранее настроенный тариф.
4. **Нужны ли несколько собственных точек самовывоза уже сейчас**, или достаточно одной точки и расширения позже.

До согласования не считать эти предложения реализованными или окончательными. После утверждения обновить единый [CHECKOUT_UX_SPEC.md](CHECKOUT_UX_SPEC.md), затем код, миграции, RU/EN, сборку и тесты.
