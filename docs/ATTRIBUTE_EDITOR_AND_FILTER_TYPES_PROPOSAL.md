# MiniMarket — простая матрица характеристик и фильтров

**02.11.2026. Рабочая проектная спецификация на согласование; НЕ реализовано.** Эта редакция **заменяет** предыдущую сложную модель с Radio / Checkboxes / Swatches как отдельными типами характеристик. 0.5.11 остаётся последним кодовым релизом: типы list/text/number/boolean, `is_multiple` только у списка при заполнении товара и неработающий пока `is_filterable`.

## 1. Чётко разделяем четыре независимых параметра

1. **Тип значения** — одни из **семи**: `text`, `number`, `textarea`, `date`, `boolean`, `list`, `url`. Определяет хранение, проверки, формат и дальнейшее использование в поиске.
2. **Заполнение в товаре** — для типа выбирается допустимый способ ввода. Пример: Число → ввод `1500` или выбор `1000, 1500, 2000` из набора допустимых чисел. В БД всегда настоящее число `1500`, не строковый ID и не произвольный текст. Список → выпадающий список/радиокнопки/флажки; при этом значения в БД остаются ID общего справочника.
3. **Фильтр** — если включён `is_filterable`, отдельный тип визуального фильтра, **не зависящий** от способа ввода в товаре. Число может быть диапазоном, ползунком, точными значениями через чекбоксы или выпадающий список.
4. **Множественность фильтра** — разрешено ли одновременно выбрать несколько значений/интервалов. Задаётся только для режимов, которые это поддерживают; не равняется `is_multiple` товара и не равняется `is_variant`.

Отдельно `is_variant` — признак, влияет ли атрибут на будущие реальные комбинации SKU; **не является** типом данных, полем ввода или настройкой публичного фильтра.

## 2. Утверждаемый набор типов и допустимых фильтров

| Тип | Как заполнять в товаре | Допустимые фильтры | Несколько значений в фильтре |
| --- | --- | --- | --- |
| **Текст** | обычное однострочное поле | текстовый поиск или перечень фактически используемых уникальных значений | да, только для перечня |
| **Число** | ручной ввод числа или выбор из заданных **числовых** значений | ввод от/до, двойной ползунок, чекбоксы точных чисел, список чисел, заранее определённые интервалы | да, для чекбоксов/интервалов; не для одного диапазона |
| **Многострочный текст** | textarea | фильтр обычно выключен | нет |
| **Дата** | календарь/ручной ввод даты | диапазон дат, выбор готовых периодов | да, только для периодов |
| **Да / Нет** | три состояния: не заполнено, да, нет | Да/Нет/Любое (или «Только Да») | нет, оба выбора одновременно бессмысленны |
| **Список** | выбор одного или нескольких значений из общей таблицы, UI dropdown/radio/checkboxes | чекбоксы, radio, dropdown, цветные образцы (если у значений есть внешний вид) | да, когда UI поддерживает; radio всегда один |
| **Ссылка** | URL с валидацией | без фильтра | нет |

**Radio, Checkboxes, Dropdown, Colour swatches, Slider не типы хранения.** Видимые в Joomla Custom Fields «Radio» и «Checkboxes» — типы *управляющих элементов формы*, а не повод копировать хранилище. Официальная документация: https://guide.joomla.org/user-guide/fields .

## 3. Пример «Мощность» (всегда Число)

- Тип: Number, единица `Вт`, точность/целое, min/max/step.
- В товаре: **вариант 1** ввести `1500`; **вариант 2** выбрать `1500` из заданных числовых значений `1000,1500,2000`; в обоих случаях сохраняется **число 1500**. Преднастройки значений — опциональны: у разных товаров может быть произвольная числовая мощность.
- В фильтре: **вариант A** ввод «От/До» (или двойной ползунок), **вариант B** список уникальных мощностей с чекбоксами (например 1000 и 1500), **вариант C** выбираемый одиночный список, **вариант D** фиксированные интервалы (1000–1499, 1500–1999). В каждом случае считать товары по числу, а не по строковому лейблу.
- Чекбоксы в публичном фильтре могут допускать несколько точных мощностей (`power=1000 OR power=1500`), хотя в каждом товаре **одно** поле мощности. Это не требует `is_multiple=1` в товаре.
- Фильтр должен учитывать только фактические опубликованные значения товара/варианта текущей категории и её опубликованных дочерних категорий. Нельзя показывать отсутствующие мощности лишь потому, что они перечислены в возможных значениях ввода.

## 4. Минимальная структура формы характеристики

**Основное:** Заголовок, Код, Тип значения (семь типов), Единица для чисел, публикация, порядок, категории.

**Заполнение в товаре:** «Способ ввода» — варианты по выбранному типу. Для Number: `ввод числа / выбор из числового списка`. Для List: `выпадающий список / переключатели / флажки` плюс «одно/несколько» **только там, где выбранный контрол допускает оба** (dropdown); для Radio — одно, для Checkboxes — несколько. Для List — уже согласованный Joomla Subform (+/−/drag) с глобальными значениями и стабильными ID. URL валидируется, textarea и date не требуют вариантов. Для спискового цвета разрешить метаданные HEX/изображение по ID значения как будущую настройку (не новый тип данных).

**Фильтр каталога:** «Использовать в фильтре» Да/Нет. Только при «Да» показывать «Вид фильтра» из допустимых для типа, «Разрешить несколько» только для подходящих способов отображения, «Сортировка значений» (по порядку Joomla, алфавиту, числу товаров). Не показывать бессмысленных пар «длинный текст → диапазон» и «ссылка → чекбоксы». На UI могут быть предпросмотр и названия RU/EN; не копировать все системные Joomla-поля.

**Варианты товара:** «Различает варианты SKU» на отдельной вкладке/в отдельной группе; только для подходящих характеристик; не должен менять «Способ ввода» или «Вид фильтра».

## 5. Поведение фильтров (требования прежних обсуждений)

- В корневой категории фасеты собираются из **фактических товаров** включённых подкатегорий, в дочерней — из актуальной области просмотра, не из всего глобального справочника.
- В исходном состоянии показывать реально используемые свойства/значения, не все созданные в словарях.
- При выборе несовместимые значения и целые группы **disabled, не hidden**; внутренние альтернативы в одном свойстве объединяются по OR, свойства между собой по AND. Для вариантных свойств проверять совпадение условий в **одном** реальном variant_id.
- Диапазон выбирается один раз, но можно менять границы; фильтр по отдельным числовым значениям разрешает multiple OR. Нельзя считать тип UI мультивыбором просто из-за `is_multiple` у товара.
- Динамический отклик: единый серверный endpoint, SQL агрегация, индексы, cache/invalidation; скорость измерять по реальным товарам. Не раздувать форму лишними запросами.
- Публичный фасетный фильтр **не реализован** в 0.5.11. Эта спецификация не делает его работающим.

## 6. Следующий безопасный шаг

После согласования сделать новую миграцию **метаданных вида ввода и вида фильтра**, сохранив существующие `input_type`, `is_multiple`, `is_variant` и ID значений. Для Textarea/Date/URL — новые типизированные валидаторы и поля хранения/чтения. Для числовых предустановок — типизированные числовые варианты без дублирования списка строк. Взаимозависимые поля формы валидировать на сервере. Сначала CI PHP/MySQL/Windows, затем отдельный Joomla smoke с сохранением TEST-001.
