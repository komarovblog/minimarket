# План этапа 7 — реальные варианты и комбинации SKU

**Статус DESIGN ONLY после 0.5.4:** в установленной Joomla этой функциональности пока нет.

1. Один product_id, один URL и canonical для всех реальных комбинаций. UI-переключатель размера/цвета не меняет URL.
2. У каждой комбинации свой variant_id, **уникальный SKU**, цена, остаток, наличие, публикация и порядок. Для простого товара также нужен ровно один основной variant.
3. Значения определяющих свойств выбираются **по ID из общей таблицы значений**; список реальных вариантов создаётся администратором. Никакие несуществующие сочетания автоматически не добавляются.
4. Уникальность комбинации определять по отсортированному набору пар (attribute_id, attribute_value_id). Один продукт не может иметь два варианта с одинаковым набором.
5. Пример: красный S 5 шт, красный M 10, красный L 0; жёлтый S 1, жёлтый M 3; жёлтого L **не существует**. Фильтр «жёлтый + L» должен найти 0, не объединять разные SKU.
6. Фото по значению свойства (цвету) хранить один раз для всех размеров этого цвета; для конкретного SKU можно задать override. Приоритет: SKU → цвет → общая галерея.
7. Существующие SKU/цена/остаток TEST-001 переносить в один default variant **только после проверки миграции**. Не создавать два независимых источника цены и остатка у parent product и variants.
8. Планируемые сущности: product_variants, variant_attribute_values, связи изображений по attribute_value_id/variant_id. FK, ограничения уникальности сочетаний, дефолтный вариант и атомарность сохранения проработать до включения. MySQL DDL автоматически фиксирует транзакции — миграцию схемы и перенос данных проверять отдельно.
9. Фильтры, корзина, заказ, фиды и SEO ProductGroup должны использовать реальные варианты, а не пересечение цветовых и размерных списков от разных SKU.

**Не делать:** множественное поле «Размер» с одним общим остатком товара, отдельные URL для каждой расцветки, повторную загрузку одного и того же файла для каждого размера.
