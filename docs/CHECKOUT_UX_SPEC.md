# MiniMarket — оформление заказа: текущая разработка и будущая регистрация

**Обновлено:** 10.11.2026. **Приоритет:** раздел 0 задаёт действующий этап разработки **без регистрации**. Правила дальнейших разделов описывают целевую систему **после подключения SMS/ID**, не должны сейчас блокировать оформление. Прежние записи о запрете гостевых заказов сохраняются только как финальный бизнес-контракт. Исторические релизы 0.5.78 и 0.5.79 описывают код прежних этапов.

## 0. Порядок разработки — актуальное решение 10.11.2026

**Сначала завершить бизнес-сценарии и UX без интеграций.** В текущей версии 0.5.80 оформление открыто без предварительного входа. Гость заполняет имя/телефон, необязательные email/комментарий и оформляет **заказ-заявку** без SMS и создания Joomla-профиля; `orders.user_id=0`. Уже авторизованному покупателю заказ записывается с существующим `user_id`. Гость видит результат только через исходную сессию, не по публичному параметру ID. Не считать такой номер подтверждённым и не представлять заявку как оплаченную покупку.

**Только потом подключить идентификацию и уведомления:** SMS OTP, МТС ID, Сбер ID, Яндекс ID, VK ID; отдельную регистрацию и вход до покупки; автоматическую регистрацию/авторизацию в процессе checkout. После фактического подключения, тестов и приёмки целевой режим заменяет гостевые заказы заказами с обязательным `user_id`. До этого не показывать неработающие кнопки ID и не блокировать приём заявок.

| Сценарий | Сейчас, проектирование и приёмка | После интеграции |
|---|---|---|
| Покупатель без входа | Форма → заявка, без SMS и аккаунта | Форма → SMS → регистрация/вход → заказ |
| Пользователь Joomla уже вошёл | Данные из Joomla, заказ со своим user_id | То же, без повторного OTP |
| Предварительная регистрация | Не внедряем, не показываем имитацию | Телефон/SMS и четыре подключённых ID |
| Подтверждение заказа | Только в исходной сессии; чужие данные недоступны | Личный кабинет владельца и история |
| Оплата/доставка | Сначала согласуем и реализуем собственные формы, правила, статусы | Подключим провайдеров и внешние сервисы |

**Граница реализации:** к 0.5.80 относится только базовая форма контактов и заказ-заявка. Текущие способы доставки/оплаты ещё не реализованы; описанные ниже элементы относятся к проекту будущего UX. Не встраивать заглушки, которые выглядят как настоящая оплата или проверка телефона.

## 1. Целевые правила после подключения SMS/ID — пока НЕ включать

1. **Гостевых заказов нет.** Неавторизованный посетитель может собирать корзину, но завершить оформление, оставаясь гостем, не может.
2. **Отдельная предварительная регистрация и вход** доступны без покупки: МТС ID, Сбер ID, Яндекс ID, VK ID, а также телефон + одноразовый код SMS (MAX только как дополнительный проверенный транспорт кода, если будет поддерживаться). Те же варианты входа доступны во время оформления.
3. **Оформление в одной странице**, по логике DNS, но без копирования её фирменного интерфейса: покупатель → получение → оплата → итог заказа.
4. **Пользователь с действующей авторизованной сессией Joomla** оформляет заказ без повторного OTP: известные контакты подставляются, недостающие вводятся. Телефон контакта для заказа обязателен, email необязателен.
5. **Посетитель без авторизации**, выбравший оформить заказ по телефону, заполняет данные и нажимает «Подтвердить заказ». До создания заказа сервер отправляет SMS-код; успешная верификация телефона **создаёт Joomla-аккаунт либо авторизует существующий аккаунт по этому ранее подтверждённому номеру**, открывает пользовательскую сессию и только после повторной серверной проверки создаёт заказ, привязанный к `user_id`.
6. **Неуспешное SMS-подтверждение = нет нового заказа, нет новой авторизованной сессии.** Корзина и заполненные данные не теряются; возможна безопасная повторная попытка.
7. **Вход через один из внешних ID до финального подтверждения** переводит покупателя в авторизованный сценарий. Если ID-провайдер успешно аутентифицировал пользователя и сессия Joomla установлена, отдельный SMS-код ради заказа не нужен. Нельзя показывать неподключённые ID как рабочие кнопки.
8. **Email** используется только по желанию покупателя для уведомлений, никогда как публичный логин/метод регистрации/восстановления. Пароль для клиента MiniMarket не запрашивается. Учётные записи/сессии — штатные Joomla Users, без изменения ядра и без второй системы паролей.
9. **Любой заказ имеет владельца — Joomla `user_id`.** Номер и подробности заказа в личном кабинете доступны только владельцу, с проверкой доступа на сервере. Подтверждение номера телефона не даёт доступ к чужому аккаунту только по совпадению *непроверенного* контакта.
10. Все цены, скидки, итог, состав, остатки и доступность способов получения/оплаты вычисляются на сервере. Браузер не задаёт стоимость. Переход к ЮKassa — только после надёжного создания заказа и сохранения суммы.

## 2. Сценарии покупателя

| Сценарий | Вход/регистрация | SMS в checkout | Результат |
|---|---|---|---|
| Покупатель заранее зарегистрировался/вошёл по любому подключённому ID | Внешний ID → Joomla user/session | Нет | Checkout с заполненными данными, заказ у этого `user_id` |
| Покупатель заранее вошёл по телефону | Проверенный SMS-код → Joomla user/session | Нет повторного кода | Checkout, заказ у авторизованного пользователя |
| Посетитель не вошёл и заполняет оформление | Данные → «Подтвердить заказ» → SMS → проверка → создание/вход Joomla user | **Да, обязательно** | Авторизованная сессия + заказ у `user_id` |
| Посетитель нажал «Войти» в checkout и успешно вошёл через ID | Внешний ID → Joomla user/session | Нет | Продолжение той же корзины, заказ у авторизованного пользователя |
| SMS неверен, истёк либо пользователь отменил подтверждение | Не авторизован | Проверка не пройдена | Заказ не создан, корзина сохранена |
| Уже известный **верифицированный** номер подтверждён SMS снова | Вход в связанный Joomla user, а не дублирование аккаунта | Да при неавторизованном checkout | Заказ у существующего владельца |

**Важное различие:** анонимная корзина разрешена; анонимный **заказ** запрещён. Самостоятельная регистрация через внешние ID и автоматическая регистрация в checkout должны создавать один и тот же тип Joomla-профиля.

## 3. UI страницы оформления

На одной странице показывать следующие блоки (детальные визуальные решения/поля доставки и оплаты требуют отдельной приёмки):

1. **Покупатель.** Для авторизованного — имя/телефон из профиля с возможностью заполнить недостающее и ссылка на кабинет. Для неавторизованного — вход/регистрация с реально подключёнными ID или номером; также разрешено продолжить заполнение без предварительного входа, но после кнопки подтверждения обязательно будет SMS-авторизация и регистрация. Поля: имя, телефон; email — необязательное поле для уведомлений. Текст не должен обещать «покупку без регистрации».
2. **Получение.** Самовывоз/курьер/ПВЗ — только доступные и включённые способы. При выборе открывать необходимые поля, адреса, срок и серверную стоимость. Конкретный набор провайдеров/адресных полей ещё согласовать.
3. **Оплата.** Только подключённые способы. Целевой онлайн-провайдер — ЮKassa; ручная оплата при получении остаётся открытым бизнес-решением. Технический статус оплаты отдельно от статуса исполнения заказа.
4. **Ваш заказ.** Позиции, SKU/опции, количества, цена, доставка, итог, согласия и кнопка «Подтвердить заказ»; любое изменение пересчитывать сервером. На ПК итоговый блок можно размещать справа, на мобильном — под формой с доступным итогом.
5. **Подтверждение по SMS.** Для неавторизованного посетителя после нажатия «Подтвердить заказ» — шаг ввода кода, отправленного на указанный телефон. До успешной проверки не создавать заказ. Успех = вход/создание аккаунта + привязанный заказ. Ошибки показывать без потери формы/корзины.
6. **Успешное оформление.** Номер, состав, сумма, состояние оплаты, способ получения, ссылка на «Мои заказы» в кабинете. Повторное открытие не создаёт второй заказ.

На мобильном все действия должны быть доступны без горизонтального скролла. UI независим от используемого шаблона Joomla, RU/EN, адаптивный Bootstrap 5; без копирования чужих брендов и графики.

## 4. Регистрация и личный кабинет

- Самостоятельные страницы/модальные сценарии «Войти» и «Зарегистрироваться» работают **до покупки**. Провайдеры: МТС ID, Сбер ID, Яндекс ID, VK ID; телефон + SMS-код. Для пользователя единый результат — проверенная сессия Joomla.
- Первый успешный вход по внешнему provider+subject создаёт Joomla-профиль, повторный открывает ранее привязанный; вход по подтверждённому телефону аналогичен.
- Связывание внешнего ID с существующим аккаунтом — отдельное действие авторизованного владельца с проверкой полномочий. **Нельзя сливать аккаунты автоматически по совпадению имени, email или необязательно подтверждённого телефона.**
- В профиле: контакты, подтверждённый номер, связанные способы входа, история собственных заказов. Смена подтверждённого телефона требует новой проверки. Нельзя открывать чужой заказ по знанию ID.
- Joomla требует email у пользователя; при регистрации только по телефону возможен внутренний неотправляемый технический адрес. Это технический вопрос прототипа, не обязательное поле покупателя. Ядро Joomla не изменять, настоящие чужие email не подставлять.
- Кнопки ID показываются только после реального подключения провайдера, настройки OAuth/OIDC и тестирования. Не выдавать неподключённую интеграцию за работающую.

## 5. Безопасность и последовательность сервера

1. До отправки SMS проверить CSRF, допустимость корзины, товары, SKU, доступность, итог, контакт и включённые способы доставки/оплаты; выдать одноразовую контекстно связанную попытку checkout.
2. OTP SMS: криптостойкий код, короткий TTL, ограничения повторной отправки/попыток, защита от перебора, не логировать исходный код. При наличии законного и подтверждённого MAX-канала он может дополнять SMS, но **SMS обязателен как предусмотренный канал**.
3. Проверять код и соответствие номеру и текущей попытке *на сервере*. При успехе аутентифицировать по существующей **верифицированной** привязке телефона либо создать Joomla user; не связывать внешний ID автоматически по контактным полям.
4. Ещё раз проверить корзину, остатки и цены перед атомарным созданием заказа/строк и связи с `user_id`. В случае ошибки создания заказа сохранить авторизованную сессию и корзину, предложить повтор с новой проверкой; без фиктивного номера заказа.
5. Предотвращать двойное создание при повторной отправке, обновлении страницы, повторном OTP и сетевых повторах (idempotency key); после успеха очистить корзину, сохранить идентификатор результата для безопасного просмотра.
6. Неавторизованный запрос к данным заказа отклонять. Отдельные ACL администратора и минимизация персональных данных в логах. Никаких платежей/писем/уведомлений до подтверждения соответствующего серверного статуса.

## 6. Разграничение «решено» и «уже работает»

**Подтверждённое продуктовое решение:** без гостевых заказов; предварительный вход/регистрация через четыре ID и телефон; SMS при оформлении неавторизованным; автоматическая регистрация/авторизация в том же процессе; отдельное подтверждение не нужно для уже авторизованного.

**НЕ реализовано/не подтверждено в 0.5.78:** обязательный OTP, автосоздание/автовход Joomla user, вход через ID, форма регистрации до покупки, доставка, ЮKassa, личный кабинет. Текущий 0.5.78 сохраняет заказ-заявку без этих шагов и **пока не соответствует целевому бизнес-контракту**. Нельзя обозначать его как полноценно завершённый checkout.

**Следующая разработка:** прототип user/OTP и работающие сценарии входа → связь заказов с владельцем и запрет неавторизованных заказов → единая страница оформления/приёмка → доставка/оплата и кабинет. Реальную отправку SMS и OAuth запускать только после провайдера, ключей, sandbox и проверок. Перед миграциями — бэкап и MySQL 8.4 тесты; работать только в `development`, не менять Joomla core.
