# MiniMarket 0.5.51 — комплекты товаров и SKU

Дата: 05.11.2026. Ветка: `development`. **Первая реализация комплектов**, без изменения ранее принятой SKU-матрицы, галереи или ядра Joomla.

## Модель и интерфейс

**Комплект — самостоятельный товар** (новое поле `products.product_type=simple|bundle`), у него свои название, URL, базовый артикул, категория, цена, описания, SEO, фотографии, публикация, бренд и коллекции. В карточке товара появилась вкладка **«Состав комплекта»** с нативным Joomla repeatable subform, кнопкой «+» и полями выбора компонента и количества (1–1000).

Компонентом может быть:
- **Обычный товар без собственных вариантов SKU**, со своим остатком `products.stock`;
- **Конкретный SKU** товара с опциями (выбор варианта обязателен), со своим `variants.stock`; при режиме общего остатка `option_stock_mode=0` берётся общий `products.stock`;
- **Другой комплект** с его составом (вложенность до 8 уровней).

Состав — отдельная таблица `#__minimarket_bundle_items`, владелец `bundle_product_id`, выбранный товар `component_product_id`, необязательный точный `component_variant_id`, количество и порядок. Физический SKU комплекту не создаётся; базовый артикул комплекта хранится в стандартном поле `products.sku`. Комплект имеет **свою цену**, независимо от суммы компонентов.

Остаток комплекта **не редактируется вручную**, вычисляется при чтении по минимально доступному числу наборов на основе всех компонентов. Для вложенных комплектов потребности в одинаковых физических товарах и SKU сначала **суммируются**, чтобы не удваивать доступность. Учитывается публикация товаров и всей иерархии категорий, наличие конкретных SKU. Расчёт показывается в админке и публичной карточке. Резервирование, уменьшение остатков при оформлении заказа, автоматическое списание компонентов и возвраты появятся только на этапе корзины и заказов.

## Защита данных

- Миграция `0.5.51.sql` только добавляет поле `product_type` с умолчанием `simple` и таблицу состава. Существующие товары, цены, SKU и галереи не переписываются.
- Пользовательское редактирование сохраняет состав внутри **единой транзакции с товаром**. Валидация идёт на сервере: только существующие товары и их SKU; самоссылки, повторные компоненты, циклы и чрезмерная вложенность запрещены.
- DB FK запрещают удалить товар/конкретный SKU, уже используемый в комплекте; удаление самого комплекта удаляет лишь его строки состава.
- Превращать существующий товар с физическими SKU/локальными вариантами в комплект запрещено без отдельной явной миграции: данные не выбрасываются автоматически.
- Публикация недокомплектованного товара через массовые действия может оставить его с **нулевой** доступностью; показывать такой товар в продаже следует только после заполнения состава.
- Копирование комплектов и комбинации опций комплекта ещё не реализованы; редактирование собственных SKU у комплекта не обрабатывается.

## Демонстрационные данные для текущего MySQL 8.4

Вместе с установочным ZIP `com_minimarket-0.5.51.zip` лежит **отдельный** файл `minimarket_bundles_demo_0_5_51.sql`, пригодный для phpMyAdmin в базе `minimarket` с таблицами `nnop3_`. Это дополнение к предыдущему `minimarket_mysql84_nnop3_full_demo.sql`: полный старый каталог повторно импортировать НЕ НАДО. SQL добавляет 3 набора и 6 строк состава с указанием существующих демо-товаров/SKU:

1. **Подарочный комплект «Медвежата»** (1090): мишка 1002 ×1 и медвежонок 1003 ×2 → исходно доступно **14** комплектов (остатки 14 и 28).
2. **Набор юного инженера** (1091): точный SKU `SKU-1012-SET60-BLUE` ×1 и `SKU-1016-SET32` ×1 → исходно **9** комплектов.
3. **Большой комплект мягких друзей** (1092): вложенный комплект 1090 ×1 плюс медвежонок 1003 ×1 → исходно **9** комплектов. Общая потребность 1003 получается 3 штуки, а не 2. Таким образом, 28 / 3 = 9.

Все наборы имеют собственные карточки, цены, бренд/коллекции и фотографии из уже существующих `images/minimarket/sample-01.png`–`sample-10.png`. SQL повторно исполним с проверками существования; не содержит DROP/DELETE/TRUNCATE и не изменяет чужие товары.

## Приёмка

1. Сделать резервную копию БД в phpMyAdmin.
2. Обновить MiniMarket до **0.5.51** через стандартный установочный ZIP **поверх** 0.5.50. Проверить таблицу `nnop3_minimarket_bundle_items` и новую колонку `product_type`.
3. Выполнить **только** `minimarket_bundles_demo_0_5_51.sql` в базе `minimarket`.
4. Открыть три демо-комплекта, их состав, SKU, количество, цены, изображения и SEO. Сохранить, переоткрыть, проверить, что все компоненты сохранились.
5. В админке проверить 14 / 9 / 9 расчётных единиц. Временно измените остаток медвежонка 1003 — у двух связанных комплектов он должен обновиться автоматически. Возвратите исходный остаток.
6. Проверить, что попытка добавить товар с вариантами **без выбора SKU** не принимается; сама ссылка на товар/SKU не может указывать на комплект, в котором она же содержится.
7. Проверить запрет удаления товара или SKU из состава.
8. Переоткрыть обычный товар: SKU-матрица, галерея, характеристики, бренды/коллекции, связи товаров должны остаться прежними.
9. CI: PHP 8.4/8.5, MySQL 8.0 upgrade, MySQL 8.4 fresh+demo+bundles и Windows ZIP.

Ограничение: публичный вывод и расчёт остатков — предварительная реализация. Завершение списания комплекта, целостности заказов/резерва, продаж и внешнего API только в будущем этапе оформления заказов.
