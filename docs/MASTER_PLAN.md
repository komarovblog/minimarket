# MiniMarket — единая карта архитектуры и последовательности

**Статус:** рабочий план (11.11.2026); очередность фиксируется до новой функциональной разработки. **Исходный код:** `komarovblog/minimarket`, только `development`. **Текущая база:** Joomla 6, PHP 8.5, MySQL 8.4. **Документ для просмотра:** https://docs.google.com/document/d/1gn_9qykQDx3qqUr256UGfavME-GIhXINjURp7pgCj10/edit?usp=drivesdk

## Источник истины

- Этот файл определяет цели, очередь и зависимости; `docs/SETTINGS_REGISTRY.md` — перечень настроек из реальных форм; `docs/ITERATION_RULES.md` — обязательный порядок каждой итерации.
- `AGENTS.md` — входная точка для любого нового чата или агента, не второй источник продуктовых решений. `CURRENT_TASK.md` — только выполняемая задача и доказательства результата, не второй план архитектуры.
- Google Doc — удобная копия для чтения/обсуждения. При расхождении с GitHub актуализировать копию по GitHub, а не незаметно исправлять две независимые версии.
- Старые `docs/RELEASE_*.md`, `docs/ROADMAP.md`, `docs/EXTENSIONS_ARCHITECTURE.md` — история, а не основание переопределять этот план. При необходимости архитектуру меняет явная запись в разделе «Решения» с аргументацией и влиянием.

## Неделимые правила продукта

1. Один самостоятельный `com_minimarket`; товары и категории — его собственные, не Joomla `com_content`. Ядро Joomla, шаблоны сторонних разработчиков, `main`, приватные данные и рабочую БД без согласованной миграции не изменять.
2. Админ-интерфейс строится из настоящих Joomla 6 Atum, Toolbar, SearchTools, PublishedButton, Subform, WebAssetManager и Bootstrap 5; пользовательские цвета/карточки не подменяют нативные элементы.
3. Каждая настройка имеет смысл, хранилище, чтение в рабочем сервисе, наблюдаемый результат, тест, RU/EN и документированное наследование; переключатель без потребителя — **не готов**.
4. Без дублирующих сущностей, сервисов, таблиц, модулей и плагинов. Перед добавлением проверять карту расширений и существующий сервис; расширение создается лишь при доказанной невозможности решить задачу внутри имеющегося компонента.
5. Списки — единые для всех сущностей; карточки — единые нативные вкладки и контролы. Специфичная функциональность только в необходимом месте; светлая/темная темы и RU/EN обязательны.
6. Информационная характеристика имеет одно значение у товара; множественный выбор существует в фильтре. Опции заказа — отдельный механизм и основа SKU-комбинаций; цена товара общая, если нет отдельного принятого решения.
7. Согласованное поведение не менять «попутно». Каждая итерация ведется по `docs/ITERATION_RULES.md`.

## Реестр расширений: сначала используем существующее

| ID | Joomla-расширение | Состояние в src (11.11.2026) | Назначение / решение |
|---|---|---|---|
| EXT-01 | `com_minimarket` | существует | Каталог, админка, торговая логика, витрина, конфигурация, интеграционные сервисы; единственный обязательный компонент |
| EXT-02 | `mod_minimarket_toolbar` | существует, отдельная установка | Кнопка в административной панели Joomla; не включать в ZIP компонента |
| EXT-03 | `mod_minimarket_cart` | не обнаружен в src; резерв | Только если нужна корзина в позиции сайта; подключается к сервисам компонента, собственной корзины/БД нет |
| EXT-04 | `mod_minimarket_products` | не обнаружен в src; резерв | Только если нужны товарные подборки в позициях модулей |
| EXT-05 | `mod_minimarket_filter` | не обнаружен в src; резерв | Только если фильтр необходим вне страниц компонента |
| EXT-06 | `plg_system_minimarket` | не обнаружен в src; НЕ создавать по умолчанию | Только при обязательных Joomla-событиях за пределами компонента; SEO/schema внутри компонента не повод создавать плагин |
| EXT-07 | плагины доставки/оплаты `folder=minimarket` | собственных плагинов в src нет; обнаружение реализовано | Использовать существующий `InstalledMethodPlugins`; один контракт, адаптер под каждого реального поставщика по задаче, без дублирования ядра расчетов |

**Процедура создания расширения:** проверить `src/`, Joomla core API и внутренние сервисы; обосновать необходимый хук/позицию; записать ID, тип, точное имя, владелец кода, настройки, зависимости, упаковка, обновление, тесты; затем создавать. Иначе — внедрять в компонент.

**Особое правило зависимостей:** раздел может пройти локальные тесты, но остаться в статусе «интеграция ожидается», если потребитель находится в следующем этапе. При появлении потребителя обязательно закрывать интеграционный тест. Никогда не выдавать отдельно нарисованный экран за готовый сквозной функционал.

## Что делать с текущими 0.5.90 и накопленным кодом

- Не удалять проект и не переписывать работающие функции без аудита. Исторические версии — снимки, а не эталоны дизайна/архитектуры.
- В этапе 00: установить надежную проверку на PowerShell, PHP 8.4/8.5, JS, MySQL 8.4, ZIP; снять текущие блокировки, проверить инсталляцию/обновление, зафиксировать резервную копию и каноническую схему.
- Ранее реализованные экраны проверять заново на соответствующем этапе, принимая раздел по контракту. Никаких дополнительных функций «заодно».
- Существующие демоданные и рабочая БД не удаляются автоматически; чистая установка и upgrade — два разных сценария.
