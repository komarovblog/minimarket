# MiniMarket 0.5.69 — единый интерфейс редакторов и безопасный учёт остатков

Дата: 07.11.2026. Ветка `development`, Joomla 6.2 / PHP 8.4–8.5 / MySQL 8.0–8.4.

## Изменения по 11 пунктам приёмки

1. У характеристик больше нет выбираемого «Существующий режим (совместимость)»: только «Ручной ввод» / «Выбор из заданных значений». Техническое значение `legacy` **не удаляется из БД**, чтобы сохранить уже внесённые характеристики, числовые значения, словари и привязки. При ручной смене UI обновляется режим ввода.
2. Отдельная вкладка «Фильтр» содержит `is_filterable`, `filter_mode`, `filter_multiple` и пояснение, больше не перегружая «Основное».
3. Отдельная вкладка «Публикация»: категория, товар/комплект, характеристика, опция, значение, связи товаров/комплектов, бренд, коллекция; содержит состояние и порядок. Фиды получили те же поля в отдельной вкладке. Таблица фидов дополнена безопасным полем `sort_order`.
4. В редакторе обычного товара настройка учёта SKU находится над «Остаток». Если режим «каждому SKU», главный остаток становится недоступен для правки, но остаётся в БД. При общем остатке строки SKU видны, их остатки выключены для редактирования, отображается подсказка. При возвращении режима сохранённые значения доступны снова.
5. В настройках MiniMarket новая вкладка «Учёт остатков», включено по умолчанию. OFF замораживает поля количества товара и SKU без удаления. Сервер при сохранении игнорирует изменения неактивных полей; на странице товара отсутствие не зависит от нулевого остатка, и фид YML не помечает позиции unavailable только по сохранённым нулям.
6. Уже существующие общие настройки `category_cards_mobile/tablet/desktop/wide` сделаны доступными независимо от режима список/плитка. Категория по-прежнему может переопределять каждое значение или наследовать.
7. В редакторе связей добавление через «+» больше не теряет результаты поиска: текущие запрос, категория и до 25 найденных товаров хранятся в оперативном UI, уже добавленные строки остаются в списке с выключенной кнопкой.
8. Кнопки добавления над списком; поиск раскрывается непосредственно под ними — в связях, комплектующих, брендах и коллекциях.
9. В таблице форматов примеров импорт/экспорт заголовок `XLSX`, без слова Excel.
10. Фиды: вместо `+ NEW` — `Создать фид` (EN `Create feed`), без сырого ключа Joomla и лишней английской подписи.
11. Обновлены контрактные проверки форм, сборки, MySQL и отдельный системный аудит. Браузерное E2E реальной Joomla в CI не включено и не должно считаться пройденным.

## База и поставка

Выпуск включает аддитивную миграцию `admin/sql/updates/mysql/0.5.69.sql`, добавляющую `sort_order` только к `#__minimarket_feeds`. Новая таблица имеет то же поле в `install.mysql.sql`. Joomla применяет миграцию штатно при установке компонента. **Никаких DROP/TRUNCATE/удалений таблиц, товаров или SKU**.

- `com_minimarket-0.5.69.zip` — устанавливать поверх 0.5.68.
- `mod_minimarket_toolbar-0.5.69.zip` — самостоятельный модуль; повторное обновление необязательно.
- `minimarket_mysql84_nnop3_update_0_5_69.sql` — версионированная копия безопасного накопительного примера каталога; **не импортировать повторно ради этих UI-правок**. Не используйте демо SQL как миграцию живых данных.

На локальном компьютере:
```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\OSPanel\home\minimarket.local\scripts\release-to-desktop.ps1"
```

После установки вручную проверить: старую характеристику «Возраст» (без потери значений); вкладки «Фильтр»/«Публикация»; переключение SKU/общего остатка и глобальное OFF/ON; 4 разрешения карточек категорий; десять подряд нажатий «+» без повторного поиска; вкладку публикации фида и кнопку; шаблоны импорта; сохранение/повторное открытие каждой формы.

## Что ещё стоит проверить/развивать

- Сквозной Playwright E2E на настоящей Joomla 6.2 (клики/сохранение/перезагрузка, responsive, ACL), сейчас **NOT RUN**.
- Публичный динамический каталог фильтров по фактическим товарам и SKU: настройки «Фильтр» пока декларативные; не выдавать их за готовый фасетный движок.
- До удаления технических исторических столбцов/таблиц понадобится отдельная транзакционная миграция с точной проверкой всех зависимостей. Пока безопаснее оставить внутреннее хранилище, которое скрыто от пользователя.
