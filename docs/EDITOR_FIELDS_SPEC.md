# MiniMarket — единая спецификация полей и редакторов (категория / товар / вариант / комплект)

**Версия проекта спецификации:** 1.0 · **Дата:** 01.11.2026 · **Статус:** **проект структуры для согласования перед реализацией**. Никаких новых SQL, форм и пользовательских данных эта спецификация не меняет. **Актуальная очередь работ:** [ROADMAP.md](ROADMAP.md); текущий код MiniMarket 0.4.1 и скриншот пользователя не означают, что поля ниже реализованы.

## 0. Решения, общие для всех сущностей

### 0.1. Одна архитектура вкладок и привычный интерфейс Joomla

- Использовать **штатные Joomla Form XML, Editor (TinyMCE/другой редактор пользователя), Media, Toolbar, ACL, Fields и Options**, без правок ядра и зависимости от Cassiopeia/Helix/SP Page Builder.
- Все текстовые области с визуальным форматированием — **одинаковый Joomla Editor**: **«Краткое описание» и «Полное описание» обе с редактором**. Сейчас в версии 0.4.1 краткое описание — простая textarea, что пользователь справедливо отметил. Исправить перед внедрением финального редактора. Для короткого текста в карточке на витрине генерировать безопасный plain-text excerpt из HTML; не делать автосокращение при сохранении, чтобы не терять контент.
- Вкладки группируют реальные задачи. Базовый набор: **Основное → Описания → Изображения → SEO и соцсети → Отображение/Публикация**, остальные только по типу записи. Не дублировать одно поле на нескольких вкладках.
- Верхняя полоса: **Название**, **Статус** и, для товара/комплекта, явный **тип сущности**; ID и URL — **read-only** после сохранения. Алиас (slug) редактируется отдельно, но ID в URL не меняется. Отдельной вкладки «HTML-разметка» для ручного JSON-LD не будет.
- Обязательность только там, где без поля запись нельзя определить или продать. **SEO title / description / OG / alt override не обязательны**, при отсутствии автоматически берутся из понятных исходников.
- Глобальные значения задаются в **Компоненты → MiniMarket → Options**. Переопределения у категории/товара/комплекта только там, где они действительно полезны. Не создавать настройку на каждый чих.
- Одинаковые числовые значения (цена, наличие, скидка) имеют **один серверный источник истины**; нет скрытой копии цены и остатков у родителя товара после появления variants.
- Предусмотреть **публикацию/снятие с публикации**, ACL, язык (при фактической мультиязычности), создание/изменение, служебные журналы, сохранение без JS, CSRF, безопасную обработку HTML через штатные Joomla фильтры.
- Joomla позволяет вкладки «Публикация/Метаданные/Schema» для статей; для MiniMarket делаем торговую версию этих вкладок, **не регистрируя магазин как com_content**. Метатеги и Schema отдаём через Document API; не выводить дубль от шаблона.

### 0.2. Уровни данных и URL

| Сущность | Самостоятельная публичная страница | Продаваемый SKU/цена/остаток | Принцип |
|---|---|---|---|
| Категория | Да: /category/{alias}-{id} | Нет | Может иметь parent_id; дерево не входит в URL |
| Товар | Да: /product/{alias}-{id} | Через **варианты** | Общий заголовок, бренд, тексты, галерея, характеристики |
| Вариант товара | **Нет отдельного canonical** | **Да: свой SKU, цена, остаток** | Выбор цвета/размера на странице товара; прямой URL предвыбора через параметр |
| Комплект | Да: **предложение** /bundle/{alias}-{id} | Свой SKU и рассчитанный состав/цена | Состоит из конкретных variants; не «с этим покупают» |
| Подборка | Список/модуль, отдельный SEO-лендинг только при явной настройке | Нет | Не продаётся как единая позиция |
| Бренд / коллекция | По необходимости после внедрения справочника | Нет | Название/логотип/описание и SEO при собственной публичной странице |

**Предлагаемый URL комплекта** — /bundle/{alias}-{id}; до реализации роутера подтвердить, что отдельный префикс приемлем, после появления публичных URL не менять без 301. Основной Joomla Shop Itemid остаётся **одним глобальным параметром Options**; обычных menu items может быть сколько угодно, никаких скрытых пунктов меню.

## 0.3. Единая спецификация административных СПИСКОВ (новое требование)

**Списки — не формы редактирования.** В MiniMarket → **Категории** должно отображаться реальное **иерархическое дерево**, а не плоская сортировка по parent_id. Вложенность визуально понятна по отступам, узлам и раскрытию; в каждом уровне своя сортировка. Фильтр/поиск должен сохранять родительский контекст, а не выдавать дочернюю категорию как корневую.

| Список | Миниатюра и существенные колонки | Поведение |
|---|---|---|
| **Категории** | Фото категории; название/уровень дерева; товаров непосредственно/во всей ветке (два отдельно подписанных счётчика); статус; порядок; ID | Раскрыть/свернуть, поиск, фильтр состояния, сортировка среди соседей, защита циклов и «битых» родителей |
| **Товары** | Фото **основного опубликованного варианта → общего товара**; название; SKU простого/default или число вариантов; категория; цена/«от»; наличие; статус; ID | Фильтры по категории/бренду/публикации; сортировки; один родительский товар в одной строке; при вариантах раскрытие SKU по необходимости |
| **Комплекты** | Фото комплекта; название; SKU; число составляющих; итоговая цена; доступность по компонентам; статус; ID | Фильтры и сортировки, не путать с товарными подборками |
| **Варианты внутри товара** | Миниатюра SKU/цвета; значения атрибутов; SKU; цена; остаток; статус; основной вариант | Таблица внутри редактора товара, не отдельное публичное изделие с новым URL |

**Технические условия:** небольшие thumbnails, фиксированные габариты и `object-fit: contain`, не грузить оригиналы размером несколько мегабайт в каждую строку. Для отсутствующего медиа — нейтральный placeholder. Отдельно: штатный Joomla Media, адаптивность и alt. Данные для цены/остатка/фото берутся из одного серверного уровня, счётчики **не должны создавать N+1 SQL** на сотни категорий/товаров. Дерево с тысячами записей — серверная подгрузка дочерних уровней и сохранение выбранного узла при фильтрации. Для дерева сортировку лучше выполнять по родителю + локальному sort_order, а не делать вид, что простой `ORDER BY parent_id` — иерархия.

**Приёмка списков:** трехуровневая вложенность, фото каждого типа, пустые фото, разные статусы предков, много категорий, непредусмотренный/циклический узел, пагинация/поиск; товар и комплект показывают один корректный price/stock и один SKU/ID.

### 1.5. Вкладка «Публикация и служебные данные»

- Статус, даты публикации **при необходимости**, создатель/изменение/ID read-only, ограничение доступа Joomla **если используется на витрине**.

Запрет категории закрывает всю её ветку для экспорта; конкретный фид дополнительно выбирает категории и потомков. Это не кнопка публикации и не средство обхода неопубликованного родителя. Товар с цветом/размером управляет этими полями во вкладке «Варианты». Не держать одновременно независимо редактируемые product.price и variant.price.

### 2.2. Вкладка «Описания»

- **Краткое описание** — Joomla Editor; HTML фильтруется по правам, безопасный excerpt для карточек.
- **Полное описание** — Joomla Editor; общие сведения о модели товара.
- Отдельные содержательные блоки **«Комплектация» / «Особенности» / «Уход»** — не вводить жестко в SQL: при необходимости из структурированных характеристик или контент-модулей.
- FAQ — только реальные видимые вопросы/ответы, не сгенерированные SEO-ключи.

### 2.3. Вкладка «Изображения»

- **Основная обложка**, alt, порядковая галерея (несколько Joomla Media).
- Общие изображения относятся ко всему товару.
- Изображения **по значению атрибута** (например цвет красный) и **по конкретному SKU** настраиваются после появления вариантов.
- Порядок выбора: **конкретный SKU → цвет → общая галерея**. Не загружать одинаковое фото на каждую размерную комбинацию.
- Связь с файлом удаляется отдельно от файла Joomla Media; SEO Open Graph может выбрать свою картинку.

### 2.4. Вкладка «Характеристики»

- Набор характеристик доступен по категории с наследованием и доп. выбором; **текст / число с единицей / да-нет / список**.
- Разделить **общие свойства товара** (например материал корпуса) и **свойства, различающие SKU** (цвет, размер).
- Поля могут быть фильтруемыми и показываемыми на карточке, но не каждое свойство обязательно в фильтре.
- Не связывать характеристики напрямую с текстом Schema.org через ручной JSON: поддерживаемые свойства (цвет/размер/материал) маппятся автоматически.

### 2.5. Вкладка «Варианты» (продаваемые SKU)

Схема полностью описана в **разделе 3**. В редакторе товара — таблица вариантов + добавление/копирование, выбор допустимых комбинаций и автосоставление SKU **только по команде**; нельзя автоматически публиковать несуществующие комбинации.

### 2.6. Вкладка «Связи»

- «С этим покупают», альтернативные, аксессуары, ручные рекомендации/подборки; ссылка на самостоятельный комплект как рекомендация.
- Односторонняя/двусторонняя связь — явное поведение; не смешивать с составом комплектов.
- Показывать только опубликованные, реально существующие связи.

### 2.7. Вкладка «SEO и соцсети»

Общая схема — **раздел 5**. Для товара действует **один canonical**, отличающийся от прямой ссылки на предвыбранный вариант.

### 2.8. Участие в товарных фидах (после появления менеджера фидов)

У товара и SKU — **Наследовать / Разрешить / Запретить экспорт**, плюс исключения в конкретном фиде. При любом сочетании скрытый/неопубликованный товар и вариант **никогда не экспортируются**. В форме показывается объяснение, из-за какого правила запись не проходит выбранный фид. [FEEDS_SPEC.md](FEEDS_SPEC.md).

## 3. ВАРИАНТЫ товара: выбор цвета, размера, цены, остатка и фото

### 3.1. Основной принцип

**Один product_id → один URL → один или несколько variant_id → каждый variant_id со своим уникальным SKU, ценой, остатком.** Если у товара нет выбора цвета/размера, в БД всё равно ровно **один default variant**. Поддерживаем любое разумное число свойств, а не только color/size.

Пример: модель «Футболка», цвета **Красный**, **Синий**, размеры **S, M, L**. В редакторе явно создано **только 5 из 6** допустимых комбинаций — отсутствующая комбинация не является товаром и не должна попадать в фильтр/корзину. Например, Красный/S=5, Красный/M=10, Красный/L=0, Синий/S=8, Синий/M=3; Синий/L не существует.

### 3.2. Таблица и форма одного варианта

| Поле | Поведение |
|---|---|
| variant_id | Генерируется БД, read-only |
| Значения атрибутов | Например color=red, size=M; сочетание уникально в пределах товара |
| SKU | Обязателен, уникален среди продаваемых вариантов и комплектов согласно единому пространству SKU |
| Артикул производителя, GTIN | По необходимости, не заменяют SKU |
| Цена, RUB | На SKU, DECIMAL; текущая цена, опционально зачёркнутая старая (проверить > текущей), скидка — расчёт сервера |
| Остаток | Целое ≥0 по SKU; отсутствие складского учёта не означает бесконечный остаток |
| Доступность | Из остатка и разрешённых режимов «под заказ/предзаказ»; ноль ≠ всегда товар скрыт |
| Статус | Опубликован / снят с публикации; архивный/неактивный не продаётся |
| Основной вариант | Один на товар; fallback для карточки, цен «от» и фото |
| Изображения | Сначала фото SKU, затем атрибут цвета, затем фото товара |
| Порядок, название варианта | Упорядоченный список, пользовательское название генерируется по свойствам, можно переопределить |
| Масса/размер упаковки | При необходимости, если реально различаются между SKU |

**Цена/остаток редактируются у SKU.** На списке товаров цена «от» вычисляется по опубликованным доступным вариантам по согласованному правилу, не хранится второй копией. Если товар без вариантов — простая форма показывает поля единственного SKU внутри родительского редактора.

### 3.3. Поведение на сайте и в поиске

- Переключение цвета/размера **не перезагружает страницу**, сразу показывает верные цену, фото, SKU и статус.
- **Невозможные сочетания** нельзя выбирать; **существующее, но нулевое** сочетание видно как «Нет в наличии»/«Сообщить о поступлении» (если реализовано).
- Канонический URL один: \`/product/{alias}-{id}\`. Прямая ссылка на выбранный SKU допускается: \`/product/{alias}-{id}?variant={variant_id}\`. Сервер должен отдать уже выбранный вариант (цену/фото/наличие) для поискового бота и покупателя; canonical ведёт на URL без query-параметра.
- **Google ProductGroup** с \`hasVariant\`, \`variesBy\`, \`productGroupID\` и отдельными \`Product/Offer\` формируется автоматически, по реальным вариантам. Нельзя написать произвольные SEO title/description для каждого SKU, если отдельных канонических страниц нет; при необходимости — краткое описание/название варианта, видимое пользователю.
- При выборе атрибутов фильтр проверяет **один и тот же variant_id**. Условие «красный + размер L» не выполняется за счёт красного S и синего L.

### 3.4. Миграция старых товаров

Существующие \`#__minimarket_products.sku/price/stock\` переносятся в **один default variant без изменения product_id, alias, URL и фактической цены/остатка**. Не допускать двух авторитетных независимых источников после миграции; делать на копии БД с контрольными суммами, идемпотентностью, backup/restore, включая TEST-001.

## 4. Редактор КОМПЛЕКТА — этап 8

Комплект **продаётся как единая позиция**, в отличие от подборки товаров.

### 4.1. Вкладка «Основное»

- **Название, алиас, ID, SKU комплекта** (уникальный), статус, порядок, основная категория/доп. категории по необходимости, краткое описание в листинге.
- Собственный URL/каноническая страница (предложение \`/bundle/{alias}-{id}\`), обложка/галерея, alt.
- **Тип комплекта: фиксированный состав** для первого выпуска; конфигурируемый состав (покупатель выбирает допустимые SKU компонентов) — отдельное последующее расширение без изменения общего URL.

### 4.2. Вкладка «Состав»

| Поле строки | Правило |
|---|---|
| Товар | Выбор из опубликованного каталога |
| Конкретный вариант | variant_id (если товар имеет выбор SKU) — обязательный для фиксированного комплекта |
| Количество | Целое >0 |
| Порядок отображения | Стабильный |
| Имя/фото компонента | Показывается из связанного товара/variant, без второй независимой копии |

Проверять отсутствие потерянных ссылок, неопубликованных/недоступных элементов и неверных количеств. Накладывание одной и той же SKU в нескольких строках должно учитывать суммарное количество. Вложенные комплекты для первой версии **не включать без отдельного решения**, чтобы избежать циклов и проблем с остатками.

### 4.3. Вкладка «Цена и доступность»

- **Фиксированная цена** комплекта либо **цена по составу** с явно настроенной скидкой (процент/сумма). Один выбранный режим на комплект, строгие правила округления и RUB.
- **Отдельный свободно редактируемый «остаток комплекта» НЕ хранить.** Возможное количество = минимальное доступное целое по составным SKU, с учетом повторов. Резервирование/списание компонентов — атомарно при заказе.
- На момент покупки сохранять снимок состава/цены/суммы/налогов; последующее изменение исходного товара не изменяет старый заказ.
- Комплект как **одна item-позиция в ecommerce**. Стоимости компонентов не прибавлять к его выручке повторно.

### 4.4. Вкладки «Описания», «Изображения», «SEO и соцсети», «Публикация»

**Те же правила, что у товара:** два Joomla Editor, своя обложка и галерея, SEO title/meta description/robots, OG override, canonical auto, серверный \`Product/Offer\` и \`BreadcrumbList\`. Состав комплекта показывается обычным доступным HTML, а не только скрытым JSON-LD.

## 4.5. Фиды для комплектов

При появлении отдельного менеджера фидов у комплекта — «Наследовать / Разрешить / Запретить экспорт»; в настройке фида включение комплектов отдельным флажком, проверка доступности всех вариантов в составе. **Продаваемый комплект** не равен рекомендуемой подборке и имеет один собственный offer ID. [FEEDS_SPEC.md](FEEDS_SPEC.md).

## 5. Единая вкладка «SEO и соцсети» — категории, товары, комплекты

**Эта вкладка должна быть отдельной в редакторах всех трёх сущностей**, а не только в \`Options\`. Часто её не хватает сейчас — по скриншоту админки категории она пока отсутствует.

| Поле | Где редактируем | Автозаполнение и смысл |
|---|---|---|
| **SEO title** (\`<title>\`) | Каждая категория/товар/комплект | **Необязательно**, по умолчанию из названия + шаблона сайта. Не путать с H1 |
| **Meta description** | Каждая | Необязательно: краткое описание без HTML → полное описание → глобальное значение; автогенерацию не сохранять поверх ввода пользователя |
| **Robots** | Каждая | Наследовать / index,follow / noindex,follow / noindex,nofollow; реальное состояние публикации имеет приоритет. sitemap не включает noindex |
| **Canonical** | Read-only, вычисляемый | Показывать текущий canonical; ручное переопределение **только advanced режим** с проверкой домена/путей и отдельным предупреждением |
| **OG title** | Каждая | Необязательно; fallback SEO title → название |
| **OG description** | Каждая | Необязательно; fallback meta description |
| **OG image** | Joomla Media | Необязательно; fallback обложка сущности → категория/товар → обложка магазина. Отдельное социальное превью можно загрузить |
| **OG image alt** | Каждая | Необязательно; fallback alt обложки |
| **Twitter/X card** | Global Options | Обычно \`summary_large_image\` из OG; не плодить по 4 поля на каждую запись без потребности |
| **Schema.org** | Автоматический вывод, read-only preview | Для категории \`BreadcrumbList\`, при необходимости \`CollectionPage/ItemList\`; товар \`Product/Offer\` или \`ProductGroup\`; комплект \`Product/Offer\` |
| **SEO URL / alias** | Основное, не повторять | URL учитывает постоянный ID; отдельные SEO URLs для вариантов **не создавать** |

### Формат Schema.org (не отдельное поле на каждой карточке)

- **Schema.org — общий словарь**; JSON-LD и Microdata — разные форматы записи **одного и того же объекта**, не конкурирующие виды «разметки для Google и Яндекса».
- **Глобальная настройка в MiniMarket → Options:** **JSON-LD (по умолчанию)** / **Microdata (режим совместимости)** / **Не выводить компонентом**, если интеграцию целиком берёт на себя другая система. Выбор действует на все сущности по общему профилю, не плодит новые поля на SKU.
- **JSON-LD**: один серверный генератор сущностей `@id`, Product/Offer, BreadcrumbList, ProductGroup, Organization/Website; единые идентификаторы, цены, stock. **Microdata**: тот же нормализованный объект через серверные HTML `itemscope/itemtype/itemprop` на видимых блоках. Форматы должны проходить проверку на **эквивалентный набор** данных. Не выдавать два независимых Product/Offer одновременно по умолчанию.
- Если нужен одновременный вывод по специфическим требованиям получателя, выполнять только **после доказанного кейса и тестов дедупликации**, а не ставить оба галочками «на всякий случай».
- Google поддерживает JSON-LD, Microdata, RDFa и рекомендует JSON-LD; Яндекс Товары поддерживает JSON-LD и Microdata (проверено по официальным страницам). JSON-LD **не значит «только Google»**.
- Проверка: raw HTML, rich results Google, валидатор Яндекса, `@id` и `url`, отсутствие двойной цены/противоречивого availability, не выдавать Schema как ручной SEO текст. См. [SEO_ANALYTICS_AI.md](SEO_ANALYTICS_AI.md).

**Не добавлять по умолчанию:** meta keywords (для Google бесполезны), ручной Schema JSON в каждой записи, обязательные \`llms.txt\`/«AI-маркеры», выдуманные рейтинги/отзывы, произвольные OG типы на каждый SKU. URL для OG/canonical — абсолютные, без дубликатов от шаблона Joomla. Schema/фиды используют **реальные** цены/остатки, не редактируемые вручную строки.

**Приоритет наследования**: запись (если задана явная override) → настройки категории / бренда **там, где применимо** → MiniMarket Options → Joomla Global Configuration / шаблон → безопасный вычисляемый fallback. Никакого копирования inherited значения в БД записи при сохранении; на экране показывать подсказку «Используется: ...».

**Важно:** отдельная «SEO-описание» — это **plain text meta description, не визуальный редактор**. Краткое описание для людей — **Joomla Editor**. Это два разных поля и разные назначения.

## 6. Схема данных и архитектура форм (до реализации)

| Сущность / таблицы | Ответственность |
|---|---|
| \`#__minimarket_categories\` | parent_id, title/alias/state/order, intro/full, cover/alt, display flags, SEO/OG overrides; дополнительные языки/метаданные после проектирования |
| \`#__minimarket_products\` | product_id, основной category, brand/collection, общие title/alias/описания/медиа/SEO; **не авторитетная цена/склад после variants** |
| \`#__minimarket_variants\` | variant_id, product_id, SKU, price/stock/state/default, optional GTIN, dimensions |
| \`#__minimarket_variant_values\` | Ссылка variant_id → конкретные значения variant-defining атрибутов, unique tuple на товар |
| \`#__minimarket_attributes/attribute_values\` | Общие/вариантные характеристики, списки, типы; исходники этапа 6 сохранены в \`feature/attributes-stage6\`, в \`development\` ещё не реализованы |
| \`#__minimarket_product_attribute_values\` | Общие характеристики товара, typed values |
| \`#__minimarket_media\` / связи | Общие файлы Joomla Media, медиа товара/варианта/цвета/категории/комплекта с порядком и alt; физические файлы не удаляются при отвязке |
| \`#__minimarket_bundles / bundle_items\` | Bundle ID/SKU/состав/цена/статус/SEO, строки конкретного variant_id и quantity |
| Справочники брендов/коллекций | Отдельные таблицы только когда реализуется этап 2.3 |
| Joomla component params / fields | Глобальные defaults/ACL и опциональные редакционные расширения через штатные API |

**Названия новых таблиц — предварительные**, до SQL утвердить ключи, индексы, ограничения и миграцию. Для SEO/OG выбирать нормализованные колонки у сущности или один строго типизированный JSON параметров, но не оба одновременно для одного поля. Категория 0.4.1 уже имеет \`introtext/description/image/image_alt\` — **не создавать их заново под другим названием**.

## 7. Порядок внедрения без серии «поле → ZIP → тест»

**Сначала утверждаем эту спецификацию редакторов**, затем **реализуем связанный блок целиком**, автоматические тесты и **один Joomla smoke**. Промежуточные наработки допустимы в GitHub, но не должны требовать установки после каждой правки.

1. **Релиз A — категории полностью (1.3–1.7 + базовая часть 5):** два editor; основное/изображения/отображение/SEO; дерево; режимы отображения; миграция существующих category полей без потерь. Проверить 0.4.1 существующие поля и реальные данные.
2. **Релиз B — полноценный товар (2 + 3 + базовая часть 5):** редактор, бренд/коллекция, медиа/галерея, характеристики только как подготовленная вкладка без фиктивных полей, SEO, карточка и тесты.
3. **Релиз C — справочники + варианты (6–7):** вернуть сохранённый stage-6 исходник с ревью/аддитивным SQL, затем миграция простого SKU в default variant, editor вариантов/фото SKU и ProductGroup, без изменения URL.
4. **Релиз D — комплекты (8):** отдельная продаваемая сущность с составом и ценой; SEO и OG по той же модели.
5. Затем фильтры/модули (9), корзина/заказы/ecommerce (10), интеграции (11), итоговая приёмка (12). Сквозную проверку SEO вариантов/комплектов повторить после C/D.

**Нет новой установки или миграции только ради этого документа.** Не переделывать установленную Joomla 0.4.1 до подтверждения согласованного контракта полей.

**Фиды**: отдельный пункт MiniMarket → Фиды; список, редактор, дерево выбора категорий, флаги экспорта у категории/товара/SKU/комплекта, видимые причины исключения и тестовый preview; реализуются в 11.6. См. [FEEDS_SPEC.md](FEEDS_SPEC.md).

## 8. Приёмочные критерии будущей реализации

- [ ] У категории/товара/комплекта **две области Joomla Editor**: краткое и полное описание, без потери HTML после Save/Apply.
- [ ] Единые вкладки SEO с meta title/description/robots и OG; наследование видно в интерфейсе, без дублирования meta в HTML.
- [ ] Главная обложка и галерея через штатную Joomla Media, alt и SEO OG fallback без удаления источников.
- [ ] Существующие Category ID, Product ID, alias/URL, SKU, цена/остаток товара TEST-001 не потеряны при upgrade.
- [ ] У простого товара ровно один underlying SKU/variant; у товара с разными цветами/размерами каждый реальный SKU имеет свою цену/остаток/фото.
- [ ] Красный L с 0 остатков можно увидеть как недоступный, отсутствующий Синий L не создаётся; любой известный вариант можно открыть предвыбранным query URL с единым canonical.
- [ ] Комплект — самостоятельная позиция; состав, цена, доступность и резервы вычислены по реальным variant_id.
- [ ] Google \`Product\`/\`ProductGroup\`/\`Offer\`, Open Graph, GA4 и Яндекс Метрика не расходятся с видимой страницей и серверными заказами.
- [ ] Joomla ACL, CSRF, ограничение публикации и переключение языка работают для всех новых форм.
- [ ] CI PHP/Windows ZIP/временная MySQL + **пользовательский Joomla runtime PASS** до завершения соответствующих шагов.
