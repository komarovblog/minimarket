# MiniMarket — правила работы и поставки (обязательно для новых чатов)

**Дата фиксации: 05.11.2026.** Это постоянный рабочий регламент по прямому требованию пользователя. Приоритет над устаревшими замечаниями из предыдущих версий.

## Каждая итерация = готовая поставка

После **каждой** итерации, даже небольшой ошибки UI:
1. Вносить и фиксировать изменения в `development`. `main` и ядро Joomla никогда не править.
2. Обновить версию компонента в `src/com_minimarket/minimarket.xml` (следующая patch/minor версия), код и регрессионные тесты.
3. Выполнить PHP/JavaScript/MySQL-проверки, насколько доступны, и собрать установочный **`com_minimarket-X.Y.Z.zip`**. Проверить ZIP. В GitHub Actions — полный цикл тестов и артефакт версии.
4. **Дать пользователю готовый архив**, пригодный для установки в Joomla поверх текущей версии: предпочтительно прямой файл/ссылка на скачивание; если сборка доступна через GitHub Actions — точная ссылка на артефакт и название установочного ZIP. Не оставлять пользователю только инструкции «сам собери».
5. Зафиксировать изменения и текущую очередь в `CURRENT_TASK.md`, создать краткую заметку о версии и сценарий приёмки. Указывать, что проверено автоматически, а что требует проверки в реальной Joomla.
6. Никаких удаления/сброса реальных данных, не согласованных миграций, незапрошенных изменений рабочих форм, SKU или галереи.

## SQL: только когда добавлены или изменены демонстрационные данные

- **Новые сущности, справочники, зависимости и товарные данные**: кроме установочного ZIP, подготовить **готовый SQL для наполнения демоданных** — например, если введены бренды и коллекции, создать несколько брендов/коллекций и привязать их к уже существующим *демонстрационным* товарам. Пользователь не должен вручную создавать всё для теста. Демо должно выглядеть реалистично и показывать несколько возможных сценариев.
- Данные для загрузки в существующий магазин предоставлять **в отдельном файле**, не внутри Joomla ZIP. По возможности SQL должен быть аддитивным, повторно исполнимым, привязываться к известным демо-артикулам и не менять пользовательские данные. Для любого потенциально разрушающего SQL — отдельное чёткое предупреждение, не запускать автоматически.
- **Только исправление ошибки/доработка интерфейса без изменения данных**: дополнительный SQL создавать НЕ нужно.
- **Структура БД** — отдельно от демоданных: когда нужна новая схема, писать Joomla migration SQL внутри ZIP, которая автоматически и безопасно исполняется при upgrade. Миграции не удаляют старые данные. Демоданные пользователь применяет вручную при желании.
- Для актуального демонстрационного каталога файл `sample-data/minimarket_toys_rich_import.sql` **заменяет MiniMarket-каталог**, поэтому на реальной базе его запускать нельзя. Для брендов/коллекций отдельно существует `sample-data/minimarket_brands_collections_demo.sql`: только INSERT + безопасные назначения для известных демо-товаров `TOY-xxxx`. Эти файлы должны поставляться рядом с ZIP, не в компоненте.

## База и переход с MySQL 8.0 на 8.4

- Joomla 6 рекомендует MySQL 8.4; на OpenServer можно переключиться после резервного копирования и через логический **dump/load** между 8.0 и 8.4. Не переносить сырой data dir разных версий.
- Не путать установочный ZIP компонента, схему, демо-данные и резервную копию действующей Joomla. Установка с нуля + ZIP не восстановит существующие реальные продукты и Joomla-данные.
- Перед сменой сервера, импортом демо/схемы — сохранить полную SQL-копию существующей Joomla БД и `images/` и конфигурацию сайта, проверить откат. Чистую Joomla переустанавливать только если пользователь согласен начать с чистой БД и заново наполнить каталог.

## Зафиксированный план разработки (обновлён пользователем)

1. Бренды и коллекции товаров (0.5.49; 0.5.50 исправляет checkbox).
2. **Комплекты:** товар из других товаров или конкретных SKU, количества, остатки/доступность, цена/SEO, защита от циклов.
3. Полный импорт и экспорт (не упрощённый v1), с вариантами SKU, фото, брендами, коллекциями, комплектами, SEO и связями.
4. Динамические фильтры и SEO-лендинги на комбинации фильтров.
5. Корзина, оформление заказа и личный кабинет.
6. Похожие товары, рекомендации, подборки, дополнительные коммерческие блоки.
7. Финальная комплексная полировка публичной части.

Принятые пользователем элементы интерфейса сохранять без самовольных переделок. Работать пошагово, выпускать ZIP после каждого шага.
