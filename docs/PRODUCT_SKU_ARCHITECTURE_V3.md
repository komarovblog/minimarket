# MiniMarket — архитектура v3: модель и полноценные SKU (03.11.2026)

**РЕШЕНИЕ УТВЕРЖДЕНО.** Заменяет концепцию интерфейса из v2, но сохраняет совместимость данных. Не копировать полный товар для каждого цвета/размера. Полноценный SKU — отдельная *продаваемая запись*, а не отдельная индексируемая SEO-страница.

## Три уровня и их смысл

1. **Товар-модель (Product, products.id):** один основной URL/SEO, категория, наименование, общие описания, характеристики, галерея, видео. Это родительская запись, а не единица заказа/остатка.
2. **SKU-позиция (product_variants.id):** единица заказа, склада, комплекта, импорта и фида со стабильным ID, уникальным SKU, ценой, остатком, статусом. Каждая позиция редактируется **как полноценная карточка**: собственные фото, видео, описания, характеристики при необходимости. Общие поля наследуются, а не копируются.
3. **Параметры исполнения:** «Цвет», «Размер», «Объём» и т. п. со справочными значениями, в одной модели (уже есть variant_dimensions, variant_dimension_values, variant_value_assignments). Комбинации SKU состоят из конкретных ID значений, а не из произвольных строк. Для простого товара допустим один SKU без видимого выбора.

**Пример:** Футболка Classic (одна модель) → CLASSIC-RED-S, CLASSIC-RED-M, CLASSIC-BLUE-M (три SKU/остатка). Один модельный код у всей группы допустим; **одинаковый SKU при разных складских остатках недопустим**. Отдельный продукт со своим SEO/URL создаётся только для самостоятельной модели, а не каждого размера.

## Правила наследования

- Текст, видео и характеристики: явное переопределение SKU → общие данные модели. Для скалярных полей NULL = наследовать; пустая строка = намеренно пусто. Для коллекций медиа/видео нужен явный режим «наследовать / своё / без медиа», чтобы отсутствие строк не приводило к непреднамеренному сбросу.
- Фотографии: фото SKU → фото **значения цвета** → галерея модели. Галерея цвета загружается один раз для S/M/L; при этом каждый SKU может иметь свою галерею. Ниже можно расширять до любого визуального исполнения, не жёстко кодировать английское слово color.
- Цена и остаток всегда свои у SKU; никогда не наследуются от модели после единого SKU-перехода. Исторические products.sku/price/stock пока лишь совместимый переходный источник.

## Интерфейс Joomla (обязательный единый стиль)

- **Основная кнопка «Добавить SKU-позицию»** → редактирование одной полноценной позиции. Выбор Цвет/Размер из списка, «+» для создания значения *внутри товара*, собственные SKU, цена, остаток, фото/видео/описания/характеристики. Никакой обязательной генерации матрицы.
- **«Копировать SKU»** (со сбросом ID и уникальных полей) и дополнительная **«Создать несколько размеров/цветов»**. Комбинации лишь создают те же полноценные SKU-записи.
- Список позиций — штатная таблица Joomla: чекбокс, **публикация слева**, миниатюра, исполнение, SKU, цена, остаток, ID. Открытие строки → отдельная карточка позиции (в виде вложенного редактора или отдельного экранного представления, без другого публичного URL).
- Любое повторяющееся значение/фото/видео — штатный Joomla Subform «+ / удалить / переместить». RU/EN, без нестандартных больших форм и без изменения ядра.

## Торговля, импорт, фиды, фильтры и комплекты

- Заказ/склад/резерв: **variant_id**, а не product_id, плюс снимок цены, SKU и выбранных значений при заказе.
- Импорт: (source_key, external_product_id) → product_id; (source_key, external_sku_id) → variant_id. Эти таблицы уже заведены. Изменение SKU/названия/цвета не меняет внутренние ID; конфликты нельзя решать догадкой. Пакетные UPSERT, dry-run, отчёт.
- Фид: одна строка на SKU, свой offer/item ID, общий group/item_group_id, цена, доступность, фото, ссылка на один URL с предварительным ?variant=<id>; canonical модели не меняется.
- Комплект: фиксированная позиция ссылается на вариант SKU; комплект с выбором — на набор разрешённых SKU. Не списывать одновременно запас комплекта и запас составляющих.
- Фильтры AND должны пересекаться на **одном SKU**, а не на разных вариантах одного товара.
- Обычная характеристика (мощность, материал) не обязана создавать SKU. Модификаторы заказа (гравировка) отдельно от складских SKU.

## Безопасная реализация по стадиям

**Выполнено ранее (0.5.20–0.5.24):** локальные параметры и внешние ID, отдельные SKU/фото, одна SKU-позиция вручную, копирование и bulk price/stock. Браузерная проверка Joomla не подтверждена.

**Следующий шаг B2.2:** добавить к существующему SKU индивидуальные описания, видео и наследование фото (общие/по цвету/свои) без новых копий продуктов. Все SQL-изменения аддитивны, с отдельными тестами upgrade/fresh-install. Сохранение через одну транзакцию.

**B2.3:** удобная полноценная редакторная карточка SKU с выбором значений, общими и индивидуальными медиаполями, компактный нативный список; не путать прогресс SQL-схемы с готовностью UI.

**C:** диагностика legacy-товаров перед переходом на единую SKU-таблицу: каждому простому товару ровно один SKU, но никаких фантомных базовых SKU у моделей с существующими вариантами. Сохранить product_id, variant_id, внешние ключи и URL. Не делать деструктивного backfill без readback.

**D–E:** корзина/заказы/комплекты/склад, импорт/фиды/фильтрация, реальная нагрузочная и Joomla-приёмка.

**Запреты:** не изменять main/ядро Joomla, не создавать тестовые локальные БД, не удалять существующие SKU, не менять артикулы/SEO автоматически, не заявлять незавершённые части готовыми.

Ранние требования, где каждый размер — полная копия products или где для первого SKU обязательно нужно назначить глобальный «Различает варианты товара», **устарели**. Документ v2 остаётся для истории и проверки совместимости.
