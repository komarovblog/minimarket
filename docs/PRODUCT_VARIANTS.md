# MiniMarket — товары и варианты

**Согласовано 01.11.2026. Статус: DESIGN_ONLY, НЕ РЕАЛИЗОВАНО.** Заменяет прежнее правило «каждый цвет или размер — отдельный товар». Это не исторический документ «два варианта Joomla/Articles».

## 1. Один товар — один адрес

- У товара один постоянный product_id, alias, страница и canonical URL. При переключении цвета/размера **URL не меняется**, страница не перезагружается.
- Под основным товаром может быть множество товарных вариантов. Общие: название, описание, категория, бренд, общие характеристики, SEO и общая галерея. У каждого варианта: отдельный variant_id, **уникальный SKU**, значения изменяющихся характеристик (например, цвет/размер), цена (или наследование общей), собственный остаток/доступность, при необходимости фотографии и специфические характеристики. Отсутствующие фото берутся из общей галереи.
- Вариант задаётся **реальной комбинацией** доступных параметров; недопустимые сочетания не создаются и не продаются. В одном товаре нельзя создать два активных варианта с одинаковой комбинацией определяющих свойств. Один основной вариант задаётся явно. Простые товары — товары с **одним вариантом**; переключатель для них не нужен.
- Комплект товаров остаётся **отдельной сущностью** со своим остатком, не вариантом.

## 1a. Фотографии: общие, по значению свойства и по варианту

**Решение по интерфейсу:** не требовать ручную галочку «Менять фото при смене варианта» на каждом SKU. В редакторе товара одна вкладка **«Фотографии»**, где изображения привязываются к области применения. Возможны три понятных сценария — **общие фото**, **фото по цвету (или другому свойству, влияющему на внешний вид)** и **исключение для конкретного варианта**. Это **один механизм связей**, а не три независимые системы хранения и не обязательные глобальные режимы.

- Фотография по умолчанию относится к **товару целиком**. Без дополнительных привязок одинаковая галерея показывается при выборе любого варианта.
- У фотографии можно выбрать **«Применяется к: всем вариантам / цвету: красный / цвету: жёлтый / конкретному варианту (SKU)»**. Для цвета допускается назначать общую **галерею из нескольких фотографий**; фотографии привязываются к стабильному ID значения справочника характеристики, а не к тексту «Красный».
- Если у товара красная футболка S/M/L и жёлтая S/M/L, фотографии красной футболки загружаются **один раз** к значению «Красный», а не копируются в три SKU/размера. При смене S→M одного цвета галерея не меняется; при смене цвета переключается автоматически. У размера тоже может быть своя фото-галерея, если именно размер меняет внешний вид, но при нескольких конкурирующих свойствах лучше явно привязать фото к конкретному сочетанию или SKU.
- В интерфейсе допустим удобный выбор «Тип фотографий: общие / зависят от цвета / индивидуальные по вариантам», но эти переключатели должны только помогать редактировать **связи фото**, а не создавать жёстко разные схемы таблиц. **Отдельная галочка «Менять фото» не требуется**: если для выбранного значения/варианта есть фотографии, смена галереи происходит автоматически.
- **Приоритет:** фото, специально привязанные к выбранному **точному варианту**, → фото, привязанные к выбранному **значению свойства** (по явно заданному администратором визуальному свойству, например цвет), → **общая галерея товара**. Если набор пустой, используется ближайший fallback; отсутствующая картинка не должна ломать страницу. Не подмешивать фотографии чужого цвета в галерею красного товара, если для красного назначен полный собственный набор.
- Для списка товаров и результатов фильтра используется **главная фотография выбранного подходящего варианта**, а не первого случайного. При двух выбранных цветах показывается одна карточка товара с фото детерминированно выбранного подходящего варианта; пользователь может переключить доступные свотчи в карточке.
- Все фотографии — обычные медиа Joomla с повторным использованием файла и отдельными отношениями `product_id`, `attribute_value_id` и/или `variant_id`, порядок, роль (главная/галерея), alt. Не копировать бинарные файлы для каждого SKU, не создавать служебные пункты меню.
- Смена цвета на странице меняет галерею без изменения URL/canonical. Если текущий размер отсутствует для нового цвета, сначала выбрать допустимую комбинацию, затем обновить фото, SKU, цену, остаток и доступность **одного реального варианта**.

**Проверки будущей реализации:** товар с общей галереей; S/M/L красного цвета используют одни фото; жёлтый меняет галерею; вариант с исключительной фотографией имеет приоритет; отсутствие фото конкретного цвета наследует общие; фильтр цвета выбирает правильное основное фото; ссылка и canonical постоянны. **DESIGN_ONLY** — в 0.3.4 загрузки/связи фото вариантов нет.

## 2. Карточка товара и покупка

- По умолчанию показываем основной доступный вариант; если он недоступен, следующий доступный по заданному порядку. Если доступных нет, показываем основной, явно указав отсутствие в наличии.
- Переключение варианта обновляет фото, характеристики, точную цену, SKU, доступный остаток и кнопку покупки **без изменения адреса и canonical**.
- Список товаров показывает одну карточку на один product_id. Если цены вариантов различаются и вариант не выбран, допускается «от минимальной актуальной цены доступного варианта». После выбора показываем **точную цену**.
- В корзине и заказе обязательно сохраняются product_id + variant_id, количество, SKU и снимок существенных характеристик; сервер заново проверяет фактическую цену, наличие и резерв конкретного варианта. Не доверять значениям браузера и не вычитать остаток у абстрактного родительского товара.

## 3. Фильтры и совпадения вариантов

- **Внутри одного свойства — ИЛИ.** Красный + жёлтый означает color=red OR color=yellow.
- **Между разными свойствами — И.** Красный/жёлтый + размер L означает (red OR yellow) AND size=L, причём **ВСЕ условия должны выполняться в одном и том же variant_id**. Красный S + жёлтый L не означает наличие красного L.
- Товар показываем **ровно один раз**, если совпал хотя бы один его реальный опубликованный вариант. Пагинация, число результатов и счётчики фасетов считают **уникальные товары**, не строки таблицы вариантов.
- Карточка должна показывать фото/цену/наличие **варианта, соответствующего фильтрам**, а не случайного цвета. Если совпадений несколько, алгоритм **детерминированный**: сначала варианты в наличии, затем основной вариант (если он совпал), затем сортировка администратора, затем variant_id. Если фильтр «В наличии» включён, отсутствие доступных совпадающих вариантов исключает товар из списка.
- Если выбраны сразу красный и жёлтый, кресло с обоими цветами появляется **одной карточкой**. На ней виден один подходящий вариант и переключатель/свотчи других подходящих цветов. При переключении карточка меняет фотографию и цену. Никаких двух одинаковых карточек.
- При фильтре по цене, цвету и размеру выбранный в карточке вариант должен удовлетворять **всем** условиям. Сортировка по цене считается по совпавшим реальным вариантам, а не по случайной базовой цене.

## 4. URL и SEO: одно каноническое представление

- Целевой URL родительского товара, когда магазин назначен главной: /product/{alias}-{id}; в разделе сайта: /shop/product/{alias}-{id}. Варианты НЕ получают отдельные индексируемые карточки.
- При ручном переключении вариантов pathname и canonical не меняются. В поиске — одна карточка родительского товара; SEO-лендинги фильтров — отдельные сущности, а не варианты.
- **Будущий технический вопрос для SEO:** Google описывает single-page варианты через ProductGroup + Product/Offer, productGroupID, hasVariant и variesBy. Для расширенного распознавания вариантов Google требует возможность открыть предвыбранный вариант по прямому URL, обычно с query-параметром. При этом canonical у группы остаётся общим. Если нужен такой глубокий линк, можно позже обсудить необязательный параметр вида ?variant=ID, не создавая новые индексируемые страницы; переключение цвета *на самой карточке* не должно переписывать URL. **Параметр пока НЕ утверждён**, не добавлять его незаметно и не использовать скрытую сессию как замену ссылки.
- Официальное руководство: https://developers.google.com/search/docs/appearance/structured-data/product-variants . Проверить разметку ProductGroup/hasVariant/Offer и реальные цены/наличие до внедрения.

## 5. Данные и безопасный переход

- Нынешняя таблица #__minimarket_products содержит sku, price и stock непосредственно в родительском товаре — это **историческая MVP-схема 0.3.4**, а не окончательное решение.
- В будущем потребуется собственная таблица #__minimarket_product_variants (product_id, variant_id, SKU, цена, остаток, state, is_default, порядок, опциональные overrides), отношение вариантов к справочнику типизированных характеристик и отдельная связь с изображениями. Схему индексов, уникальности комбинаций и ограничений спроектировать при реализации, **не создавать SQL-миграцию сейчас**.
- Обновление должно автоматически превратить каждый существующий простой товар в **один вариант по умолчанию** с прежними SKU, ценой и остатком, **не изменяя product_id, alias, URL и публикацию**. До проверки миграции старые поля не удалять. Обязательно проверить сохранность тестового TEST-001.
- Цена и остаток продаваемой единицы имеют один авторитетный источник (вариант). Родитель не должен расходиться с выбранным вариантом; совместимость старого интерфейса — через контролируемый переход.

## 6. Контрольные тесты будущего вертикального среза

1. Простой товар и товар с вариантами: редактор товара, изменения SKU/цены/остатка/цвета/изображения и наследование общих значений.
2. Цвет внутри карточки переключается без изменения адреса; недоступные комбинации блокируются, отображаются правильные фото, SKU и цена.
3. Красный, жёлтый, красный+жёлтый — всегда одна карточка родительского товара; проверять красный+размер L на одном реальном варианте, корректные фасетные счётчики и цену.
4. Фильтр «В наличии» и реальные резервы учитываются на уровне варианта; корзина и заказ фиксируют variant_id и серверную цену; конкурентные покупки не создают отрицательных остатков.
5. Существующий TEST-001 сохраняет свой ID и адрес после миграции; новая Joomla SEF схема, canonical, ProductGroup и один публичный product URL проходят отдельную проверку.

**Не реализовано в 0.3.4:** таблица вариантов, редактор вариантов, фильтр характеристик, обновление фото по цвету, Variant ID в корзине, ProductGroup. Весь документ описывает будущую реализацию, не готовый функционал.
