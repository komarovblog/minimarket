# MiniMarket — актуальная архитектура одного Joomla 6 компонента

**Статус:** выбран пользователем 30 октября 2026. Это приоритетный документ; прошлые планы двух вариантов Articles и Catalog в `docs/VARIANTS_PROPOSAL.md` и `docs/EXTENSIONS_ARCHITECTURE.md` — исторические, не реализовывать.

## Цель

Создать **один самостоятельный устанавливаемый Joomla 6 компонент `com_minimarket`**, в котором товары, категории, комплекты, свойства, цены, изображения, остатки, корзина, заказы, SEO и маршруты принадлежат нашему компоненту. **Никаких товаров из Joomla com_content, никаких дополнительных Joomla fields для товаров.** Пользователи/сессии/ACL/медиа и framework — использовать штатные механизмы Joomla, не править ядро.

Локальная Joomla на `http://minimarket.local/` под Open Server служит тестовым стендом, а не исходниками приложения. Исходники `src/com_minimarket` в GitHub `development` → воспроизводимая сборка `dist/com_minimarket.zip` → стандартная установка/обновление через Joomla Extension Installer. Полный сайт Joomla, БД, конфиги, PII и media не коммитить.

## Почему один компонент проще для задачи

Магазин на материалах быстрее, если нужен только список статей и кнопка покупки, но полного решения для комплектов, запасов, фасетных характеристик, SEO-фильтра, заказов и оплаты всё равно нет. При работе через `com_content` пришлось бы совмещать custom fields, контентные события, сторонние template overrides, стандартные URL и собственные таблицы платежей/заказов.

Собственный `com_minimarket` требует больше начальной работы над MVC и БД, но даёт **единый источник данных, собственные представления товара/категории, предсказуемые маршруты и один цикл установки**.

## Состав расширений (минимум)

| Имя | Вид | Для чего | Когда |
|---|---|---|---|
| `com_minimarket` | **Компонент** | Вся торговая система: админка товаров/категорий/комплектов/свойств/цен/остатков; сайт: каталог, товар, фильтр, корзина, checkout, заказы, кабинет, доставка, оплата, SEO/schema/dataLayer | **Обязателен с M0** |
| `mod_minimarket_cart` | **Модуль, необязательный** | Значок/счётчик/мини-корзина в позициях Helix или через модульный блок SP Page Builder | Добавить когда понадобится |
| `mod_minimarket_products` | **Модуль, необязательный** | Подборки товаров/рекомендации на сторонних страницах и лендингах | Добавить при необходимости |
| `plg_system_minimarket` | **Плагин, необязательный** | Только сквозные события/обработчики вне страниц компонента, если невозможно решить обычными сервисами/MVC/views | Не создавать до доказанной необходимости |
| Интеграция SP Page Builder | **Необязательная** | Дополнительные визуальные блоки/аддоны, если штатных Joomla Modules недостаточно | После рабочего магазина |

**Не делать** `plg_content_minimarket_articles`, отдельный `com_minimarket_catalog`, специальные плагины под каждую Joomla-тему и дублирующие сервисы корзины/платежей. Не обязательно собирать пакет из многих расширений: **начать с одного `com_minimarket.zip`**; если позже будет несколько модулей, можно выпускать удобный `pkg_minimarket.zip`.

## Joomla / Helix Ultimate / SP Page Builder

Наш компонент сам владеет `components/com_minimarket/tmpl/product/default.php` (пример) и `tmpl/category/default.php`; именно эти default layouts используются для карточек и категорий без каких-либо переопределений `com_content`.

**Helix Ultimate** и другая тема предоставляют внешнюю оболочку, типографику и CSS. Если пользователь меняет тему, торговая логика и стандартные layouts компонента остаются. CSS-совместимость и визуальные особенности новой темы необходимо протестировать. Администратор Joomla при желании может создать **template override для `com_minimarket` в конкретной теме**, но это настройка внешнего вида, **не обязательная часть установки и не способ реализовать торговлю**.

**SP Page Builder:** для начала интегрировать через Joomla Module addon/позиции модулей и ссылки на view MiniMarket. Если понадобится конструктор карточек/категорий из динамических данных, позже добавить опциональный поддерживаемый SPPB addon; он не должен быть обязательной зависимостью.

Документация Joomla MVC/views/layouts: https://manual.joomla.org/docs/next/building-extensions/components/component-development-tutorial/step01-basic-component/ ; https://manual.joomla.org/docs/next/building-extensions/components/mvc/mvc-overview/ .

## Каталог и БД

**Набор сущностей по требованию:** категории; товары с вариантами внутри одного родительского товара и одной карточки/URL (у варианта свои SKU, остаток, изменяемые характеристики, фото/цена по необходимости); комплекты с собственным остатком; бренды/коллекции; фотографии, характеристики по категории; остатки вручную, резерв настраиваемый; связанные/альтернативные товары, «с этим покупают»; ручные SEO-фильтры и посадочные.

**Уточнение галереи 01.11.2026:** в редакторе товара общие фотографии либо привязка галереи к значению характеристики, влияющей на внешний вид (например, цвету), плюс необязательная точная привязка к SKU-варианту. При выборе цвета фото меняются автоматически без отдельной галочки и смены URL; изменение размера в том же цвете не заставляет загружать дубль фотографий. Приоритет: фото точного варианта → фото цвета/настроенного визуального свойства → общие фото товара. Отдельные связи на существующие Joomla медиа, не дублировать файлы. Полная спецификация и тесты — [PRODUCT_VARIANTS.md](PRODUCT_VARIANTS.md); пока DESIGN_ONLY.

**Новое согласованное правило 01.11.2026:** отменено «каждый цвет/размер — самостоятельный товар». Родительский товар имеет один product_id, alias и canonical URL; внутри у него несколько вариантов со своими SKU/остатком/цветом/размером/опциональными фото и ценой. Ручное переключение не меняет URL. Фильтрация: OR по выбранным значениям одного свойства (красный + жёлтый), AND по разным свойствам **одного variant_id**; даже если совпали два цвета, в выдаче **одна карточка родителя** с фото и ценой реально совпавшего варианта. При нескольких совпадениях — наличие, основной вариант, ручной порядок, id; никаких случайных результатов. Заказ/корзина хранят variant_id и серверно проверенную цену. Простой товар будет одним вариантом по умолчанию, существующий TEST-001 мигрируется без потери ID и URL. Полная спецификация [PRODUCT_VARIANTS.md](PRODUCT_VARIANTS.md). **DESIGN_ONLY / NOT IMPLEMENTED** в текущей 0.3.4.

Начальный M1 разрабатывает только необходимый вертикальный срез `#__minimarket_categories`, `#__minimarket_products`, затем необходимые связи/индексы по фактическим сценариям. **Не создавать десятки таблиц заранее** — каждую миграцию привязывать к функции. Существующие данные и ссылки сохранять при upgrade.

**Заказы:** собственные защищённые таблицы `#__minimarket_orders`, `#__minimarket_order_items` и позднее `#__minimarket_payment_events` вместо Joomla articles категории Orders. Заказ фиксирует серверные цены/состав/контакты/статусы; доступ покупателя только к своим заказам, PII вне публичных выдач; идемпотентные платежи.

## Обычные публичные пункты MiniMarket, основной URL — уточнение 01.11.2026

**Последнее решение по интерфейсу (01.11.2026):** не вводить отдельный глобальный селектор Itemid. Уже существующий видимый флажок `shop_primary_route` остаётся в обычном пункте меню MiniMarket. При **сохранении опубликованного пункта с Да** остальные опубликованные обычные пункты MiniMarket должны автоматически получить **Нет**; сам пункт сохраняет Да. Это **уточнение будущей реализации**, в 0.3.8 сохранение Joomla ещё НЕ синхронизирует флажки между пунктами. При Нет у всех прежний детерминированный fallback (MiniMarket home → lowest ID). Никаких лимитов на количество пунктов или автоматического удаления/выключения меню; не трогать остальные параметры. Пункт `Menu Item Alias` остаётся штатной ссылкой на целевой пункт, а не ещё одной самостоятельной витриной. При `save2copy` / создании неопубликованного пункта не переключать активный основной URL неожиданно.

**Статус 0.3.9:** реализован отдельный маленький Joomla content plugin в составе **одного установочного пакета**, поскольку com_menus сохраняет свои Menu Items самостоятельно. Плагин срабатывает после сохранения опубликованного Shop пункта с Да и очищает `shop_primary_route` только в других MiniMarket Shop пунктах, сохраняя все прочие значения. Это именно выбранный пользователем простой UX; глобального списка нет. Joomla runtime ещё не проверен; стандартный ZIP компонента отдельно плагин не устанавливает. После пакетной установки надо один раз включить плагин. Без глобальных ограничений на количество пунктов. [Тест 0.3.9](M1J_PRIMARY_MENU_SYNC_SMOKE.md).

**Реализационная оговорка:** Joomla 6 сохраняет пункты через `administrator/components/com_menus/src/Model/ItemModel.php` и передаёт стандартный `onContentAfterSave` для `com_menus.item`. Это не происходит автоматически внутри `com_minimarket`; потребуется корректный обработчик Joomla events (скорее всего небольшой собственный плагин) либо иной штатный способ синхронизации, с проверкой cache/ACL/повторного сохранения. Не менять Joomla core и не заявлять работу до реального smoke. Отдельный глобальный список — **отклонён** в пользу простого UX.



**Решение после сравнения со штатными категориями статей Joomla:** сохраняем **необязательный переключатель в параметрах самого обычного пункта MiniMarket**, а не новый глобальный список или механизм выбора по страницам. Видимая подпись: **«Использовать этот пункт для ссылок на товары и категории»**, технический ключ `shop_primary_route`, Да/Нет (Нет по умолчанию). **Да** означает, что все автоматически генерируемые ссылки на продукты/категории и их canonical строятся относительно этого пункта меню — даже когда посетитель пришёл с другой страницы. Другие пункт(ы) магазина остаются доступными и могут показывать свои блоки. **Нет** у всех: MiniMarket на главной → первый по меньшему ID пункт. Для предсказуемости отмечать Да только у одного пункта. В случае нескольких Да текущая реализация не запрещает пункты, а выбирает отмеченный с минимальным ID; это конфликт конфигурации, который лучше не допускать. Это **только выбор предпочтительного URL сущностей, не ограничение публичных пунктов и не копирование товаров**. Историческое предложение о глобальном выпадающем списке **не принимаем** — оно усложнит MVP.


**Дополнение 01.11.2026 — никакого лимита на число пунктов:** 2, 10 или больше **обычных опубликованных пунктов** `MiniMarket — Магазин` допустимы, если это допускают стандартные правила Joomla для меню и alias. Ни компонент, ни его установка/маршрутизатор не должны ограничивать их количество или автоматически выключать пункты из-за совпадающего содержимого. Ответственность за осмысленное создание дубликатов остаётся у администратора сайта. **Различать два случая:**
1. **Самостоятельный пункт меню MiniMarket** (в том числе Joomla «Сохранить как копию»): создаёт отдельный контекст `Itemid`, собственный путь `/catalog`, `/shop`, `/offers` и собственные параметры отображения и назначенные модули; может показывать те же торговые данные, что другой пункт.
2. **Joomla «Системные ссылки → Псевдоним пункта меню» (Menu Item Alias)**: это указатель на существующий пункт меню, **не независимая копия MiniMarket с собственным catalog view и настройками магазина**. В зависимости от опции перенаправления посетитель попадает на целевой пункт / его контекст, а не получает автоматически самостоятельную страницу с новым набором параметров. Стандартные правила Joomla для уникальности menu aliases и одной главной страницы на язык продолжают действовать.

**Основной адрес категорий/товаров — не ограничение количества страниц:** пункт с `shop_primary_route=1` (опционально) используется как предпочтительная база для автоматически генерируемых ссылок и canonical товарных/категорийных страниц. Это не запрещает открывать ту же сущность по альтернативному маршруту от другого обычного пункта. При отсутствии явного выбора остаётся документированный порядок (MiniMarket на главной → обычный пункт с минимальным ID). Не навязывать 301 между разными *самостоятельными* страницами магазина: возможен разный контент, модули и назначение. SEO-дубли — ответственность администратора, при этом компонент должен предоставлять нормальные инструменты canonical и не создавать технических дублей сам. Вопрос ручного выбора canonical самой страницы магазина — отдельная будущая настройка, а не необходимость сейчас.

Официальная справка Joomla: https://guide.joomla.org/help-pages-references/menu-items/system-links/menu-item-alias , https://guide.joomla.org/help-pages-references/menus/menus-new-item . Руководство Google о дубликатах: https://developers.google.com/search/docs/crawling-indexing/canonicalization .

**Последнее уточнение по пользовательскому runtime-тесту 0.3.6:** разрешено **несколько** обычных опубликованных пунктов Joomla типа `MiniMarket — Магазин` одновременно. Например, MiniMarket может быть **главной `/`** и иметь пункт **«Каталог» `/catalog`** с отдельными блоками. Больше нельзя требовать «ровно один пункт» или отключать «Каталог» при назначении магазина главной. **Никаких скрытых, служебных, автоматически созданных Menu Items и правок Joomla core.**

- Каждый обычный пункт MiniMarket открывает **свою страницу магазина** по штатному alias Joomla. Её оформление и переключатель `show_categories` принадлежат конкретному пункту. Для разных страниц `/`, `/catalog`, `/shop` возможны разные наборы модулей и блоков. Canonical страниц **самих пунктов** ведёт на их собственный URL.
- Для **категорий и товаров** необходим **один стабильный основной пункт**: он формирует все ссылки из каталога, модулей и карточек, а также canonical. Менеджер меню теперь показывает параметр `shop_primary_route` («Основной адрес магазина», по умолчанию Нет); по желанию ставить Да у **одного** пункта MiniMarket.
- Правило выбора основного Itemid **явное и детерминированное:** (1) пункт с `shop_primary_route=1`; (2) если таких нет, обычный пункт MiniMarket, назначенный главной Joomla; (3) если и его нет, обычный пункт MiniMarket с **наименьшим числовым ID**. Если Да ошибочно у нескольких, технически берётся наименьший ID среди отмеченных; в настройках нужно оставить ровно один. Владелец может изменить выбор без скрытых fallback-пунктов.
- Относительно основного пункта: `/category/{alias}-{id}`, `/product/{alias}-{id}` когда он главная `/`; `/shop/category/{alias}-{id}`, `/shop/product/{alias}-{id}` когда основной пункт `/shop`; аналогично `/catalog/category/{alias}-{id}` при выборе `/catalog` основным. Родители категорий не попадают в URL, ID и alias остаются стабильны при переключении пунктов.
- Для будущих комплектов `bundle` и ручных SEO-фильтров `filter` применяется та же схема с типовым сегментом, но сущности ещё не реализованы.
- **Legacy и альтернативные адреса** пока могут открываться, но canonical категории/товара указывает на выбранный основной путь. 301 миграции старых ссылок ещё НЕ реализован; требуется отдельный этап до публичного индексируемого релиза. Страницы самого магазина могут существовать параллельно, их назначение/контент должен различаться во избежание SEO-дублирования.
- Если ни одного обычного пункта магазина нет, роутер сообщает об отсутствии настроенного пункта. **Никаких автоматически создаваемых технических пунктов и fallback в чужой компонент.**

**Runtime:** 0.3.4 пользовательский PASS; 0.3.5 FAIL (неправильное поле `published`); 0.3.6 одно меню работает, **два меню FAIL** с `MiniMarket canonical URL is not absolute`; в GitHub 0.3.7 это исправлено в коде, **Joomla 0.3.7 RUNTIME NOT RUN**. Инструкция: [M1G_MULTIPLE_SHOP_MENU_SMOKE.md](M1G_MULTIPLE_SHOP_MENU_SMOKE.md).

### Настройки пункта меню «MiniMarket — Магазин»: реализовывать постепенно

**Не создавать полную форму настроек до появления реальных функций.** Пошаговое ТЗ и критерии проверок — [MENU_MVP_PLAN.md](MENU_MVP_PLAN.md). Приоритет первой реализации:

1. **Обычный штатный пункт меню «Магазин»** (внутренний site view `catalog` пока можно сохранить): место `/` или `/shop`, обычные поля Joomla для названия/alias/публикации/главной/прав/языка. Никаких дублирующих опций компонента и скрытых Itemid.
2. **Первый функциональный переключатель** `show_categories` («Показывать категории», по умолчанию Да), потому что список категорий **уже реализован**. При Нет — вывод страницы магазина может состоять из обычных Joomla Modules. Не показывать настройку «Показывать товары», пока ещё нет общего списка.
3. **Штатный Joomla Router**: обычные опубликованные пункты магазина, целевые `category/product` под ним, единые URL из страниц/модулей, корректные canonical и 404. Роутер важнее дополнительных UI-полей.
4. **Позднее, вместе с общей выдачей товаров:** `show_products` (Да/Нет), количество, сортировка, серверная пагинация.
5. **Ещё позднее:** режимы плиток/дерева категорий, новинки, популярность, выбор вручную, контекстная фильтрация, SEO-лендинги и комплекты — только с реализацией данных и выборок.

С версии исходников 0.3.7 добавлена вторая служебно-понятная настройка **«Основной адрес магазина»**; она выбирает canonical категорий/товаров при нескольких пунктах. По умолчанию Нет, поэтому при MiniMarket на главной приоритет у главной. **Joomla runtime пока не проверен.**

Стандартное хранилище параметров пункта Joomla (`params`) вместо новых таблиц конфигурации. Параметры отдельного модуля относятся к модулю, параметры страницы к пункту меню, торговая логика и защита цены к компоненту. Значения по умолчанию должны сохранять текущую работающую витрину, а добавление новых опций не ломать существующие пункты меню.

### Общая выдача товаров в пункте магазина — реализация исходников 0.3.8

На каждом обычном опубликованном пункте MiniMarket можно **независимо от других пунктов** управлять двумя стандартными блоками компонента: `show_categories` (имеющийся список категорий) и `show_products` (новый список всех опубликованных товаров из всех опубликованных категорий). `show_products` по умолчанию выключен для обратной совместимости. При включении появляются параметры `products_per_page` (12, 24, 48) и `products_order` (последние добавленные **по ID**, название, цена ASC/DESC), серверная пагинация `?mm_page=N` и независимый canonical такой страницы с её собственным Itemid. Все товары берутся SQL-запросом с LIMIT/OFFSET и условиями `product.state=1` и `category.state=1`, не целиком в PHP. Никаких SQL миграций и новых таблиц. Данный блок — **обычный общий каталог**, не полноценный фильтр и не модуль популярных/новинок/подборок. Эти модули остаются отдельными будущими Joomla расширениями. **Joomla runtime 0.3.8 пока НЕ ПРОВЕРЕН**: [M1I_CATALOG_ASSORTMENT_SMOKE.md](M1I_CATALOG_ASSORTMENT_SMOKE.md).

### Модули на любых страницах Joomla
- `mod_minimarket_categories`: дерево/плитки/сквозное раскрывающееся меню категорий; настраиваемые корни/поддерево/количество, ссылки в один выбранный пункт магазина.
- `mod_minimarket_products`: базовый модуль списка всех товаров или товаров категории с потомками, сортировка, лимиты, пагинация.
- `mod_minimarket_popular`: **самостоятельный модуль** популярных товаров, после определения источника измерения популярности.
- `mod_minimarket_new`: **самостоятельный модуль** новинок, после появления устойчивой даты публикации/создания.
- `mod_minimarket_selection`: **самостоятельный модуль** вручную составленной подборки с выбором ID и порядком.
- `mod_minimarket_filters`: **самостоятельный модуль** фильтров по характеристикам с контекстом категории; появится вместе с фасетной моделью.
- **Эти блоки не являются опциями пункта меню «Магазин».** Их можно назначать на разные страницы и позиции стандартным менеджером модулей Joomla. Сервис выборок/цен/ссылок общий с компонентом; каждый модуль отдельный, но не отдельная торговая система.
- Баннеры, редакционный текст и другие блоки остаются обычными модулями Joomla; например, главная сайта с баннером, категориями и популярными товарами может сосуществовать с отдельной страницей магазина `/shop`.
- **Пока модули ещё не реализованы**, не выдавать схему за проверенную систему. Никаких самостоятельных копий таблиц товаров и отдельного компонента для каждого блока.

### Joomla Router, миграция и SEO
- Реализовать в `preprocess/build/parse` один предсказуемый путь: выбранный стандартный пункт магазина задаёт базу `/` или `/shop`, а компонент добавляет `category/alias-id`, `product/alias-id` и будущие `bundle/filter`. Не трогать Joomla core/SEF/.htaccess ради обхода штатной маршрутизации.
- **Уже подтверждённые старые адреса** `/catalog/testovaa-kategoria-1` и `/catalog/testovyj-tovar-1` относятся к реализации 0.3.2. Новая схема — **DESIGN_ONLY**, маршрутизатор под неё не написан.
- Когда администратор переносит магазин с главной `/` на `/shop`, это **изменяет адреса**. Перед таким изменением нужны проверяемые 301 со старых URL, обновлённые canonical/sitemap и отсутствие циклов. Нельзя обещать неизменность URI при изменении его базы.
- Проверить 404 для снятых с публикации категорий/товаров, canonical только для одного пути, отсутствие дублей при нескольких пунктах меню; никаких автоматических редиректов без тестов.
- Хлебные крошки строятся из торговой иерархии, **не из URL**: `Главная → Категория → Подкатегория → Товар` либо `Главная → Магазин → Категория → Подкатегория → Товар`, если магазин отдельный раздел. Для товара в нескольких категориях выбирается основная категория.

### Фильтры, разметка и аналитика
- Ручные SEO-лендинги `filter` имеют title/description/H1/текст/модули, отключённые лендинги получают осознанное правило 301 на категорию; обычные сочетания параметров не становятся автоматически индексируемыми страницами.
- Schema.org `Product`/`Offer`, `CollectionPage`/`ItemList`, `BreadcrumbList`; никаких `Article` для товаров.
- GA4 `dataLayer`: `view_item_list`, `select_item`, `view_item`, `add_to_cart`, `remove_from_cart`, `view_cart`, `begin_checkout`, `add_shipping_info`, `add_payment_info`, `purchase`, `refund`, без PII и с согласием. Это будущие этапы, **не реализовано**.

Официальная основа: https://manual.joomla.org/docs/next/general-concepts/routing/build/ .

## Checkout, аккаунты, платежи

Остаются прежние бизнес-правила: Joomla Users, вход **только** по телефону с SMS/MAX кодом или МТС ID / Сбер ID / Яндекс ID / VK ID; email — только канал уведомлений, никогда не вход. Авторизованным checkout без повторного ввода; гостю телефон с подтверждением кода после заполнения заказа, без автоматического создания профиля. Доставка/оплата, YooKassa, Email/Telegram/MAX-уведомления, ручные статусы, возвраты и защита заказа от подмены цен. Эти функции идут после рабочего каталога, в основном компоненте, а не в двух независимых системах.
