# MiniMarket — актуальная архитектура одного Joomla 6 компонента

**Статус:** выбран пользователем 30 октября 2026. Это приоритетный документ; прошлые планы двух вариантов Articles и Catalog в `docs/VARIANTS_PROPOSAL.md` и `docs/EXTENSIONS_ARCHITECTURE.md` — исторические, не реализовывать.

## Цель

Создать **один самостоятельный устанавливаемый Joomla 6 компонент `com_minimarket`**, в котором товары, категории, комплекты, свойства, цены, изображения, остатки, корзина, заказы, SEO и маршруты принадлежат нашему компоненту. **Никаких товаров из Joomla com_content, никаких дополнительных Joomla fields для товаров.** Пользователи/сессии/ACL/медиа и framework — использовать штатные механизмы Joomla, не править ядро.

Локальная Joomla на `http://minimarket.local/` под Open Server служит тестовым стендом, а не исходниками приложения. Исходники `src/com_minimarket` в GitHub `development` → воспроизводимая сборка `dist/com_minimarket.zip` → стандартная установка/обновление через Joomla Extension Installer. Полный сайт Joomla, БД, конфиги, PII и media не коммитить.

## Почему один компонент проще для задачи

Магазин на материалах быстрее, если нужен только список статей и кнопка покупки, но полного решения для комплектов, запасов, фасетных характеристик, SEO-фильтра, заказов и оплаты всё равно нет. При работе через `com_content` пришлось бы совмещать custom fields, контентные события, сторонние template overrides, стандартные URL и собственные таблицы платежей/заказов.

Собственный `com_minimarket` требует больше начальной работы над MVC и БД, но даёт **единый источник данных, собственные представления товара/категории, предсказуемые маршруты и один цикл установки**.

## Состав расширений (минимум)

| Имя | Вид | Для чего | Когда |
|---|---|---|---|
| `com_minimarket` | **Компонент** | Вся торговая система: админка товаров/категорий/комплектов/свойств/цен/остатков; сайт: каталог, товар, фильтр, корзина, checkout, заказы, кабинет, доставка, оплата, SEO/schema/dataLayer | **Обязателен с M0** |
| `mod_minimarket_cart` | **Модуль, необязательный** | Значок/счётчик/мини-корзина в позициях Helix или через модульный блок SP Page Builder | Добавить когда понадобится |
| `mod_minimarket_products` | **Модуль, необязательный** | Подборки товаров/рекомендации на сторонних страницах и лендингах | Добавить при необходимости |
| `plg_system_minimarket` | **Плагин, необязательный** | Только сквозные события/обработчики вне страниц компонента, если невозможно решить обычными сервисами/MVC/views | Не создавать до доказанной необходимости |
| Интеграция SP Page Builder | **Необязательная** | Дополнительные визуальные блоки/аддоны, если штатных Joomla Modules недостаточно | После рабочего магазина |

**Не делать** `plg_content_minimarket_articles`, отдельный `com_minimarket_catalog`, специальные плагины под каждую Joomla-тему и дублирующие сервисы корзины/платежей. Не обязательно собирать пакет из многих расширений: **начать с одного `com_minimarket.zip`**; если позже будет несколько модулей, можно выпускать удобный `pkg_minimarket.zip`.

## Joomla / Helix Ultimate / SP Page Builder

Наш компонент сам владеет `components/com_minimarket/tmpl/product/default.php` (пример) и `tmpl/category/default.php`; именно эти default layouts используются для карточек и категорий без каких-либо переопределений `com_content`.

**Helix Ultimate** и другая тема предоставляют внешнюю оболочку, типографику и CSS. Если пользователь меняет тему, торговая логика и стандартные layouts компонента остаются. CSS-совместимость и визуальные особенности новой темы необходимо протестировать. Администратор Joomla при желании может создать **template override для `com_minimarket` в конкретной теме**, но это настройка внешнего вида, **не обязательная часть установки и не способ реализовать торговлю**.

**SP Page Builder:** для начала интегрировать через Joomla Module addon/позиции модулей и ссылки на view MiniMarket. Если понадобится конструктор карточек/категорий из динамических данных, позже добавить опциональный поддерживаемый SPPB addon; он не должен быть обязательной зависимостью.

Документация Joomla MVC/views/layouts: https://manual.joomla.org/docs/next/building-extensions/components/component-development-tutorial/step01-basic-component/ ; https://manual.joomla.org/docs/next/building-extensions/components/mvc/mvc-overview/ .

## Каталог и БД

**Набор сущностей по требованию:** категории; товары (каждый цвет/размер как отдельный товар, без вариантов, если это прежнее согласованное требование); комплекты с собственным остатком; бренды/коллекции; фотографии, характеристики по категории; остатки вручную, резерв настраиваемый; связанные/альтернативные товары, «с этим покупают»; ручные SEO-фильтры и посадочные.

Начальный M1 разрабатывает только необходимый вертикальный срез `#__minimarket_categories`, `#__minimarket_products`, затем необходимые связи/индексы по фактическим сценариям. **Не создавать десятки таблиц заранее** — каждую миграцию привязывать к функции. Существующие данные и ссылки сохранять при upgrade.

**Заказы:** собственные защищённые таблицы `#__minimarket_orders`, `#__minimarket_order_items` и позднее `#__minimarket_payment_events` вместо Joomla articles категории Orders. Заказ фиксирует серверные цены/состав/контакты/статусы; доступ покупателя только к своим заказам, PII вне публичных выдач; идемпотентные платежи.

## Модульная витрина и независимые URL — уточнение 01.11.2026

**Приоритетное решение пользователя:** в MiniMarket нет обязательной «главной-каталога», обязательной страницы `/catalog` и корневой категории «Каталог». Каталог как торговые данные существует **самостоятельно** от Joomla страниц, меню и модулей. Главной Joomla может быть любая страница (статья, собственный макет, сборка Joomla Modules); её назначение не должно менять URL товаров и категорий. Предыдущие формулировки «главная / сама является каталогом» ниже и в исторических документах **заменены этим решением**.

### Неизменные публичные маршруты сущностей
- `/category/{alias}-{id}` — категории, даже если в БД иерархия;
- `/product/{alias}-{id}` — товары (независимо от категории/точки перехода);
- `/bundle/{alias}-{id}` — комплекты, когда сущность появится;
- `/filter/{alias}-{id}` — только *вручную* созданные SEO-лендинги фильтров.
- `/catalog` — **необязательный** маршрут представления всего ассортимента, создаваемый владельцем как обычный публичный пункт меню Joomla. Отсутствие этой страницы не мешает работе карточек, категорий или модулей MiniMarket. На тестовой Joomla существующий `/catalog` пока не удалять.

**Предлагаемое поведение необязательного `/catalog`:** сверху дерево **всех** опубликованных категорий (включая уровни вложенности), ниже — пагинированная выборка всех опубликованных товаров магазина из всех опубликованных категорий и их потомков, сортировка и применимые общекаталоговые фильтры. Не выгружать весь ассортимент в память/HTML; на уровне категории показывать товары этой категории **и вложенных категорий** (если владелец не выбрал другой режим). Чётко различать *каталог со всем ассортиментом* и *страницу отдельной категории*. SEO-фильтры формируются вручную и не зависят от существования `/catalog`.

### Вывод на любых страницах через модули Joomla
- `mod_minimarket_categories`: блок/дерево опубликованных категорий, режим корневые/поддерево/все, лимит, отображение, ссылки на неизменные `/category/...`. Может быть плиткой на главной или раскрывающимся навигатором в шапке на всех страницах.
- `mod_minimarket_products`: **один** модуль списка товаров с настройками: все (пагинация), из категории (при необходимости со всеми потомками), последние/новинки, популярные, выбранные вручную. Лимит, сортировка, шаблон вывода; цена/остаток читаются сервером из MiniMarket. Режим «популярные» потребует явно определённого источника статистики (продажи, просмотры или ручной рейтинг); **до этого нельзя выдавать случайный порядок за популярность**.
- Фильтры по атрибутам и цене — часть собственного каталога/категорий и, при необходимости, специальный модуль. Фильтры должны учитывать текущий контекст и не превращать автоматически любое сочетание параметров в индексируемый SEO-лендинг.
- Баннеры, тексты, прочие блоки могут быть **обычными Joomla Modules**. Размещение регулируется позициями шаблона/назначением на пункты меню. На одной главной возможна композиция «баннер → модуль категорий → популярные → все товары» вообще без публичной страницы `/catalog`. Joomla-шаблоны и модули — механизм композиции, не источник торговых данных.
- Модули используют общие read-only сервисы/репозитории MiniMarket и `RouteHelper`; **не дублируют** товарные таблицы, маршрутизацию, бизнес-валидацию, цены или остатки. Не добавлять отдельный компонент/движок на каждый блок.
- **Стадия:** пока эти модули и динамическая пагинация не реализованы; в 0.3.3 есть один `com_minimarket` с тестовым каталоговым view. Писать готовность только после установки и smoke-тестов модулей.

### Joomla routing и реальные ограничения
Joomla связывает SEF маршруты с `Itemid` и menu aliases. Поэтому **независимость торговых URL от наличия *публичной* страницы каталога — требование**, но технически могут понадобиться невидимые route anchors/служебные пункты меню или совместимый системный механизм. Это нужно спроектировать и проверить на Joomla 6.2.0, не редактируя Joomla core и не создавая публичную ссылку `/catalog` автоматически. Важные тесты: главная сайта — обычная статья/сборка модулей, публичного меню «Каталог» нет, при этом `/category/...` и `/product/...` работают прямо, а ссылки из модулей и canonical постоянны. Публичные `/catalog` при желании пользователя не должны менять canonical товаров или ломать URL. Для уже существующих `/catalog/{alias}-{id}` отдельно решить 301 и 404, не допускать SEO-дублей.

### Навигация и хлебные крошки
Хлебные крошки отражают **торговую иерархию**, а не расположение пунктов меню: `Главная → Категория → [Подкатегория] → Товар`. «Каталог» в крошках **не обязателен**, даже если отдельная страница существует; его включение допустимо только осознанным UX-решением, не привязывающим карточки к URL каталога. Для товара с несколькими категориями определить основную для стабильного пути. Сквозное раскрывающееся меню категорий и модули товаров независимы от этого выбора.

**Официальная документация Joomla:** https://manual.joomla.org/docs/next/general-concepts/routing/build/ ; https://manual.joomla.org/docs/next/building-extensions/ ; https://manual.joomla.org/docs/next/building-extensions/modules/module-development-tutorial/step1-basic-module/ .


## URL/SEO

- **Целевая модель витрины, уточнение 01.11.2026:** **главная страница `/` сама является каталогом**, а не отдельной маркетинговой страницей с обязательным переходом в `/catalog`. **Корневой категории «Каталог» в БД не существует**. В стандартной конфигурации отдельный публичный пункт меню/URL `/catalog` **не создаётся**. В Joomla остаётся обязательный *технический default/home menu item* типа MiniMarket catalog; его заголовок «Главная», не «Каталог», и он ведёт на `/`. Если администратор позже сознательно создаёт отдельную страницу «Каталог», она должна давать отличное назначение (например, полный список всех товаров с фильтрами, если главная становится подборками); нельзя автоматически делать два одинаковых индексируемых адреса `/` и `/catalog`.
- **Целевые адреса, без иерархии категорий в пути:**
  - главная / каталог: `/`;
  - категория: `/category/{alias}-{id}`;
  - товар: `/product/{alias}-{id}`;
  - комплект: `/bundle/{alias}-{id}`;
  - вручную опубликованный SEO-фильтр: `/filter/{alias}-{id}`.
  Префиксы `category/product/bundle/filter` различают типы, идентификаторы стабильны внутри типа, совпадающие числовые ID допустимы для разных сущностей. Перенос товара между категориями не меняет URL; смена alias требует отдельной политики редиректов.
- **Навигация и содержимое главной:** шапка со сквозной раскрывающейся кнопкой «Категории» на всех страницах; левый столбец категорий/фильтров в каталоговых списках (адаптивный drawer на мобильных); на `/` одновременно блоки/модули категорий, подборки (опционально) и **пагинированный** список товаров разных категорий с сортировкой. Не выгружать сразу все товары одним ответом и не показывать узкокатегорийные фильтры до выбора контекста. Joomla Modules допустимы как подключаемые блоки, не как альтернативные таблицы каталога.
- **Хлебные крошки:** навигационная иерархия не обязана совпадать с URL. Например, `Главная → Инструменты → Дрели → Дрель Bosch`, хотя URL товара `/product/drel-bosch-2001`. Для нескольких категорий у товара нужна одна стабильная основная категория/ветка для BreadcrumbList (а не зависимость от страницы перехода). Для SEO-фильтра — `Главная → Категория → Подборка`, если она связана с категорией. Для простого товара без категории (если вообще разрешён) — `Главная → Товар`; ссылки крошек должны вести на реально опубликованные страницы. Google рекомендует типичный путь пользователя, а не зеркалирование URL: https://developers.google.com/search/docs/appearance/structured-data/breadcrumb .
  Префиксы `category/product/bundle/filter` зарезервированы за компонентом. ID постоянный внутри типа; категория и товар могут иметь одинаковый ID (разные таблицы), префикс различает сущности. Перемещение товара не меняет URL. Псевдоним выбирается при создании, смена псевдонима требует отдельно проверенных 301 и canonical.
- **Отдельные SEO-фильтры:** URL `/filter/{alias}-{id}` получает только вручную созданная опубликованная посадочная с выбранным набором характеристик, заголовком, метаданными и содержимым. Произвольные значения UI-фильтра не создают автоматически индексируемые посадочные; для них отдельные правила canonical/noindex.
- **Техническая реализация Joomla 6 (предстоит):** Site Router использует выбранный пункт меню `Itemid` как базовый сегмент URL; текущие локально проверенные `/catalog/testovaa-kategoria-1` и `/catalog/testovyj-tovar-1` — временная реализация версии 0.3.2. Чтобы получить целевые **корневые** `/category/...` и `/product/...`, нужно продумать привязку к Joomla menu aliases (возможны скрытые опубликованные пункты маршрутизации) и согласовать `preprocess/build/parse`, генерацию ссылок/canonical, шаблоны и тесты. Не исправлять это только заменой строки в `Router.php`, не модифицировать Joomla core и не создавать незаметно пункты меню на реальных сайтах. Переход разрабатывать маленьким обновлением, сначала для category/product, bundle/filter только после реализации сущностей.
- **Миграция старых URL:** для опубликованных страниц нужна отдельная проверка `301` со старых `/catalog/{alias}-{id}` на новые типизированные, без неоднозначности типа и циклов; приоритет — 404 для неопубликованных сущностей и отсутствие SEO-дублей. На локальном тестовом стенде без индексирования отложенная 301 допустима только как явно зафиксированное ограничение; не выдавать это за готовую миграцию.
- Отдельный **SEO-фильтр в том же компоненте**: пользовательская фильтрация по цене, бренду, свойствам/наличию, сортировка, пагинация; **вручную** созданные индексируемые SEO-лендинги (title/description/H1/текст/модули) и 301 на категорию при отключении. Не индексировать все автоматически генерируемые сочетания параметров; контролировать canonical/noindex/пагинацию.
- Schema.org: товар `Product` + `Offer` с реальной серверной ценой/наличием, категория/SEO-фильтр `CollectionPage` + `ItemList`, хлебные крошки `BreadcrumbList`. Никакой `Article` разметки товара.
- Все GA4-совместимые события **`dataLayer`** реализовать в компоненте: `view_item_list`, `select_item`, `view_item`, `add_to_cart`, `remove_from_cart`, `view_cart`, `begin_checkout`, `add_shipping_info`, `add_payment_info`, `purchase` (один раз с серверной суммой и transaction_id), `refund`; без PII и с учётом согласия на аналитику.

## Checkout, аккаунты, платежи

Остаются прежние бизнес-правила: Joomla Users, вход **только** по телефону с SMS/MAX кодом или МТС ID / Сбер ID / Яндекс ID / VK ID; email — только канал уведомлений, никогда не вход. Авторизованным checkout без повторного ввода; гостю телефон с подтверждением кода после заполнения заказа, без автоматического создания профиля. Доставка/оплата, YooKassa, Email/Telegram/MAX-уведомления, ручные статусы, возвраты и защита заказа от подмены цен. Эти функции идут после рабочего каталога, в основном компоненте, а не в двух независимых системах.

| **M3** | Корзина, checkout, защищённые заказы, доставка/оплата, события `dataLayer`, модуль мини-корзины только при необходимости |
| **M4** | YooKassa (безопасные тестовые платежи), телефон/ID-авторизация, уведомления, возвраты, комплекты/связанные товары и дополнительные функции |
| **M5** | Аудит чистой установки/обновления/удаления, Helix + Cassiopeia, SP Page Builder модули, SEO/security/performance регрессии; релиз |

Сквозные тесты коротких вертикальных срезов не откладывать на M5; внешние реальные платежи/сообщения не запускать без явного одобрения пользователя.
