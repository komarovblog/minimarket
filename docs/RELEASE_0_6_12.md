# MiniMarket 0.6.12 — отчёт «Остатки», фиксация складских правил, необязательный Scheduler

**Код:** `komarovblog/minimarket`, ветка `development`; Joomla 6, PHP 8.4/8.5, MySQL 8.4. **Проверки GitHub Actions: 6/6 PASS** — [Actions #43404889863](https://github.com/komarovblog/minimarket/actions/runs/43404889863), исходный SHA `e42cc6c2415f717bada47bc43facfdaeedfa4e08`; PHP 8.4/8.5, MySQL fresh/upgrade/demo, Windows ZIP и опциональная отдельная сборка Scheduler. **Реальная локальная браузерная проверка в Joomla 6 и СУБД пользователя ещё не подтверждена**.

## Что реализовано

1. Новая шестая полоса **«Отчёты»** на главной MiniMarket, единственная карточка **«Остатки»**. Запись `view=stockreport` в нативном администраторском меню и Joomla dashboard preset. Сохранена синхронизация имён в трёх навигациях.
2. **Нативный интерфейс Joomla** для отчёта: текстовый поиск, стандартные выпадающие фильтры 30/90 дней, состояния запаса и ABC, стандартная сортировка, управление столбцами, локальная прокрутка таблицы, пагинация 20/50/100. Ссылки открывают карточку товара, никакой записи в БД.
3. Сервис `StockReport::load/analyze`: физические товары по ключу запасов (товар или вариант), `stock` — **свободно** уже за вычетом резерва; агрегат `#__minimarket_stock_allocations.status='held'` — **в резерве**; суммарно `свободно + резерв`. Учитывает раздельный остаток вариантов и компоненты комплектов; не умножает «запасы» одних и тех же SKU.
4. Спрос в штуках — сумма `fulfilled` allocation по оплаченным и **вручённым** заказам за выбранный период. `Хватит дней` = доступно / (штук за период / длина периода). Когда подтверждённого спроса нет — `—`, а не бесконечность.
5. ABC — по **валовой выручке прямых строк простых товаров** в оплаченных и вручённых заказах: A — первые 80% оборота, B — следующие 15%, C — остаток; класс без выручки отсутствует. Оборот комплектов не распределяется по компонентам; прогноз **не** учитывает реальные возмещения и полную историю до allocations 0.6.10. Это прозрачные ограничения отчёта, а не скрытая бухгалтерская логика.
6. Исправлено фактическое разрешение контроллером маршрутов `payments` и `payment` из 0.6.11, которое иначе могло возвращать 404, и добавлен `stockreport` во все allowlist.
7. **Упростили выпуск:** обычный `scripts/release-to-desktop.ps1` теперь отдаёт **только `com_minimarket-0.6.12.zip` и необязательный SQL демоданных**, без ZIP необязательного task-плагина. Для тех, кому действительно нужны фоновые Scheduled Tasks, можно явно передать `-IncludeTaskPlugin`; релиз и CI сохраняют возможность собрать плагин `plg_task_minimarketreserves-0.6.10.zip`. **Резервация товара уже внутри com_minimarket и вообще не требует плагина.**
8. `0.6.12.sql` — только `SELECT 1`; отчёт не меняет схему. Не импортировать `sample-data/minimarket_mysql84_nnop3_update_0_6_12.sql` для обычного Joomla-обновления.

## Честная готовность возвратов

На момент 0.6.12 заявки на возврат фиксируются и проходят стадии, но ни `received`, ни `closed` **не восстанавливают остаток на складе**. Это отдельный, ещё не реализованный, операторский шаг контроля пригодности товара (ручное решение + количество + проверка однократности, с отдельным складским журналом). Финансовое возмещение — отдельный механизм, также не готов. **Нельзя** автоматически возвращать в доступный остаток повреждённый товар, опираясь на сам факт возврата.

## Обязательная проверка в живом Joomla

- При установке: предварительный backup базы; проверить появление шестого раздела и одного отчёта; одинаковые ссылки в панели/левом меню/нативном preset, отсутствие 404 у старого «Платежи».
- Проверить товар со складом на уровне SKU, общий остаток вариантов, отдельные варианты, товар без продаж, без наличия, резерв и комплект; отдельные 30/90 дней, A/B/C/без ABC, RU/EN, тёмная/светлая Atum, узкий экран.
- Проверить, что изменение фильтра **не меняет** остатки, а при уже зарезервированном SKU `доступно` и `в резерве` не удваиваются.
- Проверить стандартный Desktop ZIP одной командой и что необязательный Scheduler не требуется ни при создании, ни при оформлении заказа; автозадачи без включённого плагина не работают.
- Проверить, что возврат не выдумывает автоматическую приходную операцию, а основной статус/оплата/доставка сохраняют отдельные значения.
