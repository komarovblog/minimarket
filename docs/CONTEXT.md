# CONTEXT — требования и архитектура MiniMarket
Актуализировано: 2026-10-29. Рабочая ветка: `development`; `main` не изменять.

## 1. Цель
Создать **очень быстрый, минимальный, модульный** интернет-магазин как собственный компонент Joomla 6. Joomla выполняет функции CMS (страницы, меню, пользователи, шаблон, штатные модули); вся торговая логика — в `com_minimarket`, без патчей CMS, тяжёлых сторонних e-commerce систем и универсального конструктора процессов.

**Статусы решений:** `ПОДТВЕРЖДЕНО` — заявлено пользователем; `ПРОЕКТ` — техническая рекомендация, требующая итогового согласования; `ОТКРЫТО` — не решено.

## 2. Подтверждённый функционал — ПОДТВЕРЖДЕНО
- Каталог: простые категории, товары, комплекты товаров.
- URL категорий, товаров и комплектов **без вложенности категории**, содержат собственное название/slug и стабильный ID. При переносе товара или комплекта между категориями URL не меняется.
- Фильтр каталога.
- Корзина.
- Модули похожих товаров; возможность ставить собственные модули на SEO-страницы.
- Микроразметка; события электронной торговли через `window.dataLayer`.
- SEO-фильтр: выбранной комбинации фильтров назначаются отдельные URL-лендинг, Title, Description, текст и модули.
- Простой раздел заказов без сложных бизнес-процессов; статусы заказа устанавливаются администратором вручную.
- **Штатный дизайн административной панели Joomla 6:** для компонента используем её стандартные формы, таблицы, кнопки, ACL и оформление. Собственную тему администратора не создаём.
- **Штатные пользователи Joomla:** не создаём отдельную систему пользователей/паролей. Собственный простой личный кабинет MiniMarket поверх пользователей Joomla.
- Цена, скидка, стоимость доставки и итог заказа **всегда вычисляются на сервере** и не принимаются из браузера.
- **РЕШЕНИЕ 29.10.2026 (заменяет старое):** вход только по телефону с кодом MAX/SMS либо через МТС ID, Сбер ID, Яндекс ID, VK ID. Email не для регистрации/авторизации/восстановления, а только необязательный канал уведомлений.
- Стандартные варианты доставки и оплаты; онлайн-оплата через ЮKassa.
- Минимум кода и сущностей, модульность, скорость, простота сопровождения.
- Процесс разработки и журналирование — правила в `NEW_AGENT.md`.

## 3. Предлагаемая архитектура — ПРОЕКТ
**Установочный пакет:** `pkg_minimarket` с `com_minimarket`, `mod_minimarket_cart` и `mod_minimarket_related` (модуль похожих товаров добавлять только при необходимости отдельной позиции шаблона). Отдельный plg_*, lib_* и Composer-фреймворк не создавать без подтверждённой потребности.

**Один компонент, несколько маленьких сервисов** в его namespace:
- `Catalog`: категории, единая сущность продаваемого элемента `item` (тип `product` или `bundle`), карточки и состав комплекта.
- `Filter`: фильтруемые свойства/значения и запросы выборки; никакой второй отдельной модели каталога.
- `Seo`: стабильная маршрутизация, метатеги, JSON-LD, SEO-лендинги.
- `Cart`: корзина и расчёт цен, единый интерфейс для товара/комплекта.
- `Order`: оформление, фиксированные снимки цен/позиций/доставки, ручной статус заказа.
- `Payment`: ЮKassa API, idempotency, webhook, сверка платежа; технический статус оплаты отдельно от ручного статуса заказа.
- `Account`: лёгкая интеграция со штатными Joomla Users, контакты покупателя, история заказов, выбор способа регистрации; **никакого собственного хранения паролей**.
- `Verification`: одноразовые SMS-коды, ограничения отправок/попыток, срок действия; подключение SMS-провайдера по HTTP API.
- `Notification`: почта Joomla и по желанию бот Telegram / бот MAX через отдельные маленькие адаптеры; сбой доставки сообщения не отменяет заказ.
- `Analytics`: только генерация событий dataLayer; без встроенного аналитического движка.
Контроллеры Joomla тонкие, SQL в репозиториях, бизнес-правила в сервисах, HTML в шаблонах представлений. Без дополнительных интерфейсов, абстракций и классов без нужды.

## 4. Каталог и URL — ПРОЕКТ
- Категории имеют **необязательный parent_id**: можно создать простую иерархию разделов, но URL каждого раздела остаётся плоским и не зависит от родителей. При перестановке категории/подкатегории её URL не меняется. Item принадлежит одной категории; комплект отображается в категории, как товар, но имеет отдельный тип и состав.
- Примеры URL (финальное название префиксов уточняется): `/category/kresla-12`, `/product/sinee-kreslo-1042`, `/bundle/komplekt-dlya-gostinoy-2110`. ID — источник истины, slug — человекочитаемый; при смене категории URL не меняется. При смене slug настроить 301 с известного старого адреса на актуальный и избегать дублей.
- Поиск по стабильному ID: неизвестный/неверный URL -> 404 либо один канонический 301 при правильном ID; не создавать дубликаты с произвольным slug.
- Состояния записи для MVP: опубликован/скрыт; цена, остаток (если используется), фото, описание, SEO-поля. Историю ревизий и сложные товарные вариации не включать.
- Комплект — отдельная продаваемая позиция со своей ценой. Состав: товар + количество. Правило остатков комплекта (самостоятельный / из компонентов) — ОТКРЫТО, не реализовывать на предположении.

## 5. Фильтр и SEO-лендинги — ПРОЕКТ
- Свойства фильтра задаются администратором для категории. Тип по умолчанию — дискретные значения (чекбоксы), цена — диапазон. Только свойства, реально участвующие в выборе.
- Обычный фильтр — GET-параметры, стабильный порядок/валидация значений, пагинация, сортировка. Первый HTML ответ рендерится сервером; JavaScript только улучшает UX, не является обязательным.
- Произвольные URL фильтра не индексируются как самостоятельные страницы. Настройка canonical/noindex и ограничения обхода должна быть проверена на живой Joomla, чтобы не препятствовать обходу разрешённых страниц.
- SEO-лендинг — **отдельная сущность**, связывающая категорию и точный нормализованный набор выбранных значений свойств (хранить IDs, сортировать), с уникальным человекочитаемым URL без ID, например `/kresla-sinie`. Только явно опубликованные лендинги индексируются, включаются в sitemap, имеют самоканонический URL, свои Title, Description, H1, SEO-текст.
- При визите на SEO-лендинг применяются сохранённые фильтры, показ товаров вычисляется живым запросом, не копируется. Админ может подключать стандартные модули Joomla через выделенный скрытый пункт меню для лендинга; использовать штатное назначение/позиционирование модулей, не писать второй движок модулей. Механизм короткого URL проверить в прототипе.
- Обычная комбинация фильтров, идентичная лендингу, должна иметь одну выбранную каноническую версию/переход, а не две конкурирующие индексируемые страницы.
- Пустой SEO-лендинг: запрещать публикацию без результатов или определять SEO-поведение отдельно; для пустых произвольных комбинаций не создавать индексируемую страницу.
- URL лендинга уникален среди других маршрутов сайта; конфликт с обычной статьёй Joomla должен выявляться до сохранения.

## 6. Корзина, оформление, заказы — ПРОЕКТ
- Корзина **хранится в сессии Joomla** для гостя/авторизованного пользователя на первом этапе; отдельные таблицы корзины пока не нужны. Пересчёт цен и доступности на сервере при каждом переходе к оформлению. Без сложной синхронизации между устройствами.
- Модуль корзины — компактный счётчик и сумма в шапке; HTTP-эндпоинт для динамического обновления, чтобы персональные данные не утекали через общий HTML-кэш.
- Оформление на одной странице по пользовательской логике DNS: данные покупателя → получение → оплата. Авторизованному не нужен код; гостю предлагается вход или покупка без входа. После заполнения всех полей и нажатия «Подтвердить заказ» гость подтверждает телефон через MAX/SMS; только затем сервер создаёт заказ и платёж. Проверка гостя не создаёт аккаунт, email необязателен.
- Сохранить заказ и строки заказа **до** перехода к ЮKassa (для связи payment_id и order_id). Состав, цены, количество, название, доставка и суммы фиксируются как снимок и не меняются задним числом при изменении каталога.
- **Безопасная цена:** клиент отправляет только ID позиции, количество, ID выбранного способа доставки/оплаты и необходимые контактные данные. Сервер заново загружает цену/состояние/скидки/тариф доставки из доверенных источников, проверяет права на промокод (если появится), рассчитывает итог и записывает снимок. Поля `price/total/discount/delivery_cost` из POST/JSON не принимаются как источник истины; цены на странице — только отображение.
- Денежные величины фиксировать в целых минимальных единицах валюты (например, копейках), без float. Создание заказа/строк и резервирование (если появится) — в транзакции. На создание платежа отправляется сумма сохранённого сервером заказа.
- Webhook ЮKassa: только после запроса к API и сверки `payment_id`, связанного заказа, валюты, суммы и итогового статуса; повторная доставка идемпотентна. Ссылку возврата покупателя не принимать за доказательство оплаты.
- В админке: список, поиск по номеру/контакту, карточка, ручной статус исполнения, комментарий администратора (если понадобится). Не делать маршруты, CRM, складскую систему и таблицы отчётов.
- Технический статус оплаты (`pending/succeeded/canceled`) не редактируется вручную: только подтверждённое сервером состояние ЮKassa. **Ручной статус заказа** отдельный (например `new/processing/completed/canceled`). Запрещать ошибочную отметку «оплачен» только по возврату покупателя со страницы платежа.
- Доставки MVP — конфигурируемые простые методы (самовывоз, курьер, отправка/ПВЗ без автоматических интеграций служб на первом этапе); стоимость и доступность определяются сервером. Окончательный набор — ОТКРЫТО.
- Оплаты MVP — ЮKassa; возможность включить ручной способ «при получении» обсудить отдельно.
- ЮKassa: ключи в .env; запросы с идемпотентностью; webhook -> валидация и серверная проверка фактического платежа через API ЮKassa -> сопоставление с заказом (номер, сумма, валюта, статус) -> идемпотентное обновление. 200 только после корректной обработки; ошибки фиксировать безопасно. Чеки/НДС согласовать в зависимости от модели фискализации.
- Остатки и резерв при оплате — ОТКРЫТО: если ведём остатки, предусмотреть защиту от продажи сверх наличия; не добавлять незапрошенную складскую систему.

## 7. Микроразметка, dataLayer, SEO — ПРОЕКТ
- JSON-LD для товара/комплекта: Product/Offer; для списков BreadcrumbList по фактической навигации, а не фиктивной вложенности URL. Только реальные цены, наличие и рейтинги, без выдуманных отзывов.
- `dataLayer` (GTM/GA4-совместимые названия): `view_item_list`, `select_item`, `view_item`, `add_to_cart`, `remove_from_cart`, `view_cart`, `begin_checkout`, `add_shipping_info`, `add_payment_info`, `purchase`. Единые `item_id`, `item_name`, `price`, `quantity`, `currency`; `purchase` с `transaction_id` по реально подтверждённой оплате без двойной отправки от callback/возврата. Для ручного способа будущая логика события отдельно. Скрипт GTM ставит владелец сайта, компонент генерирует данные.
- SEO категории/товара/комплекта: уникальные Title, Description, H1, основной текст, canonical, robots, sitemap. Изображения: alt, фиксированный размер, современные форматы.

## 8. Минимальная модель БД (черновой состав, не утверждён) — ПРОЕКТ
1. `#__minimarket_categories` — parent_id допускает дерево для навигации, но не влияет на URL
2. `#__minimarket_items` — товар/комплект одним типизированным объектом, category_id
3. `#__minimarket_bundle_items` — состав комплектов
4. `#__minimarket_attributes` — параметры фильтра
5. `#__minimarket_attribute_values`
6. `#__minimarket_item_values` — индекcированные связи фильтра и элементов
7. `#__minimarket_landings` — SEO-страницы (категория, комбинация фильтров, SEO и назначения)
8. `#__minimarket_orders`
9. `#__minimarket_order_items`
10. `#__minimarket_payments` — попытки оплаты/подтверждения, отдельные от статуса заказа

Итого исходный ориентир **10 торговых таблиц**. Для регистрации по телефону ориентировочно добавятся **контакты покупателя** и **SMS-проверки** (см. раздел 13), а при требовании гарантированной доставки уведомлений — небольшой outbox. Точное число таблиц ещё не утверждено: оно следует из нужных бизнес-сценариев и проверки связей, а не из искусственного лимита. Методы доставки/оплаты и их простой тариф для MVP — настройки компонента, отдельные таблицы не создавать. Изображения товаров — медиа Joomla и ссылки в полях до реальной потребности в сложной галерее. Принимаем только проверенную схему без дублей.

## 9. Быстродействие и безопасность — ПРОЕКТ
- Server-rendered HTML (без SPA), минимальный JS/запросы, работа фильтра без JS; SQL с индексами по category/status/price и парам значений; без N+1 запросов.
- Не загружать все товары и все комбинации фильтра в память. Пагинация на SQL; данные только для текущей страницы.
- Миниатюры создаются при загрузке, не при каждом запросе; lazy loading ниже первого экрана; WebP/AVIF по поддержке сервера; dimensions в HTML.
- Кэшировать публичные карточки, категории и справочники с корректной инвалидацией после изменений. **Никогда** не отдавать чужую корзину и личные заказы из публичного кэша, проверять поведение штатного cache Joomla.
- CSRF на изменяющих действиях, экранирование HTML, параметризованный SQL, валидация пользовательских вводов, ограничения частоты запросов при необходимости, права доступа в админке. Не хранить реквизиты карты.
- Специальные тесты злоумышленника: изменённая цена/доставка/скидка/количество в запросе; чужой заказ и кабинет; поддельный webhook; повторная оплата/проверка кода; попытка обойти лимиты SMS. **Сервер всегда побеждает браузер**.
- Не подгружать сторонние библиотеки на каждой странице, не создавать фиктивные «универсальные» слои.
- Метрики качества **на тестовой среде**: TTFB, SQL-query count, размер HTML/JS/CSS, LCP, CLS, скорость фильтра на реалистичном количестве элементов; целевые значения задать после базового профилирования.
- Joomla официально поддерживает 6.x PHP от 8.3 и рекомендует 8.4, для проекта целиться в PHP 8.4, MySQL 8+ по требованиям Joomla. Ветки Joomla обновлять после тестов копии.

## 10. Репозиторий и разработка — ПОДТВЕРЖДЕНО
- NEW_AGENT, CURRENT_TASK, docs/CONTEXT, docs/PLAN — обязательные четыре документа; обновлять сразу при любом изменении.
- Локальный .env исключён из Git; .env.example — точная карта ключей; отдельная штатная конфигурация Joomla не публикуется.
- Любой консольный тест запускается через общий runner; он проверяет синхронизацию development и пытается опубликовать безопасный результат в `logs/LAST_RUN.log`.
- Нет Docker как обязательной зависимости, только простая локальная среда PHP/Joomla, Windows PowerShell и Git; не создавать второй набор кода под хостинг.
- После ответа пользователя «Готово» читать GitHub, не требовать выслать текст консоли, если там появились результаты.

## 12. Открытые решения (в будущем обсуждать последовательно)
- Конкретная форма URL и название трёх префиксов; короткие SEO-лендинги без префикса — проверить конфликты Joomla.
- Как работает остаток комплекта и есть ли ограничение складских остатков вообще.
- Список способов доставки, тарифы, география, вариант оплаты при получении.
- Размеры каталога/фильтров для тестов производительности.
- Правила оформления чеков и налогов в ЮKassa.
- Не расширять MVP до большого Shop без отдельного решения пользователя.
- Email-вход исключён окончательно. Внутренний технический email Joomla — открытая задача прототипа, не новое требование к покупателю.
- SMS-провайдер, восстановление/связка двух способов входа, необходимость постоянной очереди уведомлений и конкретные события.
- Целевой набор входов: МТС ID, Сбер ID, Яндекс ID, VK ID и телефон MAX/SMS. Подключение МТС/Сбер требует партнёрских разрешений; T-ID и MAX ID в текущий набор не входят.

## 13. Пользователи, личный кабинет и регистрация — частично ПОДТВЕРЖДЕНО, реализация ПРОЕКТ
- **ПОДТВЕРЖДЕНО:** единая идентичность, пароли, сессии, блокировка и ACL — через штатный Joomla `#__users` и API пользователей, никакой второй таблицы с паролями. Пользователь с группой Registered не получает доступ к админке. Личный кабинет MiniMarket — собственные страницы поверх Joomla: контакты, история заказов, адреса/настройки при необходимости и подключённые способы уведомлений. Для гостей оформление заказа сохраняем доступным без обязательной регистрации (предложение из архитектуры, ещё проверить бизнес-решение).
- **НОВОЕ ПОДТВЕРЖДЁННОЕ РЕШЕНИЕ:** МТС ID, Сбер ID, Яндекс ID, VK ID либо телефон MAX/SMS без пароля. Старый сценарий по email/паролю отменён.
- **Email НЕ путь авторизации.** Может быть добавлен только для уведомлений; внутренний обязательный email в Joomla User — техническое поле, не показываемое покупателю и не пригодное для отправки писем/восстановления. Реализацию подтвердить прототипом Joomla без изменения ядра.
- **Телефонный вход:** нормализованный номер E.164 и разовый код MAX/SMS без пароля; после верификации в режиме входа создаётся/открывается Joomla-пользователь. В режиме гостевого заказа номер подтверждается без создания/открытия аккаунта. **Ограничение ядра Joomla:** email обязателен в учётной записи. Чтобы поддержать настоящий вход только по телефону, потребуется безопасный внутренний технический email со служебным неотправляемым доменом, а стандартные почтовые уведомления/активацию/восстановление для такого аккаунта заменить соответствующими телефонными сценариями. Нельзя генерировать реальные посторонние адреса или рассылать письма на фиктивные. Проверить в прототипе валидацию Joomla, смену email, восстановление и совместимость с обновлениями до реализации. Более простой альтернативой остаётся требование email и при телефонной регистрации — **не подменять решение без согласования**.
- Сведения об email/телефоне связываются с `user_id` Joomla, с признаком подтверждения и уникальностью подтверждённого номера. При добавлении второго способа входа уже существующему пользователю — повторное подтверждение владения; никаких автоматических объединений аккаунтов по совпадению введённого контакта.
- **SMS-проверка, ПРОЕКТ:** 6 цифр из криптографически стойкого генератора, TTL 5 минут, повторная отправка не чаще 60 секунд, ограниченные попытки + лимиты по IP/телефону/периоду, защита от регистрации/перебора и нейтральные ответы без раскрытия существования аккаунта. На сервере — защищённый digest кода (с привязкой к контексту), время истечения и счётчики, никогда не исходный код в логах. Код одноразовый, погашается атомарно.
- При смене номера — повторная проверка MAX/SMS; восстановление доступа только по телефону или действующему внешнему ID, не по email.
- Для регистрации и восстановления нужен платный сторонний SMS-провайдер с API. Выбор провайдера и его настройки — ОТКРЫТО; секреты в локальном `.env`, список ключей в `.env.example` **добавляем только при реальной реализации**.
- Упрощённая БД — ПРОЕКТ: `#__minimarket_user_contacts` (user_id, phone_e164, verified_at, каналы уведомлений/ID чатов), `#__minimarket_phone_verifications` (одноразовый digest, expiry, попытки, лимиты/временные записи). Нужно проверить, можно ли ограничиться меньшим набором без ущерба безопасности; не создавать пользователей заново при каждом заказе.

## 14. Email / Telegram / MAX — ПРОЕКТ
- Единый `NotificationService` с адаптерами отправки: Joomla Mail, Telegram Bot API, MAX Bot API. **Отдельного движка рассылок нет.**
- Минимальные события: заказ создан, оплата подтверждена, администратор изменил статус исполнения. Технические внутренние уведомления не должны раскрывать лишние персональные данные в групповых чатах.
- **Администратор:** выбирает один или несколько каналов и технические chat IDs. **Покупатель:** может включить каналы в профиле; email отправляется только на реальный подтверждённый адрес, Telegram/MAX — только после согласия и безопасной привязки.
- Telegram-бот не может первым начать личный диалог, пользователь должен запустить его. Для MAX предусмотреть официальный запуск/диплинк и API, проверить ограничения бизнес-профиля перед выпуском. Токен привязки случайный, одноразовый, ограничен по времени и связан с сессией пользователя; не доверять голому `user_id` в deep-link.
- Отправка в сторонние сервисы не должна блокировать и отменять успешное оформление/оплату. На первом этапе — простая отправка после фиксации операции с безопасной обработкой сбоя; если нужна гарантия и ретраи, **одна** таблица outbox и небольшой CLI/Cron-обработчик без дополнительных очередей/фреймворков. Принцип доставки уточнить перед кодированием.
- SMS — только для подтверждения номера/восстановления, не использовать дорогую SMS-рассылку событий заказа без отдельного решения.
- Токены ЮKassa/Telegram/MAX/SMS/SMTP и конфигурации каналов — в локальном `.env`; реальные личные ключи и номера пользователей не попадают в Git/логи; новые ключи документировать в `.env.example` одновременно с появлением в коде.

## 16. Вход через внешние ID — исследовано, НЕ СОГЛАСОВАНО К ВКЛЮЧЕНИЮ (29.10.2026)
**Вопрос пользователя:** возможно ли реализовать вход/регистрацию на Joomla 6 через MAX, Яндекс ID, VK ID, T-ID (Т-Банк) и Сбер ID. Итог: Joomla технически позволяет интеграцию, но включение конкретных провайдеров ещё не согласовано, а доступность зависит от внешних программ.

### Проверка доступности по официальным источникам
| Провайдер | Возможность / ограничения | Источник |
|---|---|---|
| Яндекс ID | Официальный OAuth 2.0 для сайтов, приложение и согласие на получение данных. Подходит для первой интеграции. | https://yandex.com/dev/id/doc/ru/ |
| VK ID | Официальный OAuth 2.1, SDK для веба; поддержка способов входа через VK/OK/Mail. Подходит для первой интеграции. | https://github.com/VKCOM/vkid-web-sdk |
| Сбер ID | Вход партнёрам; регистрация организации, оферта ЭДО, client ID/secret, сертификат. Подключение требует организационной работы. | https://developers.sber.ru/docs/ru/sberid/guidebook/overview |
| T-ID Т-Банк | OAuth 2.0 / OIDC, партнёрское подключение. На дату проверки 29.10.2026 официальный портал указывает ориентир допуска от **30 000 авторизаций/месяц** (не обещать доступ малому магазину). | https://developer.tbank.ru/docs/intro/partner/tid |
| MAX | Официально документированы боты и мини-приложения, подписанное серверно проверяемое `initData` **внутри MAX**. Универсальный стандартный OAuth-кнопочный вход на внешний Joomla-сайт в проверенной документации НЕ найден. Подключение платформы MAX для партнёров доступно только в установленных правилами категориях организаций/ИП/самозанятых — резидентов РФ. Вход через привязанного бота с одноразовым подтверждением возможен только как проект после отдельного аудита, не выдавать за штатный OAuth. | https://dev.max.ru/docs/webapps/bridge/ ; https://dev.max.ru/help/platform_connection/ |

### Проект единообразной реализации без тяжёлой системы авторизации
1. **Истина — Joomla `#__users.id`** и её сессии. Вход по соцсервису никогда не создаёт второй аккаунт магазина или второй механизм пользовательских паролей.
2. Небольшой сервис `ExternalIdentityService` + адаптеры выбранных провайдеров. Для каждого внешнего входа браузер перенаправляется на провайдера, сервер проверяет возвращённый код/токен и получает **стабильный ID внутри провайдера**, а не доверяет присланному из браузера email/телефону.
3. Одна таблица `#__minimarket_external_identities`: `id`, `user_id` Joomla, `provider`, `provider_subject`, `created_at` (+ минимальные необходимые техполя). Ограничения: UNIQUE(provider, provider_subject), INDEX(user_id), FKs по возможности, исключить повторное привязывание к другому пользователю.
4. Первый вход: если внешняя учётная запись уже связана с Joomla user_id — авторизовать **через штатный механизм Joomla**; если не связана — безопасно создать обычного пользователя Joomla (группа Registered) только после удовлетворения обязательных полей/контактов, затем связать внешний ID.
5. Не связывать аккаунты автоматически по совпадению email, имени или телефона, особенно если провайдер не гарантирует подтверждение поля. У уже авторизованного пользователя есть действие «Добавить способ входа», требующее проверки его текущей сессии/повторного подтверждения; иначе сначала доказать владение старым аккаунтом.
6. Вход без email: в ядре Joomla поле email обязательно. **Решение ещё открыто**: запрос настоящего email на первом социальном входе либо генерировать строго внутренний неотправляемый идентификатор с отключением почтовых сценариев. Никаких случайных рабочих адресов, запрет отправки писем на placeholder. Аналогично phone-only. Не изобретать реализацию до теста на Joomla 6.
7. Проверки OAuth/OIDC: `state` и CSRF/связка с сессией, PKCE там, где поддерживается/требуется; `nonce`/issuer/audience/expiry при OIDC, серверный code exchange, allowlist redirect URI, HTTPS; no open redirects; минимальные scopes. Верификация подписей и сроков строго по спецификации провайдера. Не хранить ненужные access/refresh токены; секреты только в `.env` и документированные имена в `.env.example`.
8. Для слабых браузерных сценариев и мини-приложений MAX никогда не доверять `initDataUnsafe` или переданному `userId`: проверять целую строку `initData` и её подписанное значение **на сервере**; `initData` внутри MAX не доказывает вход в чужой браузер Joomla. Для такого перехода понадобится отдельный безопасный одноразовый обмен.
9. Joomla поддерживает события аутентификации/входа через официальные плагины; сначала проверить минимальную интеграцию средствами компонента и штатного login API. **Новый плагин создавать только если действительно необходим**, избегать системных плагинов на каждом запросе из-за нагрузки и риска поломки админки.
10. Не выводить 5 кнопок, пока провайдеры не подключены; конфигурируемая видимость только реально работающих способов. Любой сбой OAuth не должен ломать каталог, оформление и гостевую покупку.

### Рекомендация (не решение пользователя)
В первую версию рассмотреть **email + телефон** и **Яндекс ID + VK ID**. Сбер ID — после доступов организации; T-ID — после согласования банка и объёмов; MAX — сначала как канал уведомлений, авторизацию лишь после проверки механизма привязки через бот/мини-приложение. Модуль авторизации должен быть расширяемым, но реализовывать только нужные адаптеры.

Таблица внешних идентификаторов добавляется **только если утверждён хотя бы один внешний провайдер**; пока никаких изменений схемы/кода, секретов и `.env.example` по этому разделу не делать.

## 17. Одноразовый код через MAX — исследовано 29.10.2026, реализация НЕ УТВЕРЖДЕНА
**Короткий вывод:** технически покупатель может получать OTP-коды в MAX вместо SMS. В MAX есть официальный бот `@verificationcodes_bot`, а отдельные операторские/агрегаторские каналы уже маршрутизируют OTP по номеру телефона в MAX и переходят на SMS при недоставке. **Нельзя обещать бесплатную отправку или гарантированную доставку всем пользователям MAX.**
- Официальный бот для кодов, в том числе от магазинов и сервисов: https://max.ru/verificationcodes_bot и https://help.max.ru/help/bots/chat-bot_kody_podtverzhdeniya/chto_takoe_chat-bot_kody_podtverzhdeniya
- Документация SMS-агрегатора REDSMS о маршрутизации сообщений операторами в MAX и SMS fallback: https://docs.redsms.ru/faq/questions_max/ . Указано: тариф через MAX — **как SMS**, оператор выбирает маршрут; у некоторых провайдеров канал не выбирается магазином напрямую. Возможные условия других агрегаторов проверять отдельно.
- **ПРОЕКТ (рекомендация):** сделать **один** сервис `VerificationService` и один адаптер `OtpDeliveryProvider`. Пользователь запрашивает код по номеру, провайдер решает куда доставить (MAX/SMS). Сервер проверяет код, TTL/лимиты и связывает результат с номером. Видимый UX: «Получить код» и «Отправить повторно»; не обещать определённый канал, если его назначает оператор.
- Альтернатива для уже привязанных покупателей: собственный MAX-бот может отправлять сообщения по `user_id` через Bot API, но **не знает пользователя только по телефону**, и бот должен быть заранее привязан к Joomla user_id надёжным сценарием. Публичного самостоятельного merchant API для отправки в официальный `@verificationcodes_bot` на основании одной цифры телефона в просмотренной документации не подтверждено. Боты платформы доступны после верификации российского юрлица/ИП/самозанятого; метод `POST /messages` принимает `user_id`. Источники: https://dev.max.ru/docs-api/methods/POST/messages и https://dev.max.ru/docs/maxbusiness/connection .
- **Проверить перед внедрением:** доступность и условия OTP-провайдера для нашего юридического лица; стоимость MAX/SMS и тарификация при fallback; статусы доставки, лимиты и SLA; ограничения по географии; возможность явно выбирать канал; согласие пользователя/политика обработки данных. Ввести провайдерные ключи в `.env` и `.env.example` лишь одновременно с работающим кодом.
- Не смешивать OTP через MAX с кнопкой «Войти через MAX» (самостоятельная федеративная авторизация — отдельный вопрос §16). Служебный код в MAX подтверждает контроль над выбранным каналом/номером только в рамках заявленных гарантий сервиса доставки.
