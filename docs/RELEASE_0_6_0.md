# MiniMarket 0.6.0 — три режима подтверждения, управляемые шаги и цифровая выдача

**База:** 0.5.99, `development`; компонент и отдельный `mod_minimarket_toolbar` версии 0.6.0. **Схема:** аддитивная миграция `admin/sql/updates/mysql/0.6.0.sql` (без удаления старых строк). Важно установить компонент 0.6.0 после резервной копии БД. Joomla 6, PHP 8.4/8.5, MySQL 8.0/8.4.

## Подтверждение покупки — одна настройка, три значения

Глобальный `checkout_auth_mode` в «Оформление заказа»:
- `guest` — гостевой заказ без регистрации или подтверждения (включая цифровой товар, на email из заказа).
- `guests` — неавторизованный покупатель обязан войти или создать аккаунт штатной Joomla. Уже авторизованный — без повторного кода.
- `all` — покупатель обязан войти или зарегистрироваться; перед **каждым новым заказом** получает отдельный шестизначный email-код на адрес аккаунта; 10 минут, до 5 ошибок, не чаще одного запроса в 60 секунд, ограничение 5 запросов в час на сессию. Код связан с Joomla user ID и одноразовым checkout key; после создания заказа оба очищаются.

Значения `email` и `sms`, ранее сохранённые в глобальной настройке, для совместимости читаются как `guests` — **не** превращаются в отдельную неработающую SMS-функцию. Активный способ подтверждения берётся только из «Регистрация» (`checkout_verification_method`), сейчас поддержан email. При неправильной настройке checkout блокируется. Регистрация/восстановление пароля — только штатный `com_users`; для реального подтверждения email новой регистрации включить self-activation пользователей в Joomla. SMS и внешние ID провайдеры не считаются подключёнными.

Подтверждение покупки не означает подтверждение оплаты. Email-код не выдаёт физические товары, файлы, ключи или права доступа до оплаты.

## Четыре шага checkout

`checkout_step_{buyer,delivery,payment,digital}_enabled` (Joomla list, «Включено/Выключено»). Для каждого шага сохраняется отдельное HTML-описание. Стандартное состояние — включено.

- **Покупатель:** отключение допустимо лишь когда Joomla-account уже содержит все обязательные данные и дополнительные поля не требуют ввода. Иначе checkout блокируется (не теряет контакт). Данные покупателя при цифровом заказе включают email.
- **Доставка:** показывается только если есть физические товары; если есть один самовывоз или чисто цифровой заказ, выбора нет. Отключение при обязательном адресе курьера или множестве вариантов вызывает явную ошибку конфигурации.
- **Оплата:** выбор можно убрать только при одном доступном способе, но сама проверка платежа остаётся. Цифровые-only заказы не получают «Оплата при получении»; пока доступен банковский перевод.
- **Цифровая выдача:** показывается только при цифровых позициях. По умолчанию — email покупателя. Если авторизованный покупатель указывает другой адрес, сервер требует отдельный email-код на этот адрес. Гость может указать контактный email в шаге покупателя; альтернативный адрес без входа недоступен. При отключении шага используется email покупателя.

Отдельный шаг «Подтверждение заказа» **удалён**; сумма, товары, согласия и кнопка оформления остаются в итоговом блоке, который отключать нельзя. Прежний HTML `checkout_confirmation_description` игнорируется; согласие с условиями сохраняется.

## Типы цифровой выдачи в карточке товара

`digital_delivery_mode` (file/license/manual/cloud). Выбор отображается только для цифровой позиции:
- **Файл:** существующий приватный upload за пределы Joomla webroot, защищённая HMAC-ссылка после ручного подтверждения оплаты, 30 дней / 10 скачиваний. Гостю — bearer-link из письма без создания аккаунта; для заказов пользователя сохраняется проверка владельца.
- **Ключ:** импорт до 200 кодов за раз, только в режиме license, шифрование libsodium (`sodium_crypto_secretbox`) в БД с ключом, производным от Joomla site secret; HMAC fingerprint и DB UNIQUE предотвращают повтор одного кода. При ручном подтверждении оплаты коды закрепляются за конкретным order_item в транзакции с FOR UPDATE. При нехватке ключей **оплата не помечается подтверждённой**. Выданные ключи не перераспределяются.
- **Ручная выдача:** после подтверждения платежа менеджер вводит инструкцию в карточке заказа, отправляет email, только после успешной отправки фиксируется выдача в заказе с записью события.
- **Облачный доступ:** до установки реального плагина API **только ручное предоставление доступа** через тот же защищённый процесс, без ложного «автоматически активировано». API/SaaS подключается отдельным проверенным адаптером.

При смешанном заказе физическая доставка не закрывается, когда отправлена цифровая часть. Для полностью цифрового заказа статус завершён после успешной выдачи файлов/ключей и всех ручных доступов. Повторные письма не выделяют новые ключи.

## Безопасность и ограничения

- **Секрет Joomla обязателен для расшифровки ключей**: хранить резервную копию `configuration.php`; смена `$secret` без миграции шифрования сделает сохранённые ключи недоступными.
- Файлы остаются в непубличном каталоге; сохранять резервные копии и его.
- Все оплаты банковскими переводами сейчас **ручные**. Нет готовых webhook, автоматических возвратов денег, облачных API и SMS. Облачный способ прямо называется «ручная активация».
- Заказы, лицензии и отправка email должны проверяться в установленной Joomla. Никакие unit/CI проверки не заменяют проверки SMTP, авторизации, формы новой регистрации, dark/light и RU/EN.
- Полноценного резерва физического склада и фискализации ещё нет. Не добавлять отдельные бесполезные переключатели вместо функций.

Только **одна стандартная строка** из [DELIVERY_RULES.md](DELIVERY_RULES.md); всегда из CMD/PowerShell и из любой папки:
```powershell
powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\OSPanel\home\minimarket.local\scripts\release-to-desktop.ps1"
```
Не давать отдельные `cd`, `git pull` и `-SkipPull`. ZIP компонента и toolbar отдельно. SQL примеров на рабочую БД не импортировать.
