# MiniMarket — согласованный план расширения коммерческих функций, 13.11.2026

**Исходная база:** MiniMarket 0.6.14, Joomla 6 / PHP 8.4–8.5 / MySQL 8.4; разработка только в ветке `development`.
**Источник идей:** komarovblog/shop (ветка development), документы REQUIREMENTS_V2.md §§6–12 и PRODUCT_ATTRIBUTES_OPTIONS_LINKED_PRODUCTS_2026-11-03.md. Не копировать код Symfony в Joomla. Решения здесь приняты для MiniMarket только в перечисленном объёме.

## Жёсткое исключение

**НЕТ нового журнала движения запасов**, складской ERP, отдельных складов, закупочной логистики и любого раздела «Движения запасов». Сохранить существующие товары/варианты, StockReservation и текущий отчёт «Остатки». Эта задача не разрешает менять правила резервирования или автоматически пополнять склад после Return. Нельзя придумывать подтверждённый приход товара по событию «Возврат создан». Старые документы, где журнал движений предлагался как следующий этап, в этой части считаются историческими.

## Очередность и зависимости

**A — финансы, факты, фундамент**: C01+C02 (версия 0.6.15), затем C04+C05 (следующая отдельная итерация), C10 (после проверки маршрутов доставки), C11 (после настройки реальных провайдеров). На C01/C02 не делать фискализацию, новые статусы заказов, refund или складской журнал. Требуется миграция без потери старых данных и без подставленного нуля.

**B — работа менеджеров**: C03 (Joomla Users и CRM, отдельные права), C09 (обращения), C06 (единая очередь проблем; источники C03/C05/C09). Не дублировать Order/Shipment/Return/Payment в CRM.

**C — коммерческие правила**: C07 (скидки, затем checkout), C08 (рекомендации, после подтверждённой поставки/возвратов), не менять существующие фиды и SEO без соответствующего теста.

**D — управленческая аналитика**: C12: отчёт Продажи и Возвраты после C01/C02 и корректных операций, затем Дашборд/План-факт/Маркетинг. Отсутствующие интеграции и метрики честно показывать как «Нет данных». Отчёт «Остатки» сохраняется.

## Приёмочные правила для всех этапов

- Отдельная рабочая сущность только для самостоятельного бизнес-факта. Карточки и списки — нативный Joomla Atum, RU/EN, светлая/тёмная и мобильная версия; формы в зависимости от предыдущих параметров показывают только релевантные поля.
- Сервер проверяет каждое изменение независимо от скрытых полей; деньги только DECIMAL/целые копейки без float; UTC-события с автором и доказательством, внешние дубликаты не создают две записи.
- В существующих заказах цены, скидки, товарный состав, контакты и факты оплаты не перезаписываются; миграция только аддитивная, старая неизвестная стоимость — NULL. Денежная роль не даёт публичной утечки через UI, экспорты, API и отчёты.
- Тесты PHP, свежая БД MySQL 8.4, upgrade на наполненной БД, реальный ZIP Windows; затем ручная браузерная приёмка Joomla, отдельно от CI. Только после неё этап «принят».
- Никаких фиктивных СДЭК, ЮKassa, кассы, Telegram/МАХ и налоговых подтверждений. Адаптеры и интеграции включать лишь после реального подключения.

## Текущий факт реализации

**0.6.15 C01/C02 — реализовано, CI PASS; браузерная приёмка не подтверждена.** Код даёт редактирование себестоимости только администратору, снимок на каждую новую строку заказа, стоимость виртуального комплекта из компонентных цен, подтверждение расхода по Shipment с основанием и историей исправлений, read-only показ разницы по товарам и суммы расходов по отправлениям. *Обратите внимание:* отдельная себестоимость вариантов SKU пока не задаётся (наследуется стоимость простого Product); без себестоимости одного компонента комплект не получает фиктивную стоимость. Перемещение запасов, прибыль за вычетом рекламы, возвраты и реальные API не вводились. Браузерная приёмка пока не подтверждена.
