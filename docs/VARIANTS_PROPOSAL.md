# MiniMarket — два варианта магазина на Joomla 6

Статус: **согласованное направление двух вариантов; базовая архитектура заказов и точная реализация подлежат технической проверке**, 30.10.2026. Никакой рабочий код, БД или ядро Joomla этим документом не меняются. Репозиторий `komarovblog/minimarket`, ветка `development`, `main` не трогать. Shop/Symfony — другой проект.

## Контекст и решение пользователя

Пользователь сообщил, что чистая Joomla установлена локально по адресу `http://minimarket.local/` в `C:\OSPanel\home\minimarket.local\public_html`; факт открытия админки ещё отдельно не проверен. Вместо одного проекта магазина пользователь хочет **два варианта расширения**:
1. Магазин на штатных Joomla `com_content`: категории = категории товаров, материалы = товары, дополнительные поля = цены/характеристики, переопределения шаблонов товара и категории; Joomla SEF-URL.
2. Самостоятельный каталог, где категории/товары/комплекты/атрибуты — свои сущности и таблицы, а URL плоские с ID без вложенной иерархии, как было согласовано ранее.
В ОБОИХ — SEO-фильтр, корзина, оформление заказа, авторизация, личный кабинет, уведомления, доставки, платежи, SEO, аналитика и ранее согласованные бизнес-правила. Пользователь предложил заказы как неопубликованные материалы категории `Orders`, но запросил самый простой совокупный способ реализации. Выбрана рекомендация использовать компактные отдельные таблицы заказов; доводы — ниже.

## Общая платформа и разные источники товаров

Избежать двух независимых копий корзины/оплат. Концепция: общий доменный слой `MiniMarket Core` (корзина, расчёт цены, заказы, собственные защищённые таблицы, доставка, платежи, OTP и ID-провайдеры, личный кабинет, события и dataLayer) плюс **два адаптера каталога**:
- `ArticlesCatalogAdapter` — читает только материалы каталожных категорий `com_content`, их fields/tags/images/состояния/ACL, применяет серверную валидацию числовой цены и остатка;
- `NativeCatalogAdapter` — читает собственные таблицы `#__minimarket_*`, категории и продукты, комплекты, характеристики, остатки/остаточную логику, связи.

Конкретные имена PHP-классов, ZIP-пакетов и разбиение на Joomla component/plugin/module определяются при проектировании MVP; здесь они **предложения**, а не уже существующие пакеты. Можно собирать `pkg_minimarket_articles` и `pkg_minimarket_catalog` со стандартными манифестами; **только один вариант каталога активен на конкретном сайте**. Разделяем общие сервисы в исходниках, ставим только реально нужные расширения. Joomla поддерживает пакеты из компонента, плагина, модуля и т. д.: https://manual.joomla.org/docs/next/building-extensions/install-update/installation/package/ .

## Вариант A: товары через `com_content`

- **Категории:** использовать собственный корень каталога в Joomla Categories. Подкатегории допускаются, штатные маршруты Joomla и меню сохраняются. Категории блога/новостей вне магазина не превращать в товары автоматически. Назначение каталожных категорий настраиваемое, по ID.
- **Товар:** `#__content` с ID статьи, заголовком, alias, текстом, intro/full images, статусом, SEO-мета; доп. поля Joomla (`#__fields`, `#__fields_values`) назначать только каталожным категориям.
- **Поля:** тип товара (обычный/комплект), SKU, цена (decimal через собственную нормализацию), старая цена, остаток, наличие/резерв, вес/габариты (при необходимости), бренд/коллекция, набор характеристик по категории, изображения/галерея, для комплекта — связи по Joomla article ID. Не создавать «мертвые» поля без бизнес-требования.
- **Внешний вид:** переопределения (template overrides/alternate layouts) `com_content` article и category для карточки, листинга и кнопки корзины, плюс content-плагин, только в каталожном контексте. Для поставки независимого пакета нужно решить, как безопасно доставлять overrides — не перезаписывать активный шаблон и пользовательские файлы; возможен дополнительный дочерний шаблон / совместимые alternative layouts.
- **Серверная цена и остаток:** клиент передаёт только идентификатор товара и количество, сервер читает текущие данные и проверяет права/статус/цены; цена закрепляется в строке оформленного заказа. Материалы не применяются для расчёта оплаты напрямую на клиенте.
- **URL:** стандартный `com_content` SEF, определяемый настройками меню/категорий, без вмешательства в маршрутизатор Joomla; `https://guide.joomla.org/user-guide/seo/seo-search-engine-friendly-urls` и `https://manual.joomla.org/docs/next/general-concepts/routing/build/`.
- **Медиа/галерея:** используются Joomla Media и собственный лёгкий интерфейс для дополнительных изображений, без повторной библиотеки медиа.

## Вариант B: собственный каталог

- **Свои сущности:** категории, товары, комплекты, свойства по категории, значения свойств, фото, связи альтернативных товаров и «с этим покупают»; свои таблицы и эффективные индексы; данные заказов в общем торговом Core.
- **URL:** плоские `/{alias}-{id}` для категории/товара/SEO-лендинга, **без цепочки родительских категорий**. Исключить пересечения slug/ID между типами через единый реестр маршрутов/проверку уникальности; canonical и 301 при изменении alias. Точную реализацию resolver/router подтвердить после теста Joomla SEF и конфликтов меню.
- Админка в стандартном стиле Joomla (Atum), URL/SEO, минимальный набор интерфейсов и зависимостей. Нет изменения ядра Joomla.

## SEO-фильтр ОБЯЗАТЕЛЕН в обоих вариантах

Не путать три функции:
1. **Пользовательская фильтрация:** категории, бренд, цена, характеристики, наличие, сортировка, корректные пагинация/количество, серверная выборка. Адаптеры данных разные: A по Joomla Custom Fields (при необходимости вспомогательный индекс для скорости), B по собственным индексированным таблицам.
2. **Индексируемые SEO-посадочные страницы:** создаются и включаются вручную с конкретными условиями фильтра, собственными title/description/H1/текстом/назначаемыми Joomla-модулями/canonical и записью в sitemap; не создавать индексируемую страницу для каждой случайной комбинации фильтров.
3. **Обычные сочетания параметров:** запросы с параметрами имеют предсказуемый URL, не индексируются как дубликаты (canonical/noindex по проверенной SEO-политике), сохраняют фильтр при пагинации, не подмешиваются в ручные SEO-страницы.

**A:** основные категории/товары используют стандартные SEF `com_content`. SEO-лендинги могут оформляться как штатные пункты меню Joomla на представление фильтра MiniMarket с меню-ориентированными URL, не меняя адреса самих материалов. Стандартные template overrides **не реализуют SQL-фильтрацию/корректную пагинацию сами по себе**; нужна отдельная выборка и контроллер/представление или подходящий слой Smart Search. У Joomla Smart Search есть индексируемые поля-таксономии, но он не заменяет универсальный фасетный торговый фильтр без тестов. См. https://magazine.joomla.org/issues/2025/march-2025/stop-searching-start-filtering ; https://guide.joomla.org/user-guide/smart-search .
**B:** наш роутер делает плоские SEO-адреса лендингов с ID и 301; та же общая административная модель лендингов, иной источник товаров.
При отключении SEO-лендинга — 301 на исходную категорию (по прежнему согласованному правилу), корректные hreflang при языках, JSON-LD Product/Offer/BreadcrumbList (по фактическому типу страницы), dataLayer.

## Заказы: минимальное защищённое хранилище (базовая архитектура)

По просьбе пользователя сравнивали, **как проще реализовать в совокупности**, а не только как быстрее завести форму. Выбрана **рекомендуемая базовая архитектура: собственные таблицы заказов для обоих вариантов каталога**, а не неопубликованные статьи категории `Orders`. Пользователь ещё может изменить это решение до реализации, но разрабатывать систему платежей на статьях `com_content` не следует по умолчанию.

**Почему не неопубликованные статьи?** Установка `state=0` и закрытая категория препятствуют обычной публичной публикации, но не моделируют атомарные транзакции, зафиксированный состав заказа и цены, платёжную идемпотентность, составные строки и адресный доступ покупателя к заказу. Если использовать статьи, к ним пришлось бы всё равно дописать собственные таблицы строк/платежей, отследить жизненный цикл article, остановить экспорт персональных данных в поиск, API, модули, RSS и стандартные ACL. Это увеличивает, а не уменьшает объём и риски.

**Минимальный состав исходных таблиц:**
- `#__minimarket_orders`: внутренний ID, номер, Joomla user_id (nullable для гостя), статус заказа и оплаты, контактные данные с ограниченным доступом, стоимость, доставка, скидка/налоги, итог, служебные временные метки, версия/идемпотентность;
- `#__minimarket_order_items`: заказ, тип источника каталога A/B, исходный article/product ID, зафиксированное имя, SKU, цена, количество, сумма и существенные характеристики;
- `#__minimarket_payment_events`: внешний идентификатор транзакции/события, уникальные idempotency keys, проверенный статус вебхука, технические timestamp; при необходимости — последующая история статусов отдельной таблицей, а не искусственно много таблиц на старте.

Приоритет — принципиальная модель. Точный набор/состав таблиц утвердить перед первой миграцией (в том числе защита PII, возвраты, хранение логов и очистка). Joomla user, авторизация по телефону/ID и гостевой заказ действуют по общему ранее согласованному правилу.

**Админка «Заказы»** — в стандартном стиле Joomla Atum, список и форма как у материалов, но с ограниченными правами и без публикации в `com_content`. Поэтому отдельный интерфейс можно сделать компактным, без полной CMS-обвязки каждого заказа. **Не создавать категорию `Orders`** и не пытаться хранить реальные контакты покупателей в `#__content`.

## Настройка товарных категорий для MiniMarket Articles

Отличаем товары не по глобальной подмене типа `com_content`, а по **настройке MiniMarket**:
- В админке расширения `MiniMarket → Настройки → Каталог на материалах` поле `Товарные категории`: multi-select существующих **Joomla category IDs**, вначале пусто. Доступно по правам Joomla admin.
- Флаг `Включать подкатегории` (отдельно, по умолчанию **выключен до явного решения**); при включении учитываются дочерние категории рекурсивно, исключённые/неопубликованные категории и ACL проверяются при выборке. Для MVP допускается один корень.
- Только **опубликованный Joomla article из выбранной/разрешённой товарной категории** с корректной ценой, доступом и наличием считается активным товаром для листингов/корзины/Schema Product/dataLayer. В других категориях материалы остаются обычными статьями, даже если у них похожие поля.
- При переносе материала в/из товарной категории он меняет режим после проверки данных; старые строки заказов остаются неизменными, потому что являются снапшотами. Корзина проверяет актуальный article ID, состояние/ACL, цену, остаток на сервере.
- **Поля Joomla:** создать согласованную группу (например «Товар») и назначить её выбранным категориям; SKU, цена, старая цена при наличии, остаток, характеристики (по категории), фото/галерея, бренд и коллекция только при необходимости. `Automatic Display` у торговых полей — `Do not automatically display`, чтобы штатный вывод материалов не дублировал коммерческий интерфейс.
- Привязку Joomla custom fields к новым категориям нужно синхронизировать при изменении настроек, без удаления данных при выключении. Формат цены строго проверяется и нормализуется сервером; не смешивать `string` и деньги.
- Joomla category/article URLs штатные (`com_content`); шаблон товара/категории — через alternative layouts / безопасные template overrides, без патчей ядра и чужого шаблона. Не делать глобальный override обычных статей без ограничивающих проверок.

Joomla официально поддерживает привязку Custom Fields к категориям и альтернативные layout/overrides: https://guide.joomla.org/user-guide/fields/fields-adding-custom-fields-parameters ; https://guide.joomla.org/user-guide/templates/templates-template-layouts ; https://guide.joomla.org/user-guide/templates/templates-template-overrides .

## Schema.org — только торговым страницам, обе реализации

Обязательный контекстный вывод JSON-LD без конфликтующих дубликатов (Schema.org не равна GA4 dataLayer):
- Карточка товара A/B: `Product` + корректный `Offer` (name, image, sku, brand, price, priceCurrency, availability; расширения доставки/возвратов, если реально известны). Разметка Merchant listings: https://developers.google.com/search/docs/appearance/structured-data/merchant-listing .
- Категория/SEO-лендинг A/B: `CollectionPage`, `ItemList` с действительными товарами, `BreadcrumbList` по фактической навигации; **не ставить основной `Product` на всю страницу каталога**, поскольку это листинг, а не один товар.
- Обычные статьи Joomla: штатные `Article`/`BlogPosting`; MiniMarket не вмешивается. На товарах предотвращать конфликтующий избыточный основной `Article` тип, если Joomla Schema.org plugin уже сгенерировал его: согласованная интеграция/настройка Joomla Schema plugin, затем один корректный Product. Joomla Schema types/Custom: https://guide.joomla.org/help-pages-references/common-elements/edit-schema .
- Всё отражает **текущие серверные** цену, доступность и публичную информацию; не показывать вымышленные рейтинги, не дублировать разные цены; валидировать Google Rich Results Test.

## Электронная торговля через `dataLayer` — обязательна A и B

**Одна реализация событий в общем торговом Core**, читающая товарные данные через `ArticlesCatalogAdapter` или `NativeCatalogAdapter`. Самостоятельные хардкодированные разметки для A/B не дублировать. События на действия пользователя:
`view_item_list`, `select_item`, `view_item`, `add_to_cart`, `remove_from_cart`, `view_cart`, `begin_checkout`, `add_shipping_info`, `add_payment_info`, `purchase`, `refund` (если реализован возврат).
- Единый GA4 ecommerce object: `currency`, `value`, `items[]` (`item_id`, `item_name`, `price`, `quantity`, категории, бренд/список при наличии). Каждому товару нужен стабильный `item_id`: рекомендуется namespace `article:<id>` vs `product:<id>` (или SKU, если он действительно уникален и неизменен) для устранения коллизий при смене адаптера.
- Событие `purchase` только по подтверждённому оформлению заказа, с `transaction_id` (ID/номер заказа) и рассчитанной на сервере суммой; guard against duplicate pushes при повторной загрузке страницы/возврате из платёжного шлюза. Возврат связан с той же транзакцией. Нельзя считать просто открытие страницы оплаты покупкой.
- **Никогда не помещать в dataLayer** телефон, email, ФИО, адрес, одноразовые коды, платёжные токены или другие персональные данные. Отправка тегов после согласия пользователя в режиме блокировки cookie; отдельно соблюдать согласованный альтернативный режим.
- `dataLayer` — только слой данных, **не навязывать** конкретный аналитический сервис и не подключать GTM автоматически; сайт подключает провайдер по своим настройкам. Стандарты событий GA4: https://developers.google.com/analytics/devguides/collection/ga4/ecommerce?client_type=gtm .

## Общий функционал (обе версии)

- Статусы заказов вручную; история изменений и идемпотентность платежей; цены и состав на момент заказа.
- Joomla Users, вход **ТОЛЬКО телефон MAX/SMS OTP** или МТС ID/Сбер ID/Яндекс ID/VK ID; email только уведомления, не логин. Зарегистрированный пользователь без дополнительных полей; гостевой checkout с телефоном, подтверждённым кодом после заполнения заказа; отсутствие автоматической регистрации гостя. Техническое поле email Joomla не превращать в способ входа.
- Единая логика доставок/вариантов оплаты; YooKassa, проверка backend/webhook; email/Telegram/MAX уведомления.
- Комплекты, остатки, рекомендации, JSON-LD, dataLayer, SEO, быстродействие, безопасные обновления Joomla без патчей core.
- Разработка в GitHub `development` → сборка ZIP → установка через Joomla; работающая CMS и её БД в `public_html`/MySQL вне Git.

## Последовательность разработки — предложение

1. **Проверить установленную чистую Joomla:** сайт и `/administrator/`, PHP 8.5, DB-префикс, пример одного article/category/field; не изменять ядро.
2. Определить интерфейс общего Core: `ProductInterface` (`id, sku, price, availability, images, attributes`) и `CatalogProviderInterface` (get item/list/filter/search); серверная цена, заказы, безопасные миграции.
3. **Сначала реализовать вариант A** с одним каталожным root, одним тестовым товаром и категорией, полями price/SKU, override article/category, кнопкой добавления в корзину; проверить URL `com_content`.
4. Добавить общую корзину, checkout, защищённые заказы, тестовые платежи без реальных денег.
5. Реализовать SEO-фильтр A и ручные SEO-лендинги, обеспечить правильные pagination/robots/canonical.
6. Реализовать вариант B на общих интерфейсах и сервисах, своим каталогом и плоским роутером с ID. SEO-фильтр B.
7. Проверить установку/обновление/отключение каждой версии, отсутствие повреждения Joomla и возможность последующей миграции A → B через явную карту IDs/301 (не обещать миграцию без теста).

**Базовое решение:** товары в A — выбранные категории Joomla/материалы/поля; заказы A+B — защищённые таблицы MiniMarket с привычной админкой; Schema.org и dataLayer реализуются контекстно в обеих версиях. Открыто для детализации: точные права, исключения категорий/наследование, состав полей, доставка overrides/темы A и имена пакетов; одновременную активацию A/B на одном сайте не планируем.

## Уточнение архитектуры и фронтенда 30.10.2026
Разобрали Helix Ultimate и SP Page Builder; предложено не два независимых магазина, а один общий `com_minimarket`, Articles адаптер `plg_content_minimarket_articles` и отдельный `com_minimarket_catalog` для версии B. Общие Schema/dataLayer и виджеты; theme-specific overrides только для *полной компоновки*, а не для бизнес-логики. Подробный перечень, ZIP, ограничения SPPB/Dynamic pages и этапы — **`docs/EXTENSIONS_ARCHITECTURE.md`**. Два варианта нельзя считать одновременно устанавливаемыми на один сайт, пока не решено владение shared dependencies. Существующая работающая Joomla только тестовый стенд.
