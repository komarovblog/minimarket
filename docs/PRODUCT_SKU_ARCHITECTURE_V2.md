# MiniMarket — утверждённая модель «товар → SKU» (02.11.2026)

**Реализация на 03.11.2026 (0.5.24):** после основания A (0.5.20) и локального редактора B1 (0.5.21–0.5.23) опубликован B2.1: добавить одну SKU-позицию, выбрать её локальные параметры, копировать торговые поля без повторения идентичности, массово редактировать цену/остаток отмеченных вариантов. Сохранение — старый серверный ProductVariants в транзакции, новые SQL-таблицы не требуются. [Ручная приёмка 0.5.24](M24_SKU_POSITION_EDITOR_B2_SMOKE.md) пока NOT RUN. **Не считать** реализованными фотогалереи общих значений цвета, собственные видео/характеристики позиции (B2.2), единый SKU вместо базовых торговых полей (C), корзину/резерв (D), импорт/фиды/фасеты (E).


**Статус: решение пользователя, целевая архитектура. Не путать с текущей реализацией 0.5.19.** Один товар, один основной URL, множество равноправных продаваемых SKU. Каждый SKU может иметь свой артикул, цену, остаток, публикацию, фото, описание и особенности. В админке не должно требоваться предварительно создавать глобальную характеристику и назначать её категории. Всё создаётся внутри самого товара. Интерфейс штатный Joomla 6, RU/EN; ядро не меняем.

## Модель

**Товар** (стабильный product_id): общая карточка, группа, URL, название, бренд, категория, SEO/canonical, общее описание, общие фотографии и характеристики. Это не самостоятельная продаваемая единица, если у него уже есть SKU.

**SKU** (стабильный variant_id): конкретная продаваемая единица с уникальным артикулом, ценой, остатком, статусом, необязательными отдельными фото и описанием. Все SKU в одном товаре равноправны. Смена варианта не меняет основной URL.

**Параметры выбора**: Цвет, Размер, Объём и другие локальные параметры, задаваемые прямо в карточке товара. Значения сохраняются с независимыми ID. Не нужно заранее создавать «Различает варианты товара» в глобальных характеристиках. Глобальные справочники можно подключать **опционально** для единообразия и импорта. Несколько материалов, например металл + камень, не создают SKU автоматически.

**Простой товар:** один SKU скрыт от пользователя как отдельная строка; обычный редактор просто показывает SKU/цену/остаток. При переходе к вариантам данные не дублируются и не теряются. Пока продолжается миграция, старые поля products.sku/price/stock — переходная совместимость; не объявлять их удалёнными.

## UX редактора

Товар → Варианты: кнопка «Добавить варианты», затем локально вводим «Цвет: красный, синий», «Размер: S, M, L» через нативные повторяемые поля. «Создать комбинации» показывает предварительную матрицу 2×3. Администратор может исключать сочетания, массово вводить цены/остатки и SKU, копировать строку, сортировать. Нажатие на SKU раскрывает его дополнительные фото, описание, свойства. Для одинаковых размеров фотографии могут наследоваться от товара; для цвета можно использовать фотографии цвета; отдельный SKU может переопределить. Не нужно загружать 80 одинаковых картинок для 80 размеров и цветов. Предпросмотр не публикует неполные SKU. Максимум 4 оси и 200 комбинаций по умолчанию (возможность пересмотра лимитов отдельно).

**Запрет**: не блокировать создание первого SKU из-за несуществующего глобального атрибута. Старый флаг is_variant — только совместимость до миграции. Удаление SKU, связанного с заказом/импортом, не должно молча уничтожать связь.

## Витрина

Один основной URL. Можно открыть тот же URL с query variant=<variant_id>, чтобы предварительно выбрать SKU из фида/рекламы; canonical всегда основной URL. Параметры выбора (цвет, размер и т. д.) переключают цену, SKU, остаток, фото, при необходимости другие свойства. Нельзя автоматически подменять отсутствующую комбинацию; показывать недоступность. Остаток 0 — «Нет в наличии». Корзина/заказ всегда хранят variant_id и снимок SKU/цены/параметров при покупке.

## Данные и импорт

Планируем нормализованные таблицы:
- product_variants: стабильный ID продаваемой единицы, product_id, SKU, price, stock, публикация и фото.
- variant_dimensions: id, product_id, code, title, sort_order.
- variant_dimension_values: id, dimension_id, code, title, image/hex (опционально), sort_order.
- variant_value_assignments: variant_id, dimension_id, value_id — одна выбранная опция по каждой оси, валидация принадлежности товару.
- import_product_keys: (source_key, external_product_key) → product_id.
- import_sku_keys: (source_key, external_sku_key) → variant_id.

Уникальность SKU внутри магазина важна, но артикул не единственный ключ импорта: внешний идентификатор из ERP/CSV/API может оставаться прежним при смене артикула. Не объединять строки разных источников по одному только SKU; конфликт требует отчёта и ручного сопоставления. Пакетный UPSERT, dry-run, отчёт и атомарные изменения. Одна строка экспорта/фида на SKU с общей группой товаров, собственной ценой/наличием/изображением и ссылкой variant=id.

Пример импорта (одна группа 1001):
| group_id | external_sku_id | SKU | Цвет | Размер | Остаток |
| --- | --- | --- | --- | --- | --- |
| 1001 | A1 | F-R-S | Красный | S | 5 |
| 1001 | A2 | F-R-M | Красный | M | 10 |
| 1001 | A3 | F-B-M | Синий | M | 7 |

## Утверждённый контракт: товар, вариант, артикул, характеристика

Не смешивать четыре понятия:

| Понятие | Смысл | Идентификатор и правила |
| --- | --- | --- |
| **Товар (Product)** | Общая карточка модели: название, описания, категория, бренд, SEO, основной URL, общие медиа/свойства | Неизменяемый внутренний product_id; сам по себе не является продаваемой единицей |
| **Вариант (ProductVariant / SKU-запись)** | Конкретное заказываемое исполнение с отдельным складским остатком, ценой и статусом | Неизменяемый variant_id; принадлежит ровно одному товару; запись существует и у простого товара |
| **Артикул (sku_code)** | Человекочитаемый код учёта/обмена, например F-RED-M | Уникальный непустой код в рамках магазина для продаваемых SKU; **не** первичный ключ и может быть изменён контролируемо |
| **Параметр варианта** | Ось выбора: Цвет, Размер, Память, Отделка и т. п. | Локальные ID оси/значения, словари глобальных характеристик могут подключаться опционально |
| **Обычная характеристика** | Описание товара или конкретного исполнения (состав, материал, вес) | Не порождает SKU автоматически и не подразумевает отдельный остаток |

Термин **SKU** в интерфейсе означает продаваемый вариант, но в данных нужно различать внутренний **variant_id**, запись варианта и её **артикул sku_code**. SKU-код не заменяет ни product_id, ни variant_id, ни внешний ID поставщика. У товара нет второго независимого «продаваемого SKU», когда появились дочерние варианты.

### Футболка Classic — эталонный сценарий

Основной URL: /futbolka-classic-1001. Все строки — один Product 1001:

| Цвет | Размер | Артикул | Остаток |
| --- | --- | --- | ---: |
| Красный | S | F-RED-S | 5 |
| Красный | M | F-RED-M | 10 |
| Красный | L | F-RED-L | 0 |
| Синий | M | F-BLUE-M | 7 |

Покупка «Красный/M» ссылается на variant_id, соответствующий F-RED-M; в заказе сохраняются variant_id и неизменяемый снимок артикула, цены и выбранных значений на момент покупки. Красный/L **существует**, хотя остаток 0. Отсутствующая комбинация (например, Синий/S в этом наборе) **не существует** и не может быть заказана или автоматически подменена ближайшим вариантом.

Для простого товара всегда **одна продаваемая SKU-запись** без видимого покупателю переключателя. Добавление осей превращает редактор в вариативный без нового Product, URL, копирования SEO и ручного создания отдельных карточек.

## UX: создание вариантов из карточки товара, без предварительной подготовки категории

Требования для следующего редактора (этап B; **не выдавать за реализованное в 0.5.20**):

1. Администратор создаёт обычную карточку. Вкладка «Варианты» предлагает «Добавить параметры», например Цвет: Красный, Синий; Размер: S, M, L. Создание глобальной характеристики и переключение «Различает варианты товара» **необязательны**.
2. Значения вводятся в нативных Joomla-полях с добавлением/удалением/сортировкой. При желании локальный параметр связывается с глобальным словарём нормализованных значений для поиска/фидов/импорта.
3. Команда «Создать комбинации» **предварительно** строит матрицу произведения выбранных значений (2×3 = 6); администратор исключает ненужные строки до сохранения. Неполные строки/коллизии не превращаются в опубликованные SKU.
4. Таблица редактирования: комбинация, артикул, цена, остаток, публикация/доступность, сортировка, изображения; массовая правка цен/остатков, копирование строки и удобное удаление **неиспользуемых** сочетаний. На строке раскрываются индивидуальные настройки SKU.
5. При редактировании старой комбинации её variant_id сохраняется. Изменение параметров не должно молча удалять использованные в заказах/импорте SKU; при необходимости деактивировать/архивировать с сохранением ссылочной целостности.
6. При удалении параметра или изменении значения предусмотреть предупреждение со списком затрагиваемых SKU, сохранение в одной серверной транзакции и контролируемую миграцию связей.
7. До реализации этого редактора интерфейс 0.5.19 с обязательным глобальным is_variant является **legacy**, не нормативной моделью. Его нельзя распространять в импорт, корзину и API как постоянное требование.

Ограничения прототипа 4 оси/200 комбинаций на одну карточку — **технический порог текущего решения**, а не ограничение количества товаров или строк импорта в магазине; изменение порога требует отдельной проверки производительности и UX.

## Витрина, изображения и выбор SKU

- Один основной URL и canonical для всей группы; переключатель параметров не открывает отдельный SEO-документ.
- У каждого реального варианта допустима deep link ссылка вида /futbolka-classic-1001?variant=245. Сервер по **variant_id** выбирает нужную комбинацию, не полагаясь на клиентскую цену/остаток; подменённый или принадлежащий другому товару ID отклоняется.
- При смене варианта меняются **артикул, цена, наличие, фотография**, а также только те характеристики, которые действительно зависят от исполнения (например, вес). Общее описание, бренд, категория и базовый адрес остаются.
- Приоритет галереи: **собственная галерея SKU → общая галерея значения параметра (например, Красный) → общая галерея товара**. Один набор красных фотографий используется красными S/M/L без дублирования файлов; индивидуальная галерея может переопределить.
- После выбора одного параметра остальные показывают только **существующие комбинации**. Несуществующие значения disabled, не превращаются в фиктивные SKU; отсутствующий SKU никогда не заменяется другим по умолчанию. Ранее выбранный SKU по умолчанию тоже должен физически принадлежать этому Product.
- **Нет в наличии (stock=0)** — действующий вариант без возможности обычной покупки при запрете предзаказа. Опубликованность и остаток — **разные** признаки. Лист ожидания и предзаказ подчиняются отдельным настройкам магазина.
- Корзина и сервер расчёта заказа валидируют текущую цену, остаток, статус и variant_id; браузерные значения не считаются источником истины. Резерв/списание остатка происходят для variant_id, с защитой от конкурентных покупок.

## Фильтры: совпадение в пределах одной продаваемой единицы

- Поиск товара по нескольким вариантным признакам должен находить **хотя бы один конкретный SKU**, удовлетворяющий всем условиям (AND между осями; OR внутри множественно выбранных значений одной оси). Нельзя брать «Красный» из SKU-A, а «M» из SKU-B и ложно считать товар совпавшим.
- Показываем **одну карточку Product**, даже если подошло несколько SKU: COUNT DISTINCT product_id. У карточки можно предварительно выбрать подходящий SKU и его изображение.
- В корневой категории фасеты — объединение реально используемых параметров включённых вложенных товаров; в дочерней — допустимый набор этой области. Значения, не встречающиеся ни у одного товара исходной области, не показывать. После выбора другого фасета ранее существовавшие, но несовместимые значения оставлять видимыми **disabled**, чтобы можно было снять выбор.
- Обычные описательные многозначные характеристики (например, «Металл + Камень») не трактовать как матрицу продаваемых SKU; их фильтрация может выполняться на уровне Product.

## Импорт, обмен, внешние ID и фиды

**Идентичность:** внутренние product_id и variant_id стабильны; код SKU может меняться. Два независимых соответствия — (source_key, external_product_id) → product_id и (source_key, external_variant_id) → variant_id. Внешние group_id нельзя слепо считать внутренним product_id. Повторный импорт по прежним ключам **обновляет** существующие записи, а не создаёт новые карточки или варианты.

Пример импортируемых строк:

| external_group_id | external_variant_id | sku_code | Цвет | Размер | Остаток |
| --- | --- | --- | --- | --- | ---: |
| 1001 | EXT-1 | F-R-S | Красный | S | 5 |
| 1001 | EXT-2 | F-R-M | Красный | M | 10 |
| 1001 | EXT-3 | F-B-M | Синий | M | 7 |

Требования импорта: сначала сопоставление источника/группы/SKU и нормализация значений параметров; проверка уникальности артикула, допустимости комбинации и связей; dry-run с конфликтами; пакетная серверная обработка; повторный запуск идемпотентен. Необъявленные строки не удалять автоматически; изменения SKU-кода/группы/архивация требуют отдельного правила и отчёта. Артикул, совпавший у разных источников, сам по себе **не** доказывает идентичность товара.

**Фиды:** товарная группа передаёт общий item_group_id, каждый продаваемый вариант — собственный стабильный id (не обязательно текущий изменяемый артикул), цену, наличие, релевантное фото, параметры color/size и точную landing-page ссылку с выбором SKU. Для Google Merchant Center комбинация id + item_group_id используется по правилам соответствующего канала; требуемые дополнительные атрибуты и формат проверяем **на момент реализации**. Для Google Search single-page схема может использовать ProductGroup + Product/Offer, общий canonical и отдельные query URL для предварительного выбора реального варианта. Для Яндекс Маркета и иных площадок — собственные адаптеры группировки/идентификаторов, без изменения внутренней модели.

Документы-источники для будущей проверки фидов:
- Shopify, [Product variants](https://help.shopify.com/ru/manual/products/variants/add-variants).
- Яндекс Маркет, [объединение вариантов](https://www.yandex.ru/support/marketplace/ru/assortment/operations/combine).
- Google Merchant Center, [Product data specification](https://support.google.com/merchants/answer/7052112?hl=en), [Item group ID](https://support.google.com/merchants/answer/6324507?hl=en).
- Google Search Central, [Product variant structured data](https://developers.google.com/search/docs/appearance/structured-data/product-variants/).

## Когда товар отдельный

Один Product + SKU для размеров S/M/L, цветов одной футболки, объёмов памяти **одной модели** телефона, вариантов отделки **одной конструкции** камина. Отдельные Product для принципиально иных моделей телефонов или каминов с собственным назначением, описанием, SEO и товарной идентичностью. Такие Product можно связать отношением «Другие модели» или «Похожие», но не принудительно группировать SKU.

## Критерии приёмки по этапам B–E

- **B:** создать Color+Size в самой карточке без глобальной характеристики; превью 2×3; исключить отсутствующую комбинацию; массово задать цену/остатки; повторное открытие сохраняет variant_id; нативная Joomla админка RU/EN; ссылки на связанные SKU не теряются.
- **C:** один простой Product = ровно один SKU, а не одновременно parent SKU и variants; миграция legacy-данных проверяется до/после, без дублей; все конфликты артикула/комбинации показаны; никакого автоматического удаления данных.
- **D:** красный M показывает верные фото/цену/остаток/SKU, красный L с нулевым остатком не продаётся без разрешённого предзаказа; deep link восстанавливает конкретную комбинацию; корзина и заказ привязаны к variant_id; сервер не принимает подменённые цены.
- **E:** повторный импорт не создаёт новых Product/SKU; внешние ID сохраняются при смене артикула; фильтр красный+M использует один SKU; фиды отправляют отдельный id на SKU и общий item_group_id; canonical остаётся основным URL; тесты массовых данных и реальная Joomla-приёмка.

**Статус реализации:** на 0.5.20 подготовлен только фундамент **A** в исходном коде. Наличие этого документа не доказывает реализацию редактора B, миграции торговых полей C, заказа/витрины D, импортёров/фидов/динамических фильтров E. Базу MiniMarket, код Joomla и версии релиза этим документированием **не меняем**.

## Безопасный план выполнения

**A — фундамент**. Аддитивная схема локальных осей и внешних ключей; тесты fresh-install, upgrade, FK, unique, проверка неизменности старых данных. Ни одной существующей SKU-строки не переписывать.

**B — удобный редактор**. Локальные параметры внутри товара, генерация комбинаций, нативная таблица и мини-карточка SKU, сохранение без глобального is_variant. Для существующих глобальных атрибутов/selection_json — совместимый перенос без потери исходных ID и данных.

**C — единая SKU-таблица для простого и вариативного товара**. Предварительная диагностика дубликатов, вариантов и коллизий. На каждый простой товар переносится ровно один SKU; если есть старые варианты, не создавать «базовый» дубль по догадке. Обязательный readback до/после.

**D — серверная торговля/витрина**. Единственный источник цены, остатка и артикула — SKU. Старые поля products остаются временным совместимым зеркалом, без двойного ручного редактирования. Витрина, корзина, учёт остатков и deep links работают по стабильному variant_id.

**E — импорт, фиды и фильтры**. Уникальные внешние ключи по источнику, пакетный импорт, одна строка на SKU в фидах; AND-фильтры применяются в пределах одного variant_id. Тесты производительности и реальный Joomla smoke.

**Принципы:** только development, не main; не трогать ядро Joomla; не создавать дополнительные локальные БД; не делать деструктивный автоматический backfill; каждый шаг сопровождается тестами и статусом, не заявлять A как готовый B–E.
