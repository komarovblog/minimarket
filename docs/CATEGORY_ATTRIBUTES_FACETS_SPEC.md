# MiniMarket — привязка характеристик к категориям и динамические фильтры

**02.11.2026. Статус: USER REQUIREMENTS + PROPOSED TECHNICAL DESIGN / DESIGN ONLY для нового функционала, без готовой Joomla-реализации.** Основано на шести уточнениях пользователя к выпуску 0.5.4. Реальное состояние 0.5.4: глобальные справочники атрибутов/значений и флаги `is_variant`, `is_filterable`, **нет** назначения характеристик категориям, заполнения характеристик в товарах, самих SKU-комбинаций и публичного фасетного фильтра. Английский интерфейс Joomla — выбранный пользователем язык, а не ошибка; все новые подписи должны быть локализованы в RU/EN, как существующие.

## 1. Модель владения данными

1. **Глобальный словарь**: единожды создаётся характеристика (`attribute_id`, уникальный `code`, название, тип `list/text/number/boolean`), у списков — общие значения (`value_id`, `attribute_id`, `code`, название). Создание значения «Чёрный» **не** означает его наличие во всех товарах с характеристикой «Цвет».
2. **Категория → характеристика**: отдельная связь `category_id ↔ attribute_id`. В карточке категории нужна вкладка **«Характеристики»**, в которой администратор выбирает применимые свойства из глобального словаря; у каждого свойства можно настроить порядок, обязательность заполнения, показ на карточке и использование в фильтрах. Возможность различать SKU ограничена типом `list` и соответствующим разрешённым флагом. Не делать копию самого свойства на каждую категорию.
3. **Наследование вниз**: подкатегория получает свойства родителей и добавляет свои. В форме видны собственные/наследуемые свойства с источником; унаследованные не записываются повторно. Для исключения унаследованного свойства предусмотреть явный **override/disable** у дочерней категории, но не удалять исходную родительскую связь. Если товар меняет категорию, список допустимых свойств пересчитывается; хранимые значения, больше не допустимые в новой категории, не удалять молча — требовать явного решения администратора при сохранении.
4. **Товар → значения**: редактор товара показывает **только** свойства конечной категории (с наследованием) и существующие значения. Простые типы имеют типизированные данные и проверку; списки используют ID значений. При изменении глобального названия товарам не нужно перезаписывать текст.
5. **SKU-вариант → значения**: характеристики, различающие варианты (цвет/размер), относятся к **реальным комбинациям SKU**. Один вариант: стабильный `variant_id`, собственный SKU, цена, остаток, статус, набор `(attribute_id, value_id)`. Общие характеристики, например Материал, могут храниться на уровне товара. Вариантные свойства не хранить одновременно как независимые множественные поля товара. Никаких «жёлтый L», если такого SKU нет.
6. **Медиа**: обложка/общая галерея остаются, связи для визуального значения/варианта используются без копирования файлов. Приоритет SKU → визуальное значение (например цвет) → общая галерея. Путь только `images/...`, без служебного Joomla-хвоста/width/height.
7. **Категория не равна набору значений**: выбор характеристики в категории лишь разрешает её использование. Доступные значения в фильтре определяются **реально назначенными значениям опубликованных товаров/вариантов**, не всеми значениями глобального справочника.

## 2. Правила фильтра в иерархии

- **Открыта конкретная категория**: фильтр строится по товарам **этой категории и её видимых подкатегорий, если их товары включены в каталог на этой странице**. Используются фактически доступные характеристики из набора этих товаров, а не перечень всех созданных в справочнике атрибутов. Если страница настроена показывать только товары непосредственно своей категории, область фильтра должна совпадать с этим выбором.
- **Открыт корень с несколькими подкатегориями**: объединённый список характеристик и значений всех включённых ветвей и товаров, с устранением дублей по `attribute_id/value_id`, а не по написанию заголовка. Свойства несовместимых групп могут одновременно находиться в исходном списке.
- **Вложенная категория**: не показывать свойства другой ветки, если товары этой ветки отсутствуют в текущем каталоге. При переходе вниз пересчитывается scope категории. В родительской категории значения могут идти от всех её реально видимых дочерних товаров.
- **Пустые значения справочника**: в категории с красными и жёлтыми товарами **не показывать** «Чёрный», если нет ни одного опубликованного товара/варианта с таким цветом. Вся характеристика отсутствует, если у подходящих товаров вообще нет заполненных значений.
- **Статус и наличие**: первоначально учитывать опубликованные товары, опубликованные значения и варианты, а также всю цепочку опубликованных категорий. Остаток 0 не равен неопубликованности: он участвует в фасетах, пока не выбран отдельный фильтр «В наличии». Когда выбран — варианты с остатком 0 исключаются из кандидатов.
- **Без дублей карточек**: одна карточка на один `product_id`, даже если совпало несколько SKU; превью, цена и остаток берутся от детерминированного подходящего варианта.

## 3. Динамические disable-фасеты

**Главное требование:** после любого выбора в фильтре пересчитать совместимость остальных значений, **отключить** невозможные, **не скрывать** уже отображённые значения или целые группы. Пользователь должен понимать, почему выбор недоступен.

1. Изначальный полный список свойств/значений фиксируется по публикации, заполненности и scope текущей страницы. Он определяет структуру фильтра в данном контексте, независимо от последующих выборов.
2. После установки значения других групп вычисляется число **уникальных товаров**, имеющих реальный опубликованный вариант, удовлетворяющий условиям и пробному значению.
3. Если возможных товаров `0` → `disabled=true`, стиль отключён и нельзя установить галочку; если больше `0` → можно выбрать, и опционально рядом показан счётчик.
4. Если ни одно значение группы несовместимой категории не остаётся доступным — **отключить всю группу**, но оставить её и её значения видимыми; не терять форму/контекст страницы.
5. **Внутри одного свойства — ИЛИ**, **между свойствами — И**. Для расчёта кандидатов в группе A использовать остальные выбранные группы, **игнорируя текущий выбор A** (*disjunctive self-exclusion*), чтобы пользователь мог добавить альтернативный цвет к уже выбранному. Например при выборе `Материал=Джинс` в группе Цвет синий активен, красный/жёлтый недоступны; в группе Материал можно выбрать ещё другой материал, не снимая джинс.
6. **Все вариантные условия должны совпасть в одном реальном `variant_id`**. Нельзя объединять цвет от красного S и размер от жёлтого L, искусственно создавая красный L. Общие атрибуты товара присоединяются к каждому его варианту логически, но не порождают декартово произведение вариантов.
7. **Сохранить уже выбранные значения** в URL/истории фильтра и показе UI. При изменении контекста, устаревшей ссылке или скрытом снаружи изменении остатков возможно состояние 0 результатов; выбранное значение оставить видимым, предложить очистку. Не скрывать selected и не удалять выбор молча.
8. Не запрещать все значения текущей группы только потому, что один из её элементов уже выбран: сначала пересчитать доступность с учетом OR в этой группе.
9. После каждой интеракции обновлять одновременно доступность фасетов, число результатов и товары; не показывать старые, уже неверные числа как актуальные.

### Показательный сценарий

| Состояние | Материал | Цвет |
| --- | --- | --- |
| Исходно в родительской категории | Джинс, Хлопок, Лён доступны | Синий, Красный, Жёлтый доступны |
| Выбран **Джинс**; в реальных товарах для него есть **только синий** | Джинс выбран; другие материалы остаются альтернативами для OR, если представлены в исходной области | **Синий доступен**, Красный и Жёлтый **видны, но disabled** |
| Выбрано свойство/значение товара из одной ветки | В другой несовместимой группе нет подходящих товаров | **Вся несовместимая группа видна, но disabled** |

## 4. Производительность и обновление UI

Динамика **не означает** `N` сетевых обращений или SQL-запросов на каждый checkbox. Предлагается один серверный endpoint, который за одно обращение возвращает актуальные товары (страница/сортировка/количество) **и состояние всех фасетов**.

- **Без повторной загрузки страницы**: асинхронный fetch после выбора; при быстрых кликах — отмена устаревшего запроса/актуальный response ID, опциональный debounce 100–200 мс, показывать состояние обновления. Базовое отображение каталога/фильтров должно работать и с обычным запросом без JS.
- **Не считать по всем значениям в PHP**: выборка реальных опубликованных product/variant ID в SQL, затем `GROUP BY attribute_id, value_id` и `COUNT(DISTINCT product_id)`. Для каждой фасетной группы применяется self-exclusion. Запросы сгруппированы по группам, **без N+1 на значение**.
- **Индексы под реальные условия**: category subtree/product visibility, `product_id ↔ variant_id`, `variant_id ↔ attribute_value_id`, `attribute_id/value_id`, цена, остаток, публикация. Специфика индексов проектируется по итоговой схеме и проверяется `EXPLAIN ANALYZE`, а не угадывается.
- **Кэш**: исходные фасеты категории и заполненные значения можно кэшировать по category scope, дате/версии каталога, публикации и конфигурации. Ключ динамического состояния включает нормализованный фильтр и переключатель «В наличии»; менять/сбрасывать кэш после правок товаров, SKU, связей и остатков. Не использовать устаревший кэш для проверки возможности заказа.
- **Скорость**: для малого/среднего каталога задача технически выполнима в рамках обычного интерактивного HTTP-запроса. **Нельзя заранее обещать конкретные миллисекунды** без реальной БД, числа SKU/значений и нагрузки. На целевом OpenServer и SpaceWeb добавить SQL-план, профилирование и нагрузочный тест для 100/1 000/10 000 товаров и соответствующих вариантов; оптимизировать узкие места измерениями.
- **Graceful degradation**: если асинхронный расчёт недоступен, сохранить выбранные параметры, дать повторить или отправить обычный GET; сервер по-прежнему проверяет фильтр (в том числе несовместимые комбинации).

## 5. Этапы реализации, без опасного переноса торговли

- **6.2 — категория → характеристика**. Отдельная таблица связей, вкладка «Характеристики» в категории, наследование с явным исключением и тесты на перестановку родителя, пересечение ветвей и удаление назначения. У существующих категорий сначала нет назначений, данные не теряются. RU и EN обязательно.
- **6.3 — редактор товара**. На вкладке «Характеристики» видны только применимые свойства из категории/предков. Сохранение типизированных общих значений, проверка принадлежности и миграционные тесты при смене категории; не копировать глобальные значения. Список значений для товара зависит от его категории, но отображаемая админом форма может показывать полный справочник **для разрешённой характеристики**, а фильтр — только реально использованные значения.
- **7 — варианты SKU**. Миграция existing product SKU/price/stock → один primary variant, атомарная модель реальных сочетаний цвет/размер, уникальность сочетаний и неизменный URL товара. Правило: **один источник истины по торговым данным**, ни в коем случае две независимые цены/остатка.
- **7.4 — медиа по цвету/варианту**. Существующие общие фотографии не копировать; модель связей точный variant → visual attribute value → common.
- **9.1 — статические фильтры**: источник scope/фасетов по опубликованным данным, применяемость к категории и её подкатегориям, без ложных значений.
- **9.2 — динамические фасеты**: disable вместо hide, серверный endpoint, disjunctive counts, совместимость одного SKU, обработка быстрых кликов, история URL.
- **9.3 — оптимизация**: индексы, планы SQL, cached base facets, bench + регрессии. Изменение остатков и публикации всегда отражается корректно после сброса кэша.

**Не делать**: подсовывать все глобальные характеристики всем товарам, копировать характеристики в категории как новые справочники, фильтровать по общему набору `value_id` без связи с опубликованными SKU, выдавать черный цвет по факту его существования в справочнике, удалять 0-value группы после первого выбора, связывать цвет и размер из разных variant_id, загружать одно изображение на каждый размер.
