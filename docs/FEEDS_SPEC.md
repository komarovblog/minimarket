# MiniMarket — управление товарными фидами и правила отбора

**Проект спецификации v1.0 · 01.11.2026 · Статус: DESIGN ONLY.** Ничего из описанного ниже в админке не реализовано. Главный план — [ROADMAP.md](ROADMAP.md), шаг **11.6**. Внешние форматы развиваются: перед написанием конкретного экспортера требуется сверить актуальную спецификацию соответствующего получателя, а затем зафиксировать версию/набор тестов.

## 1. Самостоятельный раздел «Фиды»

Админка MiniMarket → **Фиды** (наравне с Категориями/Товарами/Комплектами, не отдельный обязательный Joomla plugin). Один магазин может иметь **несколько независимых фидов**, даже одного формата, с разными категориями, наличием, правилами исключения и получателями.

**Список фидов**: статус, название, назначение, формат, число включенных предложений, число исключенных/ошибочных, время последней успешной генерации, состояние задачи (готов/генерируется/ошибка), ссылка/действия «Просмотр / Скачать / Сгенерировать / Проверить / История». Контроль ACL: смотреть, управлять, запускать, просматривать закрытые URL. Строка с фидом сама ничего не отправляет во внешнюю систему.

**Редактор одного фида — вкладки:**

1. **Основное:** название, активен/выключен, получатель, формат, валюта, язык, публичный домен, ID фида, частота обновления, защищенная URL раздача, сохранение и ручной запуск. Получатель — профиль правил (например, Яндекс Товары или Яндекс Директ), не просто синоним XML.
2. **Отбор:** категории (дерево, несколько значений, включать потомков/нет), бренд/коллекция (если существуют), типы (товары/варианты/комплекты), опубликованность, наличие (только в наличии / все допустимые), ценовые ограничения при потребности, явные исключения товаров/SKU, сегменты и признаки. При пустом дереве — **все опубликованные доступные категории** как явный default.
3. **Поля и соответствия:** какие поля источника MiniMarket попадают в обязательные/необязательные поля поставщика, price, currency, URL, picture, GTIN/brand/MPN, categoryId, variant group, additional images, sale price, НДС и доставка (только когда они фактически настроены), дополнительные свойства и выбранные атрибуты. Для каждого провайдера — проверяемый профиль соответствий; нельзя позволять произвольным полям подменять реальную цену.
4. **Генерация и доставка:** генерация по cron либо вручную, TTL, формат UTF-8, публичная ссылка для роботов (при нужде непредсказуемый секретный URL), скачивание, автоматическое обновление атомарным переключением файла, фиксированное имя и version. Внешняя отправка по API — **отдельная интеграция с явным включением**, не предполагается флагом «Активен».
5. **Предпросмотр и ошибки:** счётчики по категориям/типам, **первые N включённых предложений и причины исключения** (неопубликован, нет родителя, категория не выбрана, выключено вручную, отсутствует обязательное фото, SKU/цена/URL невалидны и т. д.); проверка схемы XML/CSV и требований конкретной площадки, попытка сгенерировать «тестовую выборку» без замены рабочего фида.
6. **История:** журнал запусков, время, результат, версии профиля, число строк, список типов ошибок, контроль неизменности предыдущей успешной версии. Не логировать персональные данные или секретные токены.

## 2. Иерархия правил отбора и признаки у записей

**Обязательные серверные ограничения**, которые нельзя переопределить настройкой фида: опубликованный и доступный на сайте товар; опубликованная цепочка родителей категории; опубликованный вариант/комплект; корректный конкретный URL; цена/идентификатор/фото и прочие обязательные поля профиля; отсутствие запрета на экспорт. Доступность «на складе» — отдельное правило получателя, **не равна публикации**.

**Настройки каталога** (подготовить поля при проектировании редакторов, не добавлять их преждевременно):
- У **категории**: «Участие в фидах» = **Наследовать / Разрешить / Запретить**. «Запретить» исключает ветку целиком; явно разрешённая дочерняя категория не должна обходить запрет своего предка без специально согласованного правила.
- У **товара** и **комплекта**: «Разрешить экспорт» = **Наследовать / Да / Нет**. По умолчанию «Наследовать» означает можно участвовать при соблюдении правил выбранного фида. Неопубликованные не экспортируются даже при «Да».
- У **варианта SKU**: «Разрешить экспорт» = **Наследовать / Да / Нет**; «Нет» исключает только данный SKU, не весь родительский товар.
- У **конкретного фида**: список точечных исключений, чтобы один SKU можно было выгрузить в Яндекс Товары, но исключить из отдельного рекламного фида. Точечное «включить» возможно **только при выполнении общих запретов и дерева выбранных категорий**. Никакой флаг не публикует скрытый товар.

**Детерминированное правило**: (1) опубликованная сущность и все опубликованные предки; (2) глобальный запрет экспорта категории/товара/комплекта/SKU; (3) включение в выбранные категории, типы и сегменты конкретного фида; (4) точечное исключение фида; (5) наличие и валидность обязательных атрибутов по профилю. Тот же алгоритм должен использоваться **для предварительного просмотра, генерации и счётчиков**. Причины исключения видны администратору.

**Товары с несколькими категориями:** способ выбора основной категории для categoryId определить до реализации; если товар попадает в несколько выбранных веток, генерировать **одно предложение на SKU**, а не по одному на каждую категорию. Комплект включать по отдельному флагу и своему categoryId; его availability определяется компонентами.

## 3. Форматы и специфика получателей

| Профиль | Начальный формат | Особенности |
|---|---|---|
| **Яндекс Товары** | YML | Список categoryId/currencies/offers, требования к обязательным полям (изображение, бренд, цена, availability), валидация текущей спецификации |
| **Яндекс Директ — товарные объявления** | YML, позже другие поддерживаемые форматы | Уникальный стабильный offer id, correct available, категория, валюта, фото, нужные свойства для сегментации |
| **Яндекс Маркет** | YML, только по актуальному документу Маркета | Логистика, НДС, SKU, карточки и правила доступности могут отличаться от Яндекс Товаров/Директа |
| **Google Merchant Center** | Product data XML/TSV/CSV (позже API) | ID, item_group_id, price, availability, shipping/return policy по требованиям рынка, GTIN/brand при наличии |
| **Универсальный XML/CSV** | XML/CSV по сохраненному шаблону | Сопоставление доступных полей и формат без объявления его стандартом Google/Яндекса |

**Профиль получателя** выбирается отдельно от синтаксиса: два YML-файла разных сервисов могут иметь несовместимые требования. Для всех значений цены/наличия используем **тот же расчёт, что карточка товара и корзина**; не храним их «фидовую копию».

Идентификаторы предложений стабильны между фидами одного бизнеса: один SKU варианта → один offer ID, один продаваемый комплект → свой отдельный offer ID. После миграции простого товара сохранять маппинг идентификатора для предотвращения разрушения истории товаров на площадках. Бренды и категории в фидах используют реальные записи, без выдуманных значений.

**Наличие:** исходное stock/availability отражает факт на сайте. Некоторые получатели разрешают `out_of_stock`, другие требуют только доступные предложения. Поэтому «Только в наличии» — **настройка профиля/фида**, но не общая техническая причина удалять товар из всех выгрузок. Например, Google Merchant имеет поддерживаемое `out_of_stock`, но для конкретной программы Яндекс Товаров могут требоваться предложения `available=true`; проверять до включения профиля.

## 4. Хранение, безопасность, обновление

- Сущности: `feeds` (конфигурация), `feed_targets` (профиль/формат), `feed_selection_rules` (параметры и списки ID), `feed_item_overrides` (исключения по SKU/поставщику), `feed_runs` (журнал), `feed_field_mapping` (поля). **Названия предварительные**, не команда создать SQL.
- Для большого каталога: выборка пачками, избежание N+1, memory limit, генерация во временный файл и **атомарная публикация** только успешно валидированного файла; старую исправную версию не перезаписывать пустым/сломавшимся.
- Возможность **ручной проверки** и чернового фида, который не выдается публично. Статус фида отдельно от статуса товара.
- Доступ извне: по HTTPS и управляемому URL, проверяемые настройки публичности/токена, отключение/ротация токена без изменения содержимого, запрет индексации URL фидов, rate limits при динамической отдаче; секреты не выводить в GitHub.
- Указать дату генерации и checksum, записывать статистику и предупреждение «последнее успешное обновление было ...». Незавершённые запуски после ошибки не должны выдавать старый фид за новый.
- Не разрешать выгружать данные из непросмотренных категорий без нужной ACL на просмотр товаров.
- Обновление фида по cron и по кнопке — разные источники запуска, но **одна** проверяемая реализация правил и логики генерации. Отдельный замок от параллельного запуска.
- Никакие механизмы экспорта не меняют цены/публикацию/остатки на сайте. Не делают заказы, не пишут во внешние кабинеты без отдельной явно активированной интеграции.

## 5. Приёмка

- [ ] Создать два YML-фида: «Все опубликованные в наличии» и «Только выбранная категория и все её подкатегории», сравнить экспорт и предпросмотр.
- [ ] Исключить товар/вариант в одном фиде и проверить, что другой фид не изменился.
- [ ] Исключить ветку категории: потомки/товары исчезли. Неопубликованный предок никогда не обходится локальным флагом.
- [ ] Проверить разные режимы наличия и форматы поставщика, без пустых/фиктивных price, image, url и брендовых полей.
- [ ] Проверить стабильность offer ID после обновления товара и миграции простого SKU в default variant, отсутствие дублей, поддержку комплектов.
- [ ] Тестовый предпросмотр, ручная и cron-генерация используют одну выборку. При ошибке сохранена предыдущая корректная версия, лог показывает понятные причины.
- [ ] Правила YML/Google форматов проверены по **актуальной официальной документации на дату включения**, а не только по исходному проекту.
- [ ] Все тесты CI (форматы/XML/CSV и SQL выборка), затем один реальный Joomla smoke без отправки фида на внешнюю площадку.
