# MiniMarket ↔ Shop: анализ функционального ТЗ на 12.11.2026

**Источники:** `komarovblog/shop` (`development`), [`docs/REQUIREMENTS_V2.md`](https://github.com/komarovblog/shop/blob/development/docs/REQUIREMENTS_V2.md), в первую очередь §§2.4–2.12, 5, 6.3–6.25, 11.2–11.5, 12; `docs/REQUIREMENTS.md` — в значительной части исторический и содержит **прямо отменённые решения**. Ветка MiniMarket — `development`, код 0.6.7 и интерфейсная итерация 0.6.8.

**Важное разграничение:** Shop здесь — **утверждённое функциональное ТЗ S00**, а не доказательство готового работающего функционала. MiniMarket — реализуемый компонент Joomla 6, не Symfony. Переносить можно **продуктовую модель и условия**, но не ORM/Twig, Bootstrap 6 alpha, организацию проекта и несовместимые старые решения.

## 1. Главный вывод: три независимые оси, один Order.status

| Измерение | MiniMarket 0.6.7 | Shop: действующее ТЗ | Решение к обсуждению |
|---|---|---|---|
| Основной статус заказа | `new, confirmed, completed, cancelled`; оператору доступны произвольные ручные изменения | §6.11: `Новый → В работе → Завершён`; `Отменён` только до передачи, с обязательной причиной; автоматическое завершение из «В работе» только при полном вручении и полной оплате | **P0.** Оставить 4 состояния, подписать `confirmed` «В работе» (0.6.8 меняет UI-ярлык), затем в отдельной бизнес-итерации ввести запрещённые переходы, причину отмены и автоматическое завершение |
| Оплата | `unpaid, paid, refunded` прямо в `orders.payment_status`; `payment_reference/payment_url` ручные | Ожидает оплаты / Обрабатывается / Оплачен, по доказательствам от банка или подтверждённому документу; возврат — независимая операция | **P0.** Добавить независимые PaymentAttempt / PaymentTransaction / RefundTransaction, идемпотентность. Не превращать «возвращено» в основной статус оплаты. Не пытаться выдавать ручное заполнение ID за ЮKassa |
| Исполнение/доставка | `orders.fulfillment_status` pending/shipped/delivered, отдельные `shipments.status` new/in_transit/delivered/cancelled | §6.13: 7 состояний «Ожидает сборки», «Собирается», «Готов к передаче», «В доставке», «Ожидает получения», «Вручён», «Доставка не удалась»; независимая история событий | **P0.** Сначала согласовать правила для самовывоза, курьера, ПВЗ, нескольких отправок; затем единый источник состояния (Shipment + события), а не два конкурирующих ручных переключателя |
| Возврат | Пять состояний (new/approved/received/rejected/closed), решение о возврате и позиции | §6.16: шесть стадий требования + независимые «деньги» и «замена/доставка» | **P1.** Перенять стадии и независимые факты; деньги возвращены ≠ возврат товаров завершён |

### Предлагаемая модель заказа (после согласования)

- **Основной Order:** Новый (создан); В работе (явно принят оператором); Завершён (оба факта: полностью оплачен и полностью вручен, проверенные); Отменён (весь заказ, подтверждённая причина, до передачи). Просмотр не меняет статус. Возврат после завершения не переоткрывает Order.
- **Payment:** Ожидает оплаты → Обрабатывается → Оплачен. Неуспех попытки хранится в PaymentAttempt и не превращает Order в состояние «отменён». Возврат денег фиксируется отдельно, включая частичный и подтверждённый.
- **Исполнение:** Ожидает сборки → Собирается → Готов к передаче → (В доставке → Ожидает получения) → Вручён; при доказанном окончании без вручения — «Доставка не удалась». Отдельные этапы пропускаются, если неприменимы. При нескольких доставках одна операция = отдельный Shipment, а агрегированное состояние исполнения заказа **вычисляется по применимым отправкам**. Причина первичная/повторная/замена — не статус.
- **Смену бизнес-статусов нельзя внедрять только CSS / формой**, прежде нужна миграция данных, правила переходов, резервов, корректное признание платежей и вебхуки. Нынешние ручные платежи — тестовый/административный режим с явной оговоркой.

## 3. Что MiniMarket уже делает сильнее/иначе

- **Нативная Joomla 6:** реальные стандартные ACL, меню, компоненты, модули и темы Atum/Bootstrap 5, без создания второго фреймворка/панели или необходимости переносить Symfony/Twig.
- **Категорийная модель и атрибуты:** дерево категорий и правила участия/наследования характеристик; сложные фильтры, SEO-фильтры с тремя режимами совпадения. У Shop это в большей степени проектное ТЗ, не доказанная рабочая реализация.
- **Одна цена товара и отдельные SKU-комбинации опций:** товарная матрица, связанные товары, самостоятельные комплекты, галереи; требуется отдельно согласовывать возможную разницу с актуальной Shop ProductVariant/Bundle моделью. Не заменять существующую схему импульсивно.
- **Режимы физического и цифрового магазина:** лицензии/файлы/облако/ручная выдача, управление цифровыми доставками. Текущая Shop V2 в основном про физические товары.
- **Фиды, встроенный импорт/экспорт, SEO, бренды, коллекции, промокоды** уже имеют рабочие административные сущности MiniMarket. Не считать их «отсутствующими» только потому, что есть пункт в Shop.
- **Несколько доставок на заказ и Return, связанный с конкретной Shipment** появились в 0.6.7. Они могут служить базой для причин повторной доставки и гарантийной замены без нового заказа; денежные доказательства ещё нужны.

## 4. Рекомендованная очередность обсуждения

**Этап A (принять модель, без опасных миграций):** утвердить 4 статуса Order, 3 Payment, 7 Fulfillment и правила переходов для самовывоза, курьера, ПВЗ, цифрового товара и нескольких Shipment. Выбрать, как агрегировать статус всех доставок в один прогресс заказа. Обговорить обязательность выбора Joomla User в ручном заказе, не отбирать guest-mode без отдельного решения.

**Этап B (данные и события):** спроектировать `PaymentAttempt`, `PaymentTransaction`, `RefundTransaction`, `ShipmentEvent`, строгий журнал OrderHistory, причины отмены и аудиторские доказательства. Решить, как переводить прошлые `orders.payment_status='refunded'`, старые `fulfillment_status` и `shipments.status` без придумывания фактов задним числом.

**Этап C (рабочие операции):** ввести матрицы переходов и валидацию, автоматическое закрытие Order только по подтверждённым фактам, антидублирование возвратов и резервы SKU. Затем реализовывать внешние адаптеры ЮKassa и СДЭК.

**Этап D (второй круг):** раздельная экономика, брак, CRM-покупатели, уведомления, финансовая аналитика и сохранённые представления. Нельзя требовать отчёта по прибыли до появления проверенных данных себестоимости, возвратов и расходных операций.

**0.6.8:** только безопасные изменения админ UI — отдельный выбор поддерживаемого метода подтверждения, при ручном заказе привязка к реальному Joomla User, повторные доставки из любого места, вертикальные блоки заказа и понятная история. **Не утверждает и не реализует новые платёжные/логистические жизненные циклы** до решения по этапам A–C.
