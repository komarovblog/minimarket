# MiniMarket — заказы, остатки, резервы, возвраты, отчёты

**Принято 13.11.2026.** Актуальная продуктовая карта для этих подсистем. Репозиторий `komarovblog/minimarket`, ветка `development`, Joomla 6, PHP 8.4/8.5, MySQL 8.4. Предшествующие описания 0.6.7–0.6.11 не должны переопределять эту карту. Реальное браузерное тестирование Joomla/Atum у пользователя **ещё не подтверждено**.

## I. Разделы интерфейса: ровно одна последовательность

Общие группы главного экрана, системного левого меню и Joomla dashboard preset:

1. **Управление** — Заказы, Доставки, Возвраты, Платежи.
2. **Магазин** — Категории, Товары, Комплекты, Бренды, Коллекции, Связи товаров, Связи комплектов, Характеристики, Опции.
3. **Маркетинг** — Отзывы, Промокоды, SEO-фильтры.
4. **Отчёты** — Остатки (первый и пока единственный отчёт).
5. **Инструменты** — Импорт / Экспорт, Фиды.
6. **Настройки** — Способы доставки, Способы оплаты, Способы регистрации, Способы уведомлений, Настройки.

Запрещено дублировать сущности в разных группах; отчёт открывается `view=stockreport`. У карточек заказа/доставки/возврата/платежа — **штатные Joomla uitab**, а не собственная реализация вкладок. Списки, включая отчёт, используют **NativeListTools → joomla.searchtools.default**, управление столбцами в стиле Joomla. Не вносить новые цвета, фоновые панели, крупные кастомные кнопки вместо Atum.

## II. Раздельные состояния заказа

- **Основной заказ (`orders.status`):** `new` (Новый), `confirmed` (В работе), `completed` (Завершён), `cancelled` (Отменён). Отменён — терминальный статус; статус доставки не должен его молча отменять.
- **Оплата (`orders.payment_status`):** `unpaid`, `processing` (подготовлено в модели, не подтверждение банка), `paid`, `refunded`. Источник факта оплаты — ручное подтверждение или будущая проверенная интеграция; сумма/способ и источник хранятся отдельно.
- **Выдача/исполнение (`orders.fulfillment_status`):** `awaiting_assembly`, `assembling`, `ready`, `in_transit`, `awaiting_pickup`, `delivered`, `failed` плюс legacy `pending`/`shipped` для совместимости старых данных.
- **Возврат** — отдельное дело `returns` со своими стадиями `new → approved → received → closed` или `rejected`, и отдельно `resolution`. Не является статусом платежа и не должен автоматически инициировать денежный возврат.
- **Перевозки** — отдельные `shipments` с датами, tracking_number, перевозчиком, несколькими доставками одного заказа (повторные/замены).
- Правила переходов в `admin/src/Service/OrderLifecycle.php`, контроллеры должны проверять ACL, CSRF, транзакцию и реальный переход. `order_manual_status_enabled=0` выключает ручную смену **главного** статуса, не ввод фактов о доставке и оплате. Создание доставки само по себе не означает «В пути».
- Кассовые и провайдерские платежи пока **не интегрированы**. Реестр `payments` показывает обязательство по каждому заказу; `payment_records` сохраняет только фактические подтверждённые **ручные** операции после 0.6.11; прежним заказам не придумывать квитанции. Отдельного надёжного RefundTransaction/частичной оплаты ещё нет.

## III. Остатки и резервы — архитектура без обязательного плагина

**Резервы — встроенная ответственность `com_minimarket`.** Порядок:

- В корзине **не резервировать**.
- При успешном создании физического заказа внутри одной транзакции `OrderStorage::create → StockReservation::allocate` проверяются и вычитаются доступные SKU; записи по учётным ключам `product/variant` попадают в `#__minimarket_stock_allocations` со статусом `held`. Для комплектов учитываются компоненты, а не фиктивный остаток комплекта.
- `products.stock` / `product_variants.stock` — **уже свободный остаток** (резерв вычтен), в отчёте `В резерве` вычисляется отдельно по `held`, `Всего учтено = свободно + резерв`; добавлять резерв к свободному при продаже **нельзя**.
- Разрешённая отмена **до передачи/вручения**: `StockReservation::release` возвращает количество один раз, `held → released` в транзакции. После подтверждения выдачи/передачи: `StockReservation::fulfill`, `held → fulfilled`, возврата в свободный остаток **нет**.
- Для оплаченного самовывоза `reserved_until` — срок проверки/контакта с покупателем, не разрешение автоматически отменить оплаченный заказ. Для неоплаченного самовывоза с оплатой при получении: стандартный срок 3 дня; автоматическая отмена по истечении **выключена по умолчанию**.
- Легаси-заказы отмечаются `reservation_state=legacy` и **не получают искусственно созданных резервов/списаний**.

**Необходимость плагина:** `plg_task_minimarketreserves` v0.6.10 — маленький **необязательный** Joomla Scheduler adapter, только запускает `ReservationMonitor::run` для напоминаний и настраиваемой автоматической отмены; **не реализует и не дублирует складскую логику**. Никакого отдельного «плагина резервирования товара» в обязательной цепочке покупки нет. В 0.6.12 обычный `release-to-desktop.ps1` отдаёт ZIP компонента и необязательный демо SQL **без плагина**. Если действительно нужен фон Joomla: тот же скрипт с параметром `-IncludeTaskPlugin`, отдельно установить и включить Scheduled Tasks. Пока фон/SMTP/cron не подтверждены в живой Joomla, не говорить, что напоминания отправляются автоматически. Без Scheduler пользователь управляет заказами через фильтры вручную.

## IV. Возвращённый товар: ЧТО СЕЙЧАС НЕ РЕАЛИЗОВАНО

Сейчас `ReturncaseController` и `ReturnsController` управляют заявкой/позицией/решением; **не существует автоматического или ручного действия «Принять пригодный товар на склад» с учётной транзакцией**. Статус `received` **не увеличивает** `stock`. Это намеренно не подменено отменой исходного заказа: при доставке резерв уже `fulfilled`, а не `held`. **Возврат денег** также не равен восстановлению склада.

Следующий отдельный этап: после получения/осмотра товара оператор выбирает «Пригоден для продажи → вернуть на склад» с количеством; повреждённый/непринятый/неполный товар не увеличивает доступные остатки. Реализовать отдельный неизменяемый складской журнал с уникальным ключом по возвращаемой позиции и защитой от двойного зачёта; суммарно нельзя восстановить больше фактически проданного; для комплектов нужна историческая раскладка компонентов на момент продажи; старые заказы без исходных allocation не восстанавливаются автоматически. Действие должно быть независимо от `resolution=refund/replacement`. До этого **не выдавать** восстановление остатков после возврата за готовую функцию.

## V. Отчёт «Остатки» — версия 0.6.12

Первый отчёт расположен `Отчёты → Остатки`, реализации:
- `admin/src/Service/StockReport.php` (read-only выборки и расчёт);
- `admin/src/View/Stockreport/HtmlView.php` (период, поиск, фильтры, сортировка, пагинация);
- `admin/tmpl/stockreport/default.php` (нативный Joomla SearchTools и таблица).

**Единица учёта:** простой физический товар по `product:id` при общем остатке либо вариант `variant:id` при раздельном учёте вариантов. Отдельные строки комплектов отсутствуют — их состав уже списан с физических компонентов.

Колонки: товар, SKU, **доступно**, **резерв**, **всего учтено**, **фактически отгружено/вручено за 30/90 дней**, **запаса хватит, дней**, **ABC**, **прямая выручка**. «Хватит, дней» = доступно / (подтверждённый спрос за выбранные 30/90 дней / 30/90). При отсутствии наблюдаемых продаж показывать прочерк, не бесконечность. Спрос по `stock_allocations.status=fulfilled` с привязкой к оплаченному и вручённому заказу; поэтому включает расход компонентов комплектов. Вклад «Прямая выручка» отдельно по `order_items` **простых товаров** в оплаченных и вручённых заказах; доход от проданного комплекта **нельзя правдоподобно приписать компонентам без исторических долей**, поэтому в ABC он не участвует.

ABC строится по валовой выручке (не прибыльности): **A — первые 80%**, **B — следующие 15%**, **C — оставшиеся 5%**. Рассчитывается по всему каталогу **до** фильтрации и пагинации. Товары без прямой выручки — «—». Нет надёжного нетто-оборота: реальные возмещения/списания/возвращённые товары ещё не учтены как отдельные финоперации. Это операционный прогноз на истории, **не обещание будущего спроса**.

Фильтры: период 30/90 дней, поиск по SKU/названию, нет доступного запаса, не более 7 дней, резерв, нет продаж, ABC. При отключённом учёте остатков предупреждать об ограничении точности. Отчёт read-only, не пишет складские данные, не требует новых таблиц. История до внедрения учётных allocations (0.6.10) неполная; это следует явно учитывать.

## VI. Проверка / обновление

- Источники: `docs/MASTER_PLAN.md` (карта), `docs/SETTINGS_REGISTRY.md` (поля и потребители), `CURRENT_TASK.md` (ход проверки), `docs/ITERATION_RULES.md` (процесс); текущая детализация — этот документ.
- Пакет для установки обновляется штатным скриптом **одной командой**: `powershell.exe -NoProfile -ExecutionPolicy Bypass -File "C:\OSPanel\home\minimarket.local\scripts\release-to-desktop.ps1"`. Демоданные при обновлении **не импортировать**. Перед новой миграцией — backup.
- В 0.6.12 SQL-миграция `SELECT 1;` (только read-only отчёт); системный SQL каталог не меняется.
- CI PHP 8.4/8.5 + MySQL 8.4 + Windows ZIP обязательно. Публикация `development` **не равна** ручной приёмке в локальном Joomla 6: проверить RU/EN, светлая/тёмная тема, 6 групп/меню, фильтры/таблицы, пустую/смешанную БД и товар с опциями, комплект, выданный/отменённый заказ.
